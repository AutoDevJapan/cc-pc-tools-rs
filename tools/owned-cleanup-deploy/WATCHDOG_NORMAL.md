# Watchdog normal distribution resources

The normal update entry requires one live producer-owned build product before
opening the installed target. It moves that product once and invalidates the
previous alias. JSON, a path/hash, an old clear verdict and a source test do not
issue the product. The current normal artifact issuer remains unavailable.

Original retained installation records identify the predecessor source and
release digest. They are read through fresh classification and held handles,
hashed and decoded from the same buffers. Their agreement is recognition
evidence. The normal current-target purpose issuer must independently establish
the original build-to-install link and current generation before installed
metadata or body access. That issuer remains unavailable; the summary's
installed=true is not promoted to a raw build receipt.

When both resources are genuinely issued, the files adapter keeps original
evidence, artifact, target baseline and parent handles through the update.
Owner/group/DACL and full identity checks remain in the held-file transaction.
Normal generation rechecks repeat purpose and artifact/evidence checks.

The resident adapter uses the existing registered task and exact running
instance GUID, S4U/Limited principal, XML digest, launcher action and engine PID.
It retains query/synchronize handles for either normal closed chain: launcher
to watchdog when already limited, or launcher to one reduced launcher child to
watchdog. Both acquisition and the pre-stop recheck require the same principal,
image paths, parent links and creation order, and refuse ambiguous chains or
extra descendants. Task names and proxy health replies
alone do not authorize a stop. The only stop call is on the exact instance
after the definition and engine generation are compared again. All Actions
must contain exactly one Exec and its Context must bind the one S4U/Limited
principal. The returned XML bytes are checked against their digest and field
projection. The same registered task XML is rechecked immediately before Stop.

Existing launch/watch mutex objects are opened rather than creating a new
task, monitor or service. Holding the launch object suppresses new launches
through the existing launcher; the watch mutex is acquired on one pinned OS
thread after the held chain is signalled. The task definition is never edited.
Failure to confirm stopping is an unknown effect and does not invite a kill
fallback or retry. Release failures remain cleanup failures.

Three held process snapshots are not a full-lifetime collection proof. Before
Stop, a normal owner must supply the same task-generation live collection
resource, covering all root/child membership from before execution and preventing
escape. AllReaped is emitted only after that owner confirms complete collection.
The current lifetime issuer remains unavailable, so the normal adapter refuses
before Stop. Increasing snapshot counts cannot replace the missing owner.

After publication, a never-started or already-exited candidate can use finite
undo only when the same lifetime owner proves full-generation quiescence and
returns a real reacquired launch/watch hold. The task definition, current
candidate identity and collection are rechecked under that hold. No running
instance is invented, and zero task instances alone never permit restoration.
Unknown or foreign generations remain refused with reconciliation required.
Each newly acquired recovery hold has its own release-once result. An earlier
release or Close failure remains recorded, but cannot suppress Release of a new
issued hold. Partial acquisition retains its reference for Close without claiming
that the generation is ready for restoration.

A Stop attempt or recovery acquisition begins an explicit collection obligation.
Close of a process query handle cannot clear it: unconfirmed collection is
returned as a separate cleanup failure while the primary failure remains.
The result reports stop_attempted and unreaped separately from cleanup_failed;
query-handle release is not reaping.
Check-only close of a live observed process creates no such stop obligation.
Check-only qualification also rechecks cancellation after the final Task callback;
a cancelled observation never becomes a successful check or an apply permit.

After publication, the adapter waits finitely for the next instance of the
unchanged task. It compares the new process generation and same held artifact
object, reads qualified status samples, requires the started event and rejects
termination/service events. health_only establishes only proxy response
observation; it never establishes proxy ownership or a termination grant.

The task command is a fixed, bounded, hidden PowerShell/Task Scheduler COM
operation. No external task selector, credential, registration or configuration
change is accepted. The native process path requests no termination rights.
Partial handles and failed closes remain referenced with explicit cleanup
failure; no failed Close is retried. Mutable status and event observations alone
use read/write/delete sharing so normal append and atomic replacement are not
blocked by the reader. Two bounded reads of the same held file, physical
generation/size/last-write checks and a complete event terminator are required.
A changing or partial snapshot is unknown. The executable/artifact pin sharing
contract is unchanged.

The current source is not installed or runtime accepted. The actual formal
artifact, original-build/current-purpose and task-lifetime issuers are absent, so the
normal update remains unavailable before opening the installed target.
Native stop, full-chain collection, launch-hold behavior, rollback and actual
mapped-image observation still require independent review and owned Windows
acceptance before normal enablement. A process image path plus an observed
same-file generation is not a general mapped-image identity proof against an
uncooperative same-user namespace writer. The existing held-file lifetime and
same-parent rules remain necessary.

Codex and Claude Code representative OpenCodex CLI acceptance additionally
requires normal qualification of the actual nested Bun. HTTP health is a
separate observation.

## Bounded readiness after publication

Observe keeps one 150-second deadline across Task startup, chain acquisition,
status samples and event snapshots. Only explicitly identified readiness states
wait: no new instance yet; a validated queued/starting instance with no established
PID/action yet; a verified launcher prefix awaiting its sole child; the unchanged
predecessor status before the first new sample; or an incomplete/racing mutable
observation snapshot. These states do not authorize Stop, publication or collection.
A deadline or cancellation still fails and reaches the existing finite recovery.

The read-only observation Task decoder preserves the real queued fields and
reuses the fixed Task definition/Actions/principal verification. Stop and check
continue using the unchanged strict running-instance decoder and fixed script.
After a GUID or engine PID is observed it cannot change; the validated process
prefix also keeps its PID, parent, creation time and image across retries. An
established running instance cannot revert to queued. Foreign/invalid images,
owners, births, instance IDs, definitions, unrelated status PIDs and unknown errors
fail immediately. The engine PID remains observed data, not an independent proof
that Task Scheduler has exposed the executable action process.

Partial queried chains remain referenced for cleanup. A retry closes each old
query handle once and retains its identity facts for the next observation; a
failed Close is never retried or treated as a readiness condition. Collection
obligations and the original lifetime owner remain unchanged throughout.

Only status.json and events.jsonl permit read/write/delete sharing. Their bounded
same-buffer snapshot still rejects links, reparse points, invalid physical paths,
oversized data and held-object identity changes. A stable old object whose public
name was atomically replaced is retried as a mutable observation race. A same-object
append/overwrite race or incomplete event line also waits; raw data is not accepted
until a complete stable snapshot is obtained. Any cleanup failure stays terminal.
The executable/artifact/current-purpose pin contract is unchanged. Native Task
startup and the normal artifact/origin/lifetime issuers remain unaccepted.


Event snapshot readiness does not pause health observation after the initial
six samples. Every subsequent retry checks a current same-generation status;
health, PID, time, write-failure and health_only predicates remain required.
After events are ready, Observe rechecks the same Task instance, process,
candidate and a newly read current status before returning success. The fixed
six-sample evidence keeps its first samples and advances its final sample to a
newer valid observation, preserving the original 50-second span and 150-second
overall bound. A known unhealthy, stale, foreign-PID or write-failed current
status fails immediately, even when the event snapshot later becomes complete.
