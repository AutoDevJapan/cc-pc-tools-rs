# 自動取消後の再開

停滞監視が終了させた担当は、元の共有ToDo・仕様・成果・作業場所・会話・モデル・権限を引き継いで再開する。予約の照合で項目側の取消記録が消えても、ジョブ側の `recovery_cancel.key` と `committed_at` が残っていれば、本人の停止として保留しない。取消キーは起動キーとは別の識別子なので、両者の一致を要求しない。

スケジューラーの自動停止は `cancel_for_recovery` を使う。ジョブの通常の `cancel --recovery` も、終了処理の前にジョブのロック下で永続する取消意図を保存する。受付側が先に保存した同じ意図は置き換えない。

ジョブ側の意図は、空でないキーとRFC3339形式の日時が揃ったときだけ認める。壊れた日時を自動再開の証拠として扱わない。

共通判定は `cc-job-policy::cancellation` を使う。本人の `cancel_requested`、`stopped`、取消理由 `manual` / `person` は自動取消より優先する。自動取消の証拠がない取消、途中までしか保存されていない取消記録、別ジョブの予約は再開の根拠にしない。旧予約の根拠は、同じジョブに対応する停滞監視の `recovery_cancel`、またはスケジューラーの既知の `pending_cancel` に限る。

本人の質問、未完了のToDo依存、明示された起動期限、モデルの利用枠待ちは保持する。明示された起動期限は、停滞監視が既に予約を作っていた場合も送信・起動の前に確認する。本人の質問や停止を解除するために、この判定を使わない。

自動取消で再開するとき、新しい明示設定がなければ最新の元担当のモデル・強度・権限を使う。元会話は、同じ作業場所で他の担当が使用していない場合だけ再開する。未コミットの成果を削除・リセット・別の枝へ切り替えて起動しない。

回帰検査は共通判定、スケジューラーの照合と準備、停滞監視の予約と送信を確認する。実開始の確認には実ツール実行とプロセスの作成時刻の照合を使い、受付だけを救済完了として扱わない。
