# Codexジョブの起動と順番待ち

起動・再開・要約の各試行で、最新の保存済みオーナー指示を読み直して実入力へ追加する。登録時の古い指示、元の入力、read-only指定は書き換えない。欠落・空白・不正UTF-8の指示では起動を失敗として記録する。保存元・対象3所有者・既存Prd・配備の確認条件は[自律開発の規則](../docs/owner-autonomy.md)に記載する。

PCの再起動で途切れた担当は、ログオン時と毎分の既存のDiscord受付から自動で再開します。受付は `recover-reboot --apply` をスケジューラーの消失確認より先に実行します。再開後も同じジョブIDを使い、名前・作業フォルダー・権限・モデル・MCP設定・親子関係・共有ToDoを保持します。セッションIDがあれば `exec resume`、なければ保存済みの `prompt.md` を使います。

対象は現在のWindows起動時刻より前に作成され、最後の活動も起動前で、元の監督とCodexがともに終了した担当です。実行中・順番待ちの消失と、今回の起動後に `lost` と記録された監督の消失（502を含む）を扱います。取り消し・通常の失敗・終了イベント・完了や保留のToDo・後続の担当は除きます。クライアント案件の作業フォルダーは既存の判定ツールで除きます。

共有キュー・状態・監督のロックと `reboot_recovered_boot` の印で二重起動を防ぎます。起動に失敗しても同じ担当の再開予定を保持し、次の毎分確認で再試行します。全対象の起動が済んだら、件数と名前をDiscordの「後片付けの記録」へ通知なしで1件にまとめます。記録に失敗した場合は、担当を起動し直さず記録だけ再試行します。確認済みの起動は `reboot-recovery.json` に残し、その後の毎分確認で過去の全履歴を読み直しません。

復旧中にToDoが完了したり後続の担当ができたりした場合、まだ起動していない再開予定を解除します。履歴の一部を読めない場合も、確認できた担当の復旧は進め、その履歴だけ次回に確認します。作業範囲の確認に失敗した場合や時間を使い切った場合は終了コード75を返し、受付はその回のToDoの再割り当てを止めて、次の毎分確認に引き継ぎます。受付からの呼び出しは15秒、復旧の起動処理は準備を含めて12秒、作業範囲の確認は1件2秒を上限にします。

```powershell
codex_jobs.exe recover-reboot          # 対象の確認のみ
codex_jobs.exe recover-reboot --apply  # 現在の起動で中断した担当を再開
```

通常の自動起動はSol/max/Fast、レビューは作者と違うモデル（通常Opus/max）を選びます。利用ペースだけを理由にClaudeへ置き換えません。正規の混雑エラーでは、同じGPTモデルの異なる適格な既存OAuth枠で最大3回追加再試行し、その後に仕事と健全性からSonnet/Opusのmaxを選びます。Haikuの明示指定と単一ファイルの制約、読み取り権限、停止・依存関係を保持します。未知モデルは別のモデルへ変更しません。

保存された古いAIのHigh指定は、管理された起動・再開時に最新のMax方針へ合わせます。本人の個別指定を保持する場合は、モデルとeffortの値だけでなく、正規に取得した本人の指示を引き継いで`--model-origin owner_request`・`--effort-origin owner_request`を渡します。AIの通常の選択には`policy`を渡します。単独CLIの明示effortは保持します。実行中の要求をこの設定変更だけで強制終了せず、次の起動・再開で適用します。起動要求・native turn_context・上流の実効値は別々に記録します。

同じoriginオプションは`todo.exe add ... --spec ... --model ... --effort ...`でも指定できます。
本人の個別指示を元仕様とともに確認してから付け、dispatchableな仕様と一緒に原子的に保存します。
モデルとeffortの出所はそれぞれ独立であり、値をコピーした別の過去記録のownerフラグを流用しません。

Codex と Claude はそれぞれ家族単位で実行枠を数えます。Codex の週の利用ペースは Codex の上限だけに適用します。Claude の上限は自身の利用枠と429、共通の CPU・メモリ・プロキシの測定から調整します。両方を足した実行数にも、大きい方の上限を共通の上限として適用し、CPU85%・空きメモリ16GiB・応答不良で増枠しません。異なる会社の子が同じ家族にいる場合は両社の枠に数えます。測定が古い・壊れた場合は最小の上限へ戻り、Claudeへの自動切替を止めます。固定の上限は両社合計に適用し、自動切替を止めます。状態のJSONには各社の実行枠と上限を表示します。

共有キューのロック外で、実行中ジョブの一時停止と引き継ぎの準備を行います。ジョブごとの譲りのロックで重複を防ぎ、確定直前に共有キューをロックして子・取消し・最新状態を再確認します。要約に必要な MCP サーバー名の取得も共有ロック外で行います。`.queue.lock.owner` は保持者のPID・操作・取得時刻だけを記録し、60秒の待機期限を超えたエラーにも載せます。強制終了では古い記録が残る場合があるため、「最後に記録した保持者」として扱います。

起動時のロック競合は、Windowsへ待機要求を登録して期限まで待ちます。共有キューは60秒、ジョブごとの状態・再開・起動キーのロックは10秒が上限です。対象は各ロックファイルの先頭1バイト（範囲 `[0, 1)`）です。期限を過ぎると終了コード75と対象パス・操作を標準エラーへ返します。引数の誤りは2、その他の失敗は1です。読むだけの処理は状態ロックを取得せず、完全なJSONの置換を使います。設定・JSON・依頼文の読取りとJSONの置換には、短い期限で共有違反の再試行を行います。

新規登録の重複確認は共有索引にある実行中・待機中の記録を使います。終了済みの履歴を毎回全件読む処理を省き、プロセス起動前に共有キューのロックを解放します。登録したジョブの状態ロックは起動結果の保存まで保持します。`cargo test -p cc-jobs` には、3,132件の終了済み履歴と共通のキュー状態ファイルを使い、30個の実コマンドを並行起動する試験を含みます。

順番待ちの見張りは3秒ごとに、共有キューのロックを取らずに索引上の実行中・待機中の記録から判定を見積もります。起動できる可能性があるとき、待機理由が変わったとき、45〜90秒（ばらつき付き）ごとの定期確認のときだけロックを取って正式に判定します。実行中の長い作業が枠を譲るかの確認も、譲る可能性があるときだけロックを取ります。ToDo一覧と依頼文の「繰り返し」判定は、ファイルの大きさと更新時刻が変わるまで再読込しません。

共有Cargoの容量上限は、保存先の「空き容量＋共有target容量」の25%（最大512GiB、空き100GiBを保持）です。`CODEX_JOBS_CACHE_MAX_GIB` で上書きできます。80%に近づくと、ゲートが新規生成を記録した成果物のうち、7日間ゲートで使われていないものだけを整理します。既存成果物やハードリンクは保持します。使用日時はすべてのゲート利用で更新するため、継続利用中の成果物は整理しません。調査結果と制限は [容量管理の説明](../docs/cargo-cache-1983.md) を参照してください。

くり返し実行する親の担当は、直接依頼・PR担当・その他より低い第4順位で動きます。対象は `queue-config.json` の `lowest_priority_todo_ids` に書いたToDo番号だけで、初期値は `[18, 23]` です。題名や依頼文の文言では判定しません（共通の指示に「繰り返す」が入り、全ジョブが最下位になって順位が崩れたため）。実行中の対象の親は、上位の担当が待っていれば2時間を待たずに次の安全な区切りで枠を譲ります。別の順位の担当が1件でも待っていれば、空き枠があっても対象の親は起動しません。429後の待ち時間中や、子の枠が埋まっている待機者も数えます。取り消された担当と、監督が終了した担当は数えません。最下位同士では待機開始順に動きます。

設定は起動判定ごとに読み直します。番号を追加・削除するには `lowest_priority_todo_ids` を編集します。一時的に通常の順位へ戻す場合は `normal_priority_todo_ids` に番号を追加してください。こちらが番号指定より優先します。実行中のジョブから別のToDoの作業を登録した場合は子として扱わず、通常の順番待ちに入れます。実行中の親は従来の完了境界で枠を譲ります。親を終わらせるための子は、親の実行枠を使う従来の起動条件を保ちます。

Rust製の `codex_jobs.exe` が、複数の呼び出し元から届くジョブを共通の順番待ちに入れます。同時に動く親は初期設定で6件です。実行中の親から起動した子は親の枠を使い、各親につき同時2件まで起動します。起動できる子を親より優先し、その中でオーナーの直接依頼（`req-`）、PRを仕上げる担当（`shep-`）、その他の順に起動します。同じ順位では待機開始が古いものを先にします。子の枠が埋まった親があっても、別の親の子は起動できます。

同じ順位以上の親が順番待ちしている場合、連続2時間以上動いた親はコマンドやツールの `item.completed` の後、次の `item.started` の前にCodexを停止し、同じ順位の最後へ戻ります。ジョブID・ToDo・作業フォルダ・セッションと元の依頼文を保ち、次の起動には `exec resume` を使います。待機者がいない場合、子・孫が実行中または順番待ちの場合は譲りません。失敗・取り消し・セッション未記録・完了や判断待ちの作業は再開しません。

ツール完了後も長いコマンドが裏で動くことがあるため、実際のプロセスも確認します。CargoやCiv6の処理、その枠を持つ処理、別のCodexが残っている間は終了を待ちます。Codex内のサブエージェントも追跡し、終了・閉鎖の返答か、子自身の新しいターンの完了記録を確認するまで譲りません。追加の指示を送った子に古い完了記録を再利用しません。親がまだ受け取っていない子の結果は、子のID・結果・全文の場所を再開用の指示へ渡し、委任や送信を重複させません。起動時からあるMCPサーバーは停止と再開の対象にできますが、その後に起動した実処理は待ちます。PIDと作成時刻で本人・親子を照合します。進行を一時停止してイベントの保存を待ち、次の項目が始まっていないことを再確認してから停止します。停止時には共有資源を持つ処理が終わり、枠が返っている必要があります。

更新前から動く親も、更新済みの待機プロセスがこの境界で停止し、新版の監督へ引き継ぎます。新版の監督はツール完了時と、終了が遅れた背景の処理を待つ間に自分で確認します。配備時はexeを差し替えて `reload-queue` を実行します。Civ6の実機試験やCargoの途中で実行中の親を一斉に止める操作は不要です。

停止前に `yield-transition.json` へ同じセッションの再開記録を保存し、停止・保存・監督の起動に失敗した場合は同じジョブで再試行します。未確定の引き継ぎを失敗として通知せず、まだ生きる子孫があれば枠を保持します。一時停止した担当が終了した場合は `yield-paused.json` を使って進行を再開します。同じ秒の受付にも順序番号を使い、譲った親が待機者を追い越すことを防ぎます。旧型のターン終了予約はv0の互換処理だけに限ります。

親のIDは環境変数 `CC_JOB_ID` から取得して `parent_job_id` に保存します。別の起動元が明示するときは `run --parent-job-id <ID>` を使います。明示した親は同じキューで実行中である必要があります。環境変数の親が終了していれば警告を出し、独立した親として順番待ちに入れます。孫以降も最上位の親の枠に属し、直接の親ごとに子の上限を適用します。親が終了しても子が動いている間は親の枠を保持します。祖先の記録が読めなければ、そのIDで枠を保持し、他の親の起動判定を続けます。

設定は実行ファイルと同じフォルダの `queue-config.json` に置きます。配布先は `D:/CC/Tools/codex-jobs/` です。ファイルがなければ下記の値を使い、次の起動判定で変更を読み直します。0件の上限や不正な設定はエラーにします。

```json
{
  "max_running": 6,
  "max_children_per_parent": 2,
  "max_429_retries": 5,
  "retry_delay_seconds": 60,
  "max_retry_delay_seconds": 900
}
```

待機中は `status` の表示が「順番待ち」になります。JSONの `status` は既存の監視ツールが読む `queued` を維持します。待機中の監督プロセスはCodexを起動せず、3秒ごとに空きを確認します。待機中も `cancel <ジョブID>` で取り消せます。起動枠の確保と登録にはOSのファイルロックを使い、終了したプロセスのPIDが再利用されても別のプロセスを止めません。過去のジョブは共有索引で30秒ごとに照合し、各待機プロセスが毎回すべての履歴を読むことを避けます。

待機中も監督プロセスが60秒ごとに生存記録を更新し、既存の停滞監視が再開し直すことを防ぎます。実行ファイルを更新して待機中の監督プロセスへ反映するときは `codex_jobs.exe reload-queue` を使います。指定した既存担当だけを更新する場合は `reload-queue --job-id <id>` を使います。実行中のCodexは停止せず、順番・セッション・ToDoの担当を維持します。

監督の更新は実行枠を割り当てないため、履歴再構築の完了や30秒の履歴有効期間を要求しません。共有キューと担当の保存ロックで更新し、履歴再構築の保存時には同時に追跡した担当も合流します。派生する履歴一覧が未作成・不正なら、登録済み担当の番号を未完了の一覧へ保存し、実際の起動を全履歴の再構築まで拒否します。読み書きの失敗で追跡を保存できない場合は旧監督を止めず延期します。後継の監督は実際の起動前に履歴・実行枠・所有範囲・有限レビューの受付を再検査します。更新できても実行開始には数えません。

`status` の先頭は「実行中の枠数／上限、子を含む実行件数、順番待ち件数、待つ理由ごとの件数、共有資源を待つジョブ」を1行で表示します。名前はJSON形式で引用し、空白・改行を含んでも1つのセルとして表示します。`status --summary` はこの1行だけを返します。`status --json` は従来どおりジョブの配列を返し、各待機ジョブの `queue_wait_reason` に理由とコードを追加します。`status --json --summary` は `summary` と `jobs` を持つオブジェクトを返します。

待つ理由は起動判定と同じ処理から取得します。実行枠、子の上限、子の先行、最低順位、429後の時刻待ち、見張り不在、直近の起動判定エラーを区別します。読めない状態ファイルや起動登録中の枠も計上します。Civ6は既存の待機記録、cargoは本人のPIDと作成時刻が一致する待機記録を使い、ビルド枠待ちと共有キャッシュ枠待ちを表示します。旧cargoゲートはこの記録を出さないため、ゲートも差し替え、次に起動するコマンドから表示を有効にしてください。

exeを差し替えても、既に起動している見張りは旧版の処理を続けます。差し替え後は `reload-queue` で待機中の見張りへ反映します。停止対象は作成時刻を照合した本人だけです。本人から起動された別ジョブへWindowsの親PIDをたどって停止しません。終了済みの見張りを確認するには `cleanup-supervisors`、停止するには `cleanup-supervisors --apply` を使います。実作業の子が生きているものと、引き継ぎ処理中のものは除き、終了日時と結果を保持します。

429で失敗したときは同じジョブの同じセッションを使い、60・120・240・480・900秒後に再試行します。待つ間は起動枠を空けます。再試行は最大5回です。セッションが記録されていないときは新しいセッションを勝手に作らず、失敗を記録します。待機中は終了通知を送りません。子プロセスが生き残っている場合は枠を消費したままにします。

終了済みの429ジョブを復旧するには、最初に対象を確認します。

```powershell
codex_jobs.exe recover-429 --since 2026-10-06T17:00:00+09:00
codex_jobs.exe recover-429 --since 2026-10-06T17:00:00+09:00 --apply
```

`--apply` を付けた場合だけ復旧します。`events.jsonl` の最終イベントを確認し、ToDo・同じセッション・後続の担当と照合します。完了済みや判断待ち、後続の担当があるものは除きます。同じジョブIDを使うため、ToDoとの関連を維持します。新規受付も同じToDoやセッションの二重起動を拒否します。ToDoファイルを変更する場合は `--todo-file <path>` を指定します。

一度このコマンドで復旧したジョブを停滞監視が取り消していた場合も、同じ検査をして再開できます。オーナーが直接取り消したジョブは再開しません。

親IDの記録がない古い子は、実行中の親の `events.jsonl` にある成功した起動コマンドと、その出力のジョブIDから関連付けます。同じIDを複数の親が起動した記録は採用しません。指定時刻以降に取り消され、一度も開始していない子は同じIDで再起動できます。後続の担当があるものや、親が終了したものは除きます。これは指定時刻以降の子の復旧を明示的に依頼されたときに使う管理コマンドです。取り消し理由を自動判別する機能ではありません。待機中の古い子を関連付ける際は、その監督プロセスも新版へ起動し直します。

配備は実行ファイルの差し替え、`reload-queue`、対象の確認と復旧の順で行います。`max_running` は運用中の設定を保持します。実行中の処理を途中で止めず、ツールが完了した境界で新版の監督へ引き継ぎます。旧版も読める設定項目を維持します。`max_children_per_parent` は旧版が不正なキーとして拒否するため、それらが終了するまでは本番設定に追加せず、新版の初期値2を使います。

```powershell
codex_jobs.exe recover-children --since 2026-10-06T21:00:00+09:00
codex_jobs.exe recover-children --since 2026-10-06T21:00:00+09:00 --apply
codex_jobs.exe reload-queue
```

検証: `cargo test --manifest-path cc-jobs/Cargo.toml`。既存の互換性検査に加え、6件の親が枠を埋めても子を起動して完了できること、兄弟12件の同時判定で2件までに収まること、孫と親終了後の枠保持、親IDの取得、旧記録の復旧と再実行を確認します。外部のCodexや通知APIは偽物に置き換えて検査します。

## 文脈とモデルの利用枠（2026-10-07）

`queue-config.json` の `context_limit_percent` は初期値50、範囲1～100です。文脈の使用率がこの値を超えたら、従来のコマンド・ツール完了境界で、背景処理・子担当・Cargo・Civ6が終了したことを確かめて止めます。待機者や2時間の経過がなくても対象になります。子担当自身も、その子孫が終われば対象です。実行中に設定を読み直します。

再開したセッションの記録は開始日が古くても読み、長いコマンドの完了時には使用率を取得し直してから判定します。ブラウザ操作で後から起動するCodexのapp-serverとCUAのNodeは、配布された実行ファイルの場所と起動内容を照合し、引き継ぎの停止・再開対象に含めます。別担当のCodexや通常のNodeコマンド、ブラウザ用プロセスから起動した背景の作業は終了を待ちます。プロセス一覧を取得した直後に終了したものは、終了を確認してから除外します。

停止後は旧セッションに引き継ぎだけを書かせ、目的・終わったこと・残り・次の一手・関係ファイルとPR・最新の指示と注意点を24KB以内で保存します。内容と保存の確認後、同じジョブID・共有ToDo・作業フォルダ・権限を保ち、resumeを使わず新しいセッションを起動します。引き継ぎ中は読み取り専用です。保存できない場合は旧セッションIDを保持し、失敗を記録します。引き継ぎを終えただけでは作業完了を通知しません。取り消し・終了・判断待ちの作業は再開しません。

`run` の `--model` と `--effort` は省略できます。レビュー・確認・調べもの・後片付けは `gpt-6-luna/high`、実装は `gpt-6.1-sol/high` を使います。個別の指定が優先され、`max` は明示された場合だけ使います。[起動箇所と名前の対応表](../docs/job-launch-models.md)を参照してください。

```json
{"context_limit_percent": 50}
```

差し替えは新版を配置して `reload-queue` を実行します。旧監督が読む設定は未知のキーを拒否するため、旧版が退出するまで本番設定へ新しいキーを追加せず初期値50を使います。既存の稼働中ジョブは新版の待機監督が同じ完了境界で引き継ぎます。

測定用のRust例 `usage_comparison` は、差し替え時刻を挟む等しい長さの区間を `ocx observe usage --since/--until --surface codex` で読み、1時間あたりの要求とトークンを記録します。APIキーやモデルの呼び出しはありません。例はビルド後に直接起動し、待機中にCargoの枠を保持しません。
