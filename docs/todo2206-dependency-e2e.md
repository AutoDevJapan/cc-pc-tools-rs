# 子ジョブ開始の統合検査を隔離する（ToDo2206追加分）

親2162の統合6930472で、依存ジョブのE2e検査だけが26.257秒で失敗した。全1681件のうち1680件は成功、既存除外3件。元のログは共通の20秒待機地点だけを示し、親fixture開始・子成功・親取消し後の別root成功を区別できない。PR78の履歴走査受付修復とは別の事象として扱う。

## 実測できた問題

旧fixtureはCODEX_HOMEを一時領域へ変更するが、USERPROFILE/HOMEは呼び出し元を継承する。Context::installedはこの2つから別にhomeを決め、agentの起動前にプラグインの設定を読む。したがって、キューのfake処理が呼び出し元の設定へ依存し、設定の更新や不正内容がfixtureの起動を失敗させる。

合成caller-homeに、JSONとしては正しくenv_varsの型だけが不正な設定を用意し、同じ依存契約を実行した。親はfailed、error_kindはplugin_metadata、agent PIDは0、sleep markerなし、索引は完成した状態でparent_fixture_startが20.052秒を超えた。検査全体は20.944秒で失敗した。USERPROFILE/HOMEもfixture専用に変更すると同じ検査と通常検査が成功し、caller設定は不変だった。

この制御した失敗は、起動前の環境漏れを再現する証拠である。元26.257秒の失敗の段階が同じだったとは断定しない。診断のみのmain検査1643件（505.917秒）と、6930472の自分の隔離コピーでcc-askと対象E2eを混在させた615件（248.823秒）の成功も、元失敗の原因確定には代用しない。

## 契約の確認方法

- 各待機の20秒、実行枠1、既存のprocess-boundary直列グループを維持する。
- 親と別rootを独立した自己生成Git作業先へ置く。上位のユーザーGit設定により同じ所有者と見なされる環境でも、別rootがwork_ownerではなくrunning_limitで待つことを確認する。
- 子は親の実行枠を共有して開始・成功する。親はrunning、別rootはqueuedを維持する。
- 依存検査だけに使う親fixtureは、40秒の自然終了に依存しない。実検査担当のOSハンドルと作成時刻を照合し、明示解放・取消し・担当プロセスの実終了まで保持する。受領記録のdone値では終了させない。
- 親を取り消した後は、保持したハンドルで実プロセス終了を確認し、別rootの成功を確認する。

## 診断と後始末

失敗前に、待機段階と経過時間、匿名role、状態、待ち理由のcode、索引のrole集合、登録owner hintの有無、記録と現在のPID作成時刻、保持ハンドルの実生存を採取する。ジョブの実ID、cwd、プロンプト、自由文のエラーや認証情報は出さない。設定の不正は固定のplugin_metadataラベルで示す。

対象fixtureのプロセスだけを作成時刻に結び付けて保持し、終了を待ってからハンドルを閉じる。PID markerは、fixture自身が先に保存したPID・作成時刻と、自分のfixture実行ファイルとの一致を確認する。現在のPIDから作成時刻を推定して古いmarkerへ結び付けない。誤った保存時刻のmarkerを拒否し、正しい保存時刻でだけ保持できることを実プロセスで確認する。診断に一度、slash表記の不一致で終了済みmarkerの保持を確認できない失敗があり、表記を統一して修正した。この診断の失敗を本番キューの不具合とは数えない。

本番の索引・受付・admit・実行枠制御に、この追加分で挙動変更は加えない。元PR78の完了結果や、親2162の監査・配送の完了とは混ぜない。

最新main統合後の全件検査では、30件受付の後始末も1件失敗した。受付は30件全成功（13.282秒）であり、停止を要求した1つの監督のWaitForSingleObjectが5000ms後に258を返した。これは受付待ちの再発ではない。後始末は全所有ハンドルへ停止要求を出し終えてから、各ハンドルの終了を確認する二段階へ変更する。途中の1件が遅くても、残る監督を動かし続けない。各確認の5000ms上限も変更しない。

## 2026-10-24の起動後停止を調べる（ToDo3258）

PR420の正式CIでは、親と子の終了後に別rootのagentが起動したものの、
待機が20.601秒で期限を超えた。保持ハンドルと作成時刻は一致していた。
同じソースの単独実行と関連2件の5回ずつの反復は成功したが、過去の記録には
cmd.exeからfixture.exeへ到達したかを示す情報がなく、停止原因は特定できない。
別モデルの限定診断3551も、受付遅延・標準入力のEOF待ちを原因とは認めず、
失敗時の観測を追加するよう指摘した。OSやDefenderを原因と断定しない。

待機条件が期限を超えた後だけ、同じfixtureのプロセスを作成時刻付きハンドルで保持し、
1秒間隔でCPU時間・スレッド数・生存・子プロセスを記録する。対象は最大64プロセス。
既存の20秒条件、通常の成功時の採取、取消と後始末の動作は変えない。
この1秒は、既に決まった失敗の診断時間であり、成功を待つ期限の延長ではない。

記録する実行物名は既知のfixture・cmd・bun・conhost・WerFaultの固定ラベルだけとし、
その他の名前やコマンドラインは出さない。stdin先頭とcall.jsonのcwdも、
stdinは親・子・別root・不明、cwdは親・別root・不明の役割に変換する。
読取失敗は不明と区別し、OSエラー番号を記録する。PID markerとeventsの長さ、stderr/supervisorの
末尾最大1KiBに含まれる固定のエラー分類を記録し、プロンプト・ログの自由文は出さない。
採取エラーと上限到達も記録する。子はハンドルを保持した後の新しい一覧で、確認済みの親へ
PPIDがつながることを照合する。確認一覧が失敗した場合は新しい子を採らない。
回帰テストでは秘密文字列・実job ID・パスの非表示、末尾1KiBの上限、実子2件のPPID・固定名・
生存と2回のCPU採取、誤った作成時刻と古いPPID候補の拒否を確認する。
64プロセス・8192行・16jobの境界はコード上の制限であり、上限件数の実測テストとは区別する。

stdin.binはfixtureが標準入力をEOFまで読んだ後に保存するため、stdin_roleが別rootなら
EOF後の記録まで到達したことが分かる。call.jsonのcwdが不明な場合は、未到達だけでなく
先頭8192バイトでJSONが切れた可能性もある。読取状態とcall_parse_okを合わせて判断する。

これは再発時の原因調査を可能にする変更であり、過去の起動後停止の原因確定や
OS側の修復を実施済みとするものではない。成功済みの製品テストは再委譲せず、
この追加差分のレビューと最新ソースの必要CIを別に確認する。
