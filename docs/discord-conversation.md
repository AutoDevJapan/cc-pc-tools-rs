# 新しい質問・回答のCLI

新しい質問は `unattended-runner.exe conversation` から送る。
旧台帳と原保護名簿の復元は別に追い、新しい運用の開始条件にはしない。
旧記録を書き換えたり、空の原本を作ったり、過去の質問を再送したりしない。

```text
unattended-runner.exe conversation [--config <path>] ask --request-id <id> --todo-id <元ToDo番号> --origin-thread <元スレッドID> --body-file <本文ファイル> --decision-file <判断範囲JSON> [--title <題名>] [--wait]
unattended-runner.exe conversation [--config <path>] log --request-id <id> --title <題名> --body-file <本文ファイル> [--thread <進捗スレッドID>] [--notify] [--attach <画像> ...]
unattended-runner.exe conversation [--config <path>] replies --request-id <id>
unattended-runner.exe conversation [--config <path>] status
```

設定ファイルを省略した場合は
`D:/CC/Tools/discord-ask/unattended/config.json` を使う。
`--config` はコマンド名より前に置く。
同じフラグの重複、未知のフラグ、余分な引数は拒否する。
`--attach` は異なる添付ごとに繰り返せる。
`--wait` と `--notify` は省略時は無効で、明示的に無効にするなら `=false` を付ける。

1. 本文をUTF-8のファイルに用意する。判断範囲JSONは元ToDo番号、対象資源、
   判断の種類、許可の範囲を固定し、既存の判断範囲の形式に合わせる。
   秘密値や保護対象の情報を本文・題名・引数へ入れない。
2. `ask` は元ToDoと元スレッドを指定する。質問は独立した投稿へ送り、進捗は
   メンションのない別投稿へ記録する。`--wait` は元ToDoの質問待ちへの接続を
   指定する任意フラグで、CLIが本人の返信を待ち続ける指定ではない。
3. 失敗・時間切れの再試行では、同じ `--request-id` と同じ入力を使う。
   投稿済みか未確認でも、新しいIDに変えて送り直さない。
4. 通常の進捗は `log` で送る。既存の進捗へ追記するときは `--thread` を使う。
   通知は省略時には付かない。送信側が対応する添付は現在は画像だけ。
   原保護名簿と送信側の保護確認は引き続き必要で、名簿の欠落を画像の許可へ
   読み替えない。既存の個別の画像証跡に対する例外も拡張しない。
   動画・音声の送信はこの接続では実装していない。
5. `replies` は指定した質問への本人回答を正規の送信記録と照合する。
   標準出力は本文を含まない確認結果で、回答の参照だけでは作業への反映完了にしない。
   `status` は新しい質問の件数と段階を確認する。

CLIは設定の開始時刻・用途・絶対パス、投稿先のID、独立した受付状態の範囲を
検査する。処理中は既存の `runner.lock` を保持し、定期処理との同時更新を防ぐ。
既存状態が壊れていたり範囲が違ったりする場合は拒否し、初期化し直さない。
独立状態がまだ存在しない場合だけ、正しい初期状態をメモリ上に用意する。

1回の処理期限は60秒。子コマンドは既存の非表示実行と20秒の期限を使う。
成功時は親処理が返した確認結果だけをJSONで出力する。
引数や処理の失敗は本文・秘密値・生のエラーを出さず終了コード1、
同時実行でロックを取れない場合は `busy` と終了コード2を返す。

## 通常のCLIからの切り替え

通常の `discord_ask.exe ask/log/post` は、ツールの保存先にある
`conversation-mode.json` が次の厳密な2項目で有効化されている場合だけ新しいGo実装へ渡す。
`CC_ASK_HOME` があれば、その保存先を使う。

```json
{"domain":"discord-conversation-mode-v1","enabled":true}
```

ファイルがない場合と正しい形式の `enabled:false` は従来の処理を使う。
不正なJSON、項目の不足・追加・重複、異なる用途は失敗として扱う。
この接続は設定を作成・有効化せず、旧台帳の復元や受付範囲の拡大も行わない。

通常の `log --topic` は新しい報告の題名へ渡し、同じ題名の別本文はGo側で同じ
進捗スレッドへまとめる。`--body-file` は `--text` より優先する。
`post --thread` は指定されたスレッドへ渡し、送信側は新しい送信記録で確認できた
スレッドだけを許可する。添付のコピーを保存したことは、画像の保護確認の代わりにならない。

通常の `ask` も既存の質問制限と `--owner-only` の理由を確認する。
`--dry-run` は従来の表示処理のまま、新しい送信は行わない。
実際の新しい質問には `--decision-file` が必須で、そのJSONの `todo_id` を使う。
元スレッドは `--thread`、JSONの `origin_thread_id`、または `scope.origin_thread_id`
で指定し、複数ある指定は一致させる。通常の質問にはGo側へ `--wait` を渡す。
既存の別の待機状態を質問待ちへ勝手に変更しない。
質問そのものへの添付は新しい `ask` の契約に含まれないため明示的に拒否する。

本文・判断範囲・対応する画像はツールの私的な保存先へ固定して保存する。
送信IDは本文・題名・通知指定・画像の内容などから決まり、同じ入力の再試行では
同じIDと保存済み入力を使う。子処理は既存の非表示・有限時間・出力制限付き実行を使う。
Go側の失敗時は旧APIへ切り替えず、同じ入力での再試行を案内する。
標準出力にはGoが返した送信記録の確認結果だけを残し、本文と私的なファイルの場所は出さない。
`replies/close/tick` など旧台帳を扱うコマンドは、この切り替えの対象に含めない。

## 新しい会話のアーカイブ

新しい会話はGoの閉鎖処理で確認し、旧送信側の `recovery-close` は呼ばない。
複数の本人返信と編集後の返信も、それぞれの最新版が実作業へ反映された場合に閉じられる。
受領、担当への配送、元ToDoの完了、古いコミット番号だけでは反映済みとしない。

各返信の反映記録は、担当へ渡された次の2項目を必須とする。

- `reply_sha256`: 本人、質問、判断範囲、本文を含む現在の返信の正規化SHA。
- `source_receipt_sha256`: 私的な保存先の `conversations/<質問ID>/replies/<返信ID>.json`
  を生のバイト列で計算したSHA。編集日時など本文以外の版の違いも区別する。

既存の取得元、元ToDo、質問と返信、本人ID、担当の所有、40桁のコミット番号、
反映日時、反映内容、実行・元記録の保持・本人確認の検証結果も照合する。
反映日時はその版の取得時刻以降、現在時刻以前である必要がある。
2項目がない古い記録や、現在の返信・保存元とSHAが違う記録は未反映として扱う。
本文が同じ編集でも保存元のSHAが変わるため、古い反映記録を流用しない。

確認できた返信は個別に反映済みとして保存する。他の返信が未反映なら質問は閉じない。
取得直後や、保存元・反映記録がまだない場合も待機を続ける。
全返信の確認後も、PATCHの前後で本人返信・判断範囲・反映記録を読み返す。
Botが所有する設定先のスレッドであることを検査し、変更するのは `archived:true` だけ。

閉鎖の記録は `conversations/<質問ID>/close-state.json` に保存する。
用途は `discord-conversation-close-v1` で、本文を含めず、対象とSHA、段階、確認履歴を保持する。
`patch_pending` は送信前に保存した閉鎖要求、`verified` はGETによるアーカイブ状態と
現在の返信・反映記録の一致を確認した状態を示す。APIの成功応答だけでは完了しない。
応答を失った場合は同じ記録からGETで確認し、返信が増えたり編集されたりした場合は
未完了として次の通常処理へ引き継ぐ。過去の保存記録は残す。

確認済みの質問を人が開き直した場合は `reopened` を記録し、自動で閉じ直さない。
すでにアーカイブされている質問も現在の全返信を確認する。新しい反映が不足していれば
以前の閉鎖記録を完了の根拠に使わない。旧台帳と旧閉鎖記録は変更しない。
