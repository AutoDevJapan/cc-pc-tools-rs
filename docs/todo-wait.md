# ほかのToDoの完了を待つ

## 取り消した担当の作業を明示的に再開する

`todo.exe start <番号>` で再開したときは、スケジューラーが既に取消結果を
照合した旧担当を履歴へ残し、その取消結果を再び適用しない。
旧担当の識別子と結果は保持し、次の担当は通常の受付で割り当てる。
進行中の担当、保存された指示・作業場所、再確認の期限、未完の依存は維持する。
この処理自体が停止項目を自動再開することはない。

## 技術的な停止の次の確認時刻を待つ

同じ実行環境で操作できないことを実確認し、短時間の再投入だけでは改善しない場合は、
元の項目へ `todo.exe wait-retry 1139 --after 3600 --reason "画面操作の接続用パイプが見つからない"` を登録する。
これは次の確認までの待機であり、接続の回復や画面検証の成功を示さない。
Plusの復旧待ちとは別の条件で、オーナーへの質問や新しい引き継ぎToDoを作らない。

理由と期限は元の項目に保存し、既存の仕様・メモ・担当履歴・作業場所・実測の進み具合を保持する。
同じ待機の再登録で期限を後ろへ動かさない。別の再開条件を上書きしない。
期限は60〜86400秒、指定を省略した場合は1時間。
待機中の新しいジョブ登録と、登録済みジョブの実行枠取得は抑止する。実行中の担当は終了まで継続する。

既存の1分ごとのToDo見張りが、実際の時刻が期限へ達した場合に元の項目を1回だけ再開可能にする。
本人の停止・完了・未完のToDo依存は解除しない。通常の資源枠と担当の所有権を守る。
再開した担当は実際の操作機能を確認して元の受入を続ける。
回復していなければ同じ元項目で次の確認時刻を登録し、成功や完了にはしない。
繰り返す再開失敗は、PCの規則に従って1時間ごとの確認とする。

配備は `todo.exe`、`codex_jobs.exe`、`scheduler.exe`、`discord_ask.exe` を同じ検証版へ揃える。
この待機はブラウザやWindows画面操作の接続そのものを追加する機能ではない。

ChatGPT Plusの復旧確認だけを待つ場合は、元の項目へ
`todo.exe wait-ready 1974 --condition chatgpt-plus` を登録する。
これはオーナーの判断待ちではなく、状態はwaitになる。指示・担当履歴・作業場所・進み具合は保持する。
毎日09:15の確認が実際に成功した場合だけ、窓を出さずに
`todo.exe resume-ready 1974 --condition chatgpt-plus` を実行する。
登録後にオーナーのChromeで確認したlogged_inの記録が26時間以内なら、通常の起動枠で同じToDoを再開する。
Pro・旧プロフィール・模擬画面・古い記録・未来の時刻・読み取りエラーでは解除しない。
本人が止めたblock、done、ほかのToDoの未完了も解除しない。
復旧前は担当を繰り返し起動せず、復旧後の実送受信が成功するまでdoneにしない。
この待機の配備はtodo.exeを先に更新し、その後check-hidden.vbsを更新する。

`todo.exe wait 995 --on 2005` は、995の状態をwaitにして待ち先を保存する。
複数の待ち先は `--on 2005 --on 2006` のように指定する。再度waitを実行すると待ち先を置き換える。
存在しない番号、自分自身、循環する待機、完了済みの項目への待機設定は拒否する。
メモ・進み具合・担当履歴・指示ファイル・作業場所を保持する。実測値は `--progress` で記録できる。
オーナーの判断待ちや明示停止でblockにした項目は、waitを登録してもblockを保つ。

待ち先がすべてdoneになるまで、ToDoの見張り、スケジューラー、PR担当、ジョブの登録・実行枠取得が起動を抑止する。
すでに動いている担当は終了まで継続する。待機登録によって他の担当のプロセスを強制終了しない。
同じPRを複数のToDoで追跡する場合も、ジョブに全番号を `--related-todo-ids` で保存し、順番待ちの間に追加された待機を検査する。
待ち先が削除された場合も完了とは扱わない。
ToDoの一覧・Discordの作業一覧・ジョブの待ち理由は「ToDo 2005 待ち」と表示する。

doneの保存と同じToDoロック内で待機を解除し、過去の停滞・再試行の待ち時間を解除する。
保存後に窓を出さずに見張りを起動する。別の担当がdoneを書いた場合も次の定期実行（1分ごと）で解除する。
原保護一覧の復旧を待つ間の修復モードでは、既存の`repair-step`が確認済みの修復範囲だけを同じ共通処理で解除する。
初回起動前でworktreeがない項目は、元リポジトリの保護確認後に通常の準備へ戻す。
既存worktreeがある項目はその保護確認も必要。回答済みを含め質問の記録がある項目、本人停止、外部条件、未完依存、
復旧予約、稼働中の担当はこの修復経路で解除しない。全製品や旧記録の復旧を意味しない。
通常の資源枠・実行枠・ほかの担当の所有権を守って再開する。本人の判断待ち・明示停止は解除しない。
待機解除後に新しい担当が割り当てられたら、即時再開用の印を消す。

Discordの追加指示を継続受付するときも、元の担当と保存済み選択が持つToDoの対応を引き継ぐ。
対応はToDo番号の明示指定と、担当履歴・スケジューラーの担当欄で確認し、本文中の番号や作業フォルダから推測しない。
ToDo原本の欠落・読取失敗・無効な一覧は準備完了と扱わず、予約・取消し・新しい担当の起動を保留する。
未完の依存があれば、受付の予約・元担当の取消し・新担当の起動より前に、待ち先と返信原文を保存する。
受領投稿の印と未処理の返信カーソルを保ち、すべての依存先が完了した後に既存の定期処理で再開する。
起動CLIにも関連するToDo番号を渡し、受付後に待機が追加された場合はジョブの実行枠取得時に再確認する。
未開始のまま取り消された受付は再利用せず、すでに担当が実行した処理は再実行しない。
待機登録と取消しは、取消しCLI内でqueue・担当状態・共有ToDoの順にロックして直列化する。
取消しの順序が確定するのは、共有ToDoロック内で試行番号付きの意思を保存した時点とする。
待機登録が先なら元担当を保ち、取消しが先なら後継担当の起動を依存先の完了まで待つ。
共有ToDoとqueueのロックを解放してからプロセスの終了処理を行い、担当状態のロック解放後に通知する。
この契約を導入するときは、進行中の返信処理を静止してcodex_jobs.exe・discord_ask.exeの順で更新する。

配備対象はtodo.exe、codex_jobs.exe、scheduler.exe、shepherd.exeと、作業一覧を出すdiscord_ask.exe。
Skill shared-todoとPC共通・各AIのルールに同じwait手順を追記する。
実際の待機は995・134・880から2005へ設定する。

検査はCLIの保存・循環拒否・複数待ち、見張りとスケジューラーの抑止と即時解除、
ジョブの登録抑止と実行枠の取得、PRとの厳密な対応付け、一覧表示を含む。
