# 変更の影響範囲を検査する

2026-10-17の本人指示により、すべての作業でテストは変更の影響範囲を選ぶ。
保存やコミット、マージのたびのフルテストを義務にしない。
これは2026-10-08の「マージ前に全workspaceを必ず1回」の規則を更新する。
元投稿: https://discord.com/channels/1552944707464597524/1560534965228404786/1560922714573766750

## テストを選ぶ

- 変更した処理の回帰検査と、その公開API・共有データ・設定を利用する側を含める。
  ファイル数だけで範囲を決めない。結合検査や実機の受入条件も影響があれば維持する。
- 文書だけの変更では、内容・リンク・書式を確認する。アプリの全件テストやビルドを
  代わりの確認にしない。実行時に読み込む文書・テンプレートは利用側を検査する。
- 共有の依存関係・ビルド設定・テスト選択の仕組みを変えた場合や、障害の影響を
  限定できない場合など、全体を確かめる必要があるときだけフルテストを行う。
  実行前に理由と対象のソース版を記録する。顧客契約や必須の受入検査は維持する。
- 同じ最終ソースの有効なCI結果を再利用する。失敗したら原因を直して該当検査を
  再実行し、新しい変更で影響が広がった分だけ追加する。

Rustは変更クレートと逆依存の検査を選ぶ。例は
`cargo nextest run --locked -p cc-jobs`。必要なら対象の結合テストをさらに絞る。
doctestがあるライブラリは、同じ影響範囲の`cargo test --locked -p <名前> --doc`で
確認する。Goも変更パッケージと利用側を選ぶ。外部資源を使う検査の直列指定、
資源割当、共有ビルドゲート、別モデルレビュー、CIの成功確認は維持する。

## ビルドを重ねない

小さな修正ごとに独立した全体ビルドやreleaseビルドを追加しない。
関連テストの実行で必要なコンパイルを行い、同じ生成先とキャッシュを再利用する。
独立ビルドは、まとまった変更後の確認、テストでコンパイルされない対象の確認、
配布・既存実行版の更新、またはビルド自体の不具合の再現に必要な場合に行う。
配布には変更後のソースから生成した実行物を使い、古い実行物で動作確認しない。

「大幅な修正の後だけ」という行数の基準にはしない。小さな修正でも型やリンクの
確認や配布が必要な場合がある。一方、テストですでに確認できた内容を別の全体
ビルドで繰り返す必要はない。これは効率化の方針であり、短縮時間を実測した報告ではない。

一次資料: [Cargo test](https://doc.rust-lang.org/cargo/commands/cargo-test.html)、
[nextestの実行範囲](https://nexte.st/docs/running/)。

## このリポジトリのCI

Build speedの通常実行は、固定したbase/headの差分とCargo metadataから、
変更クレートと推移的な逆依存を選ぶ。dev依存とtarget別依存も含める。
PRはmerge-baseから、pushは直前のtipから比較し、変更を戻すpushも検査対象にする。
同じ対象でnextest・doctest・Clippyを行い、先行する重複の回帰検査は追加しない。

Cargoの共有設定・ロック・ツールチェーン・nextest設定、共有runner、選択器または
このworkflowの変更では全件を選び、理由をJSONに残す。比較元を取得できない場合も
空の対象にせず全件にする。metadataや差分取得が壊れている場合は失敗として止める。
通常の文書・無関係のGoツールだけならRustの検査は選ばない。
元の有限な配布用ビルド条件、runnerの保護、同一headの入場確認は維持する。

共通の保存指示`D:/CC/AGENTS.md`にも、この文書のCI節より前の方針を反映する。
Cargo用Skillの本文にある無条件全件の指示も更新する。過去の参照資料は原資料として
保持し、2026-10-17の方針が優先することをSkill本文に明記する。
新規・再開・文脈継続の担当には、既存の起動処理がその時点の共通指示を読み込む。
稼働中の全担当が即時に読み終えたとは報告しない。
