# ToDo2494 調査結果：保存投稿の安全な確認経路

確認日: 2026-10-13 JST

## 結論

現時点で、指定された保存投稿の本文を開ける安全な経路は確認できません。保存投稿と対応するMarkdownは `scrub391 --guard-path` で保護対象かつ分類未確認となり、原台帳も復旧済みではありません。本文・元文脈・本人IDは閲覧していません。

## 確認した根拠

- 調査対象の作業範囲と受付ソースは保護対象ではないと判定されました。
- 指定された保存投稿と対応するMarkdownは、保護対象かつ分類未確認でした。空の原設定や許可情報は作成していません。
- 元登録範囲の実装ソースでは、受付時に設定済み本人ID、非Bot、対象フォーラム/スレッド、期限を確認し、Discord API由来の投稿ID・スレッドID・本人ID・日時を保存します。
- 実行前の照合では、正規APIから同じ投稿を再取得し、投稿ID・チャンネル・本人ID・Bot判定・日時・本文が保存時と一致することを要求します。これは出所と投稿世代の照合であり、保護判定を解除したり、閲覧許可を作ったりするものではありません。
- これらはソース実装の確認です。この投稿に対するライブAPI照合や、稼働版での実行はしていません。既存CLIのヘルプも確認しましたが、read-onlyの返信取得は新しい回復質問専用で、元投稿を確認する手段ではありません。
- 元ToDoにひも付くsteering用フォルダーと想定ファイルは存在しません。ソース上、steeringは既存ToDoへの後続本人返信を届けるときに別途作られるため、元投稿自体に適用する保存済みsteeringは確認できませんでした。中身は読み取っていません。

## 元担当が再開するときの手順

1. 原設定・旧台帳の復旧を担当するToDo2467の結果を待ちます。空の台帳を作ったり、今回の依頼から許可を追加したりしません。
2. 復旧後、指定された保存投稿ファイルと対応するMarkdownを個別に `scrub391 --guard-path` で再判定します。各対象について `client_resource:false` かつ `classification_unverified:false` が確認できなければ本文を開かず、ToDo2493を未完了のまま維持します。全台帳の復旧をこの判定の前提とはせず、該当資源に対する原記録の復旧を確認します。
3. 判定が通った後、正規APIで同じ投稿ID・スレッド・設定済み本人ID・非Bot・日時を照合してから本文を表示し、処理を続けます。今回、既存の正規照合処理が副作用なしで呼べるかは確認できていません。
4. 既存の正規照合処理をread-onlyで呼べない場合に限り、最小の追加実装は、元ToDo/受付キーで対象を一件に固定し、まず対象ファイルの保護判定を行い、通過後に正規API照合を行って一致時だけ本文を返すread-only入口です。投稿・ToDo更新・担当起動は行わず、保護許可を追加しません。これは今回の確認範囲では実装せず、親2488のrunner編集にも触れていません。
5. API照合経路が使えない場合は、別CLIや別表記で迂回しません。ToDo2467の原記録復旧結果と、親2488の正規受付経路の修復を待ちます。全設定の復旧が必要かは、復旧担当が原本を確認するまで断定しません。
