# Skillsの公開情報と内部検証記録を分ける

公開するSkillの出典と内容を確認できるまま、実行時の内部情報を公開ファイルへ含めない。今回の対象は既存のSkill作成・レビュー受領・作成物の読戻し・利用確認の経路であり、一般の保護設定や未知の資料へのアクセスを変更しない。

## 公開する情報と内部で保持する情報

- 公開manifestと同梱する出典情報は、固定repository・commit・path、元本文と個別noticeのhash/byte数、対象ファイルと内容hash、用途と変更内容を保持する。実行job、workspace、内部spec・判断の識別情報、会話やセッション情報を含めない。
- 実際の担当・作成者・現在の利用者、通常登録された仕様、判断範囲、レビューと作成時の根拠は内部requestと正規の検証記録へ結ぶ。公開側の項目を削ったことを、担当や許可の照合を省く理由にしない。
- 新しい形式は明示的に区別し、既存形式の正規な作成・読戻し記録を保持する。内部の対応付けを公開本文へ書き戻したり、過去の担当・原応答・作成物を現在のものへ変更したりしない。
- 既存の参照manifestは、変更しない固定資料として修復範囲を照合するためにだけ使う。新形式の作成要求や配置成功、現在の内部情報を公開してよいという許可にはしない。

## 実際の処理で確認する

1. 新形式のレビュー対象を公開の固定版・同じ内容のbyte列へ結び、実担当と独立した確認者・原応答・実行条件を内部記録で照合する。本文・notice・対象を差し替えたものや、異なる担当の結果を受け入れない。
2. 新規作成は現在の正規担当と判断範囲を確認し、許可された不在の対象だけをCreateNewで作る。同名衝突・既存原本・junction・差替えを保持し、上書きや別名での迂回をしない。一般の保護対象や原設定を再作成しない。
3. 作成時と現在の同じファイルを通常の読戻し経路で照合し、同じbufferのhash・サイズ・由来を確認して使用する。公開metadataから内部job情報を除いても、正規の作成者と対象の対応が失われないことを確かめる。
4. 新しい読み取り専用の利用担当でも、通常保存されたscopeと元の作成根拠だけを使う。長く再開している作者と新しい担当の起動指示が異なる場合は、独立した実行時の出所を証明し、任意のprefix除去・担当の自己申告・古い根拠へのfallbackで通さない。
5. 利用時の本文取得と、その担当の完了結果の受領を両方検査する。設定・登録・呼出し・metadata発見だけを、実際の本文読了と指示の使用の成功へ数えない。

## 回帰と完了条件

異なる担当・仕様・対象・入力版、過去の応答や作成物の流用、JSONの重複key・case別名・欠落・未知項目、読取権限と時間窓の不一致、作成衝突を拒否する。公開ファイルと内部記録の両方を変えて自己整合させただけのものを、独立した出所の証明にしない。未取得・未知・初回の表示不足・過去と現在の物理的連続性の未確認を保存する。

変更した処理と利用側のGo検査、必要なレビューと最終版のCI、通常のマージとWindows実行版の更新、その更新後の実CLIまで確認する。稼働中の別の書込みと並行変更を調べ、受入済みの実行版を古いものへ戻さない。APIキー・追加支出・新規契約・一般の保護解除は用いない。

現在の作業場所の途中差分・コミット・公開結果・原資料を保持する。この固定資料はcheckoutや復元要求ではない。同じ要件をすでに修正・検証した部分は、その実結果を受け入れて重ねず、残る工程だけを同じ担当で続ける。取得、担当への配送、実読、修正、検証、配布と実利用を分けて記録する。
