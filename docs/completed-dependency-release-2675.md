# 完了済みの依存を待ち続ける不具合（ToDo2675）

## 確認した原因

2026-10-15、元2671は2673の完了後もwaitを保持した。2673の実ジョブは
10:39:09にsucceededとなり、共有ToDoにはschedulerの完了文とfinishedが保存されていた。
11:06を過ぎても2671の依存は解除されず、主担当が11:10の標準再開を実施した。
この実再開は本修正の自動解除によるものではない。

起点のmainは183ac4f。PR170は監査文書の追加であり、同じコード修復を含まない。
`unattended-runner/runner.go`の定期処理は`repair-step`を呼ぶ。
`Scheduler::reconcile_repairs`はdoingの結果だけを反映し、waitを処理しなかった。
`reconcile_item`がdoneを保存する経路にも共通の依存解除呼び出しがなかった。
その後のdispatchはtodoだけを候補にするため、完了済みの依存を持つwaitは候補に戻らない。

一方、`todo.exe done`は同じ共有ロック内で`todo_wait::release_ready`を呼ぶ。
通常watchの計画にも同呼び出しがあるが、修復用の定期経路はwatchを実行しない。
一般watchは欠落した原保護一覧を必要とするため、その代わりとして無条件実行できない。
`todo.exe list`は明示的に読み取り専用であり、成功終了しても待機は解除しない。

## 修正

修復結果を反映した後に、確認済み修復範囲の待機を再照合する。
既存の共通解除処理に選別条件を追加し、状態変更・世代・再開印の扱いは再利用する。
新しくdoneになった依存と、前の回にdoneとなって取り残された依存を扱う。

対象は既存の修復用プロジェクトに属し、dispatch許可と保存済み指示があるwaitだけ。
通常の準備と同様に元リポジトリとworktreeを既存guardで確認する。
共有仕様の保管先を新しくguardへ許可する変更はしない。
本人の停止・質問・外部条件・未完依存・不明な依存・予約中の復旧は維持する。
実担当の状態とPID作成時刻を確認し、生きている担当があれば待機解除もしない。
遅い保護確認はロック外で行い、ロック内では行全体・プロジェクト対応・全依存を再確認する。
割り当ては従来のdispatchへ戻し、実行枠・優先度・資源制限は変えない。
