# 司令塔の巡回と状態の確認

既存の2つの定期タスクと既存の常駐巡回を使う。監視するチャット担当が終わっても巡回は継続する。

Consoleは開始・完了・失敗を `commander-health.json` に記録する。Operationsは稼働中、要対応、状態未取得を区別する。失敗、読取不能、開始から90秒経過した未完了、3分より古い完了は要対応。開始記録がある場合、古い完了で正常とは判定しない。配下の作業の失敗やCPU枠の待ちから司令塔へ状態を波及させない。

外部受信は最大20秒、GitHub取得は最大8秒、ほかのコマンドは最大45秒。常駐巡回の50秒の単調時計予算を子処理へ渡す。起動と出力取得も予算に含む。匿名ファイルを使い、出力パイプの無期限の終了待ちをなくす。実行中に2MiB超過を観測したら所有する子プロセス群を終了する。処理途中の受付記録を保存し、期限後は次の巡回で続ける。

定期巡回は起動時の復旧確認、停滞監視、容量確認をDiscord取得より先に行う。観測結果を `tick-health.json` に記録する。この記録はコア監視3工程の結果であり、後続のDiscord工程全部の成功を意味しない。ログの更新やタスクのRunningだけを根拠に正常とは判定しない。

ToDoの他項目完了待ち、未着手、停止、保存されたジョブの起動待ち、Console受付待ち、受付に残る準備失敗は異なる件数。スケジューラーの待ち件数と混ぜてCPU待ちの合計にしない。作業の待機理由も開始待ち、ジョブ待ち、準備失敗、実測した容量条件を区別する。

配布前に稼働中のソースとの並行変更を確認する。Consoleの配布は起動を維持する定期タスクを止め、対象サーバーの終了を確かめて実行ファイルを入れ替え、同じタスクから再開する。定期巡回の配布も同じ既存タスクを利用し、新しい監視ループを作らない。
起動時の復旧が未完了でも、既存の巡回はToDoの `watch-preview` とスケジューラーの `status` で監視を継続する。復旧対象の所有が確定するまで新規起動は行わない。結果は観測のみのモードとして記録し、復旧待ちの異常を正常へ塗り替えない。スケジューラーがロック使用中を返した場合も成功として緑にしない。

本体は共有履歴の取得より先にポートを確保し、通常起動の最初の集計は既存の常駐処理で行う。起動中に定期タスクが追加の本体を起動する競合を防ぐ。初回集計前は未取得を表示する。確認用サーバーだけは初回の読み取り集計を待つ。

受付の起動候補ループでも期限を確認する。準備失敗の照合と記録にはその処理で取得したジョブ一覧を渡し、候補ごとに全履歴を読み直さない。作業場所の証拠は同じ受付処理の中だけ再利用し、ジョブ起動後には一覧と証拠を更新する。固定の工程名を巡回記録に付けても開始時刻や前回異常は更新しない。

Discord受信は、途中まで取得したGETページを16MiB以内で段階保存する。取得境界と受信位置が同じ処理を次の巡回で続ける。元の受信位置を進めるのは全体の照合が終わった後だけ。通信失敗は途中経過を保持し、ページ形状やページ送りの検証失敗では再取得する。認証設定や環境変数は保存しない。通常チャンネルの最新メッセージが受信位置以前ならメッセージ取得を省くが、スレッドの確認は継続する。

停滞監視のメタデータ取得工程は最大20秒、続くスケジューラー確認は最大8秒を使う。数千件の受領記録の照合が8秒で毎回中断されることを避ける。既存の巡回全体の期限は延長せず、子工程は常に残り時間にも制限される。

常駐巡回の起動候補は1回の受付処理で2件まで照合する。保留した候補は末尾へ回し、次回に後続候補を確認する。巡回には受信前後の受付処理があるため最大4候補を扱う。受付全件の完了と巡回の完了は別であり、残りの受付と準備失敗の表示を保持する。期限のない通常API操作は元の全件照合を維持する。
