# 準備記録と固定成果を結ぶテスト

固定ce1aad5fのrubber4033レビューを原文のまま受領し、実Luna/max・元の仕様・
31公開資料の範囲と照合した。
結果はMust0・Suggestion1・Nit0で、原文2,153バイトのSHA256は
`8d57cd7f61888869f2843702c25e2ad047f2e4d8f0ffe3a5c8d919ebe192f11c`。

準備記録に古いbundle・manifest・source selectionの参照や名前が混ざっても、
従来の意味検査だけでは通る5例を実際のRedで確認した。
修正後は、固定した読取先から独立に読み込んだ実ファイルのbytesから
3個のSHAを求め、準備記録のSHA・source selectionの名前と完全一致させる。
対象名も実bundleの順序と集合へ結び、古い参照・別ファイル・不足する名前を拒否する。
準備記録自身が指定するpathを開く方法にはしていない。

この変更は確認方法だけであり、14出力・個別notice・原の評価・
aliasの現在の読戻し証拠・伏字・未読・権利範囲・中央の状態は変わらない。
rubberの原文に含まれたacceptance行は、generic役割の引用された出力として保持し、
独立した全文Creator資格として使用しない。
全文Creatorの4222は、元の登録関係と固定source・実モデル・正規受領を別に確認する。

追加の再確認では、source selectionの内容自体もbundleへ結ぶ改善提案を受領した。
固定3cf35e52の原結果1,787バイトのSHA256は
`439633b2caff619002048a0dca66bdc04f38099ff3112075d9dcb3a4908c244e`。
同じ領域で2回目となったため、SHA同士の対応だけに留めず、入力の結び方を見直した。
独立に読み込んだsourceの同じバッファをハッシュ検証後に解析し、2行の全内容を
bundleの個別source情報へ完全一致させる。
そこから既存のoperationのsource・個別noticeとの照合まで一つの検査へ結ぶ。
古いsourceと一致する準備SHAを一緒に差し替える、行の不足、行の入替え、
権利範囲の拡張という実Red4件を確認し、全て拒否する。
元14出力・manifest015f・個別noticeと現在の状態は、この追加修正でも変更しない。
