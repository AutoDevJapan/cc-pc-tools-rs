# Codexジョブの同時実行上限

`queue-config.json` の `adaptive: {}` で自動調整を有効にする。省略またはnullなら従来の `max_running` を使う。`max_running` は自動調整の開始値で、実際の上限は `queue-limit-state.json` に原子的に保存する。設定を書き換える処理と競合しない。

`fixed_max_running: 25` なら直ちに25枠へ固定する。nullへ戻すと自動調整を再開する。固定値は自動の最小・最大とは独立している。上限の減少は新規起動だけに適用し、実行中のジョブを終了しない。従来どおり、親と子は同じ家族の枠を使い、子の上限と共有資源の規則を保つ。

## 測定と判断

毎分、窓を出さない `cc_queue_adjust.exe` を定期タスクから1回起動する。複数の起動が重なっても独立した非待機ロックと保存済み時刻により1回だけ測定する。ジョブの受付と状況表示は保存済みの結果を読むだけで、HTTPや利用枠の確認を待たない。`codex_jobs.exe adjust-limit` でも同じ処理を実行できる。

最小4、最大60。直近5分に429がなく、プロキシ `/healthz` が1秒未満、空きメモリ16GiB以上、CPU85%未満、利用枠が取得でき、全体の実行枠が足りずに順番待ちがあると+2。ToDoの完了待ち、再試行時刻待ち、子ジョブの上限などでは増枠しない。応答失敗・遅延、メモリ不足、CPU高負荷、新しい429が直近5分に複数ある場合は半減する。減枠後は再び5分の安定を確認する。最小・最大・増加数・時間・閾値はサンプル設定で変更できる。429の `error` と直後の `turn.failed` は重複させず、成功後も発生時刻を保持する。

CPUは Windows の [GetSystemTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getsystemtimes) の差分、メモリは `GlobalMemoryStatusEx` の空き物理メモリを使う。CPUの最初の差分、読み取れない測定値、古い利用枠では増枠しない。2回分と通信の上限・起動の誤差を超えた古い測定、時計の巻き戻り、読めない状態は最小値へ抑え、再測定する。壊れたJSONは原文を保存して再作成し、I/O障害は未作成扱いで上書きしない。

## 週の利用枠

5分ごとに OpenCodex の配布済みBunから `ocx account refresh openai --json` 相当を実行する。Anthropicは `ocx account list anthropic --quota --refresh --json` 相当を使う。APIキーを使う推論やモデル検証は行わない。各呼び出しは15秒、healthは2秒で打ち切る。

週の使用率、回復日時、アカウントIDと短時間枠の枯渇だけを保存する。メール、表示名、認証情報、生の応答は保存しない。停止・再認証・検証待ちのアカウントは対象外。回復日時は秒とミリ秒の両方を扱う。不完全な結果では増枠しない。

同じアカウント・同じ回復期間について、直近1時間以内で最も古い完全な観測と最新観測を比較する。各アカウントの「使用率の増加÷観測時間」と「残り使用率÷回復までの時間」の比を計算し、最も速く消費しているアカウントに合わせて上限を下げる。比較には5分以上必要。期間変更、使用率の減少、アカウント構成変更は比較を作り直す。減枠した観測を次の比較の起点とし、減枠前の消費を繰り返し減枠の根拠にしない。利用ペースだけが問題の場合は比に応じて下げ、応答やPC負荷の悪化は半減する。同じ観測による減枠は1回だけ。全アカウントの週または短時間枠が枯渇した場合は最小値にする。

Codexが速く枠を消費しているか回復待ちで、Claudeの週・短時間枠に余裕があれば `preferred_provider: anthropic` を返す。割り当てる側の判断に使う情報であり、明示指定したモデルや進行中のセッションは変更しない。

## 表示と記録

`status --json --summary` の `summary.max_running` が実際の上限。`summary.limit` に方式・理由・各測定値・利用ペース・推奨プロバイダーを含め、`summary.limit_label` に「上限 N（自動・理由）」を返す。CLIの一覧の上にも同じ文言を表示する。

`queue-limit-history.json` に毎回の値・理由・測定値と利用枠を最大1440回保存する。`queue-limit-state.json` は再起動後も使う。保存は既存の一時ファイルとWindows置換処理を使い、読み手に不完全なJSONを見せない。

配備順は2つのexe、毎分のタスク登録、設定に `adaptive: {}` を追加、`adjust-limit`、`reload-queue`。古い実行中ジョブは止めず、待機中の見張りだけ新しい実行ファイルへ移す。最後に30分間の履歴と実際の状況表示を照合する。
