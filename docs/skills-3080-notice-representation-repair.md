## Windows置換の競合を同じ範囲で解消する

ラバーダックが指摘した、旧SHA確認とFile.Replaceの間の競合は、合成Windowsファイルに
別byteを差し込むRedで実再現した。旧v3 scriptと原レビューは変更せず保持する。
新しいdeploy3686は通常のverifyが受け入れた同merged sourceから生成し、同じreviewed
全guard入力へ含める。新しいデータの資格確認や任意ファイルの置換には使わない。

v4 wrapperは実writer・既存の正常verify・候補byte・helperの実hash/sourceを照合する。
Go helperは固定scrub391 target、そのnonceのstage/backup、同writer、同clean sourceと
作業場所内のoperationだけに限定する。旧現物とstageをREAD+DELETE、書込み/削除共有なしで
開き、全物理親を保持し、同じhandleのSHA・owner/group/DACL・実IDを照合する。
初回renameの前に実IDをnative journalへCreateNew+Flushして残す。

同じ旧handleをbackupへno-replace renameし、同じstage handleをtargetへno-replace rename
する。公開の隙間で第三者がtargetを作ると衝突として失敗し、そのtargetを上書きせず、
既知の旧backupとstageを保持する。正常時のbackup IDは元ID、新target IDはstage IDと一致する。
異常時の復旧も同じhandleのno-replace renameだけで行い、PS側のpathでhash確認してから
backupを動かす処理は廃止する。物理的に一度も不在にならない置換とは主張しない。

独立したwrite/rename/親renameの拒否、公開直前のforeign CreateNew、old移動後・新公開後の
注入失敗と同じ元IDへの復旧、未知current/stage、既存backup/journal、hardlink、先行readerを
実Windows上で確認した。broker期限でprocessが終了した場合は自動で成功扱いせず、
原operation/native ID journalと現物・backup・stageを同担当が照合して復旧する。
未知の現物をforce rollbackしない。元16資料の取得・中央書込み・一般guardへ広げない。
## 配置資格を本体へ統合する

独立したinstallerの実行入口は廃止し、native処理は同じpackage mainの非公開関数へ統合した。
import可能な別packageも公開APIも残さず、本体のapply-skills3080-updateとrecover-skills3080-updateだけが、現在の実writer、固定した
公開source/merged source、候補byte、両方の正式なreviewを通常の処理で確認してから呼ぶ。
helperを別の実行物として生成・配布する経路はない。旧v3/v4 scriptと原指摘は保持する。

runtime requestは元のreviewとpeer_reviewを持ち、別task/job/thread、同じhead/domain、
両方の実native Luna/max・両owner_request、Must/Suggestion/Nitの明示0を必須にする。
片方だけで新しいsoftwareを更新する資格は成立しない。旧single-review requestは、
既に同じbyteが配置済みの読戻しに限り保持し、変更や復旧には使わない。

同じID/SHA/SDDLをdeny-write/deleteのrename handleで再確認し、review/source/candidateの
既存handleは保持したまま操作する。境界直前にも現在writerを再確認する。
nonceは正規requestへ保存し、stage/backupは固定client-records内の同nonceに限る。
未知の現物・別IDを新しいbaselineへ採用しない。

v5 wrapperは本体の正規verify→apply→配置後verifyを使う。子の60秒打切りは廃止し、

復旧は同じ実actorと同じ元requestでrecover-skills3080-updateを実行し、両reviewとsourceを

## 元のSkill名と配置名が異なる場合

上流のディレクトリ名だけから保管先を作る判定では、実際の4件のうち3件を照合できない。
同じ固定manifest内の`references/source.json`から、repository・commit・path・SHAと
個別noticeの全宣言、改訂担当job、保存先namespaceを対応付ける。
同namespaceのSKILL.md、原notice、同じ原行を残すmasked referenceを必要とし、
JSONの重複/case alias、競合する二重対応、別の出典/担当/namespaceを受け入れない。
原objectを読む段階では、取得済みindex/treeと照合したbytesとGit blobも同じmetadataへ結ぶ。
取得済み原bytesのSHA/Git blob、notice、伏字の物理行と可視本文の照合は引き続き行う。
既存の同名配置の経路は保持し、この対応付けだけで権利やアクセスの資格を増やさない。

公開済みの実4件/28ファイルのmanifest SHA `5ab55cfca8778374e86862905e9c39d5bfe11bea2ae6e3e33ec82f82e7607f89`
を変更せず、3f6ed705では実際に失敗し、対応付け後は構造上の出典保持判定が成功した。
合成した取得済み原objectの正負例でも、出典・notice・担当・bytes/blob・namespaceと
可視行の変更を拒否することを確認した。
これは実manifestの配置、原コーパスの追加読取、Windows実行版の更新を証明するものではない。

旧名のmasked referenceまたはraw原文の写しが同居しても、その存在だけでは先に成功しない。
別namespaceにある対応付けを最初に検証し、対応するmasked referenceも元の原objectと比較する。
正しい旧名/別名の同居とraw/別名の同居は認め、不正な担当や可視行が混ざった同居は拒否する。
従来の同名metadata形式は保持し、aliasがない正規のraw保持も変更しない。
旧3D入力8件/48ファイルのflatな出典metadataも、元のrepo/commit/path/SHAと
license path/SHAが一致する本来の上流namespace内だけで従来形式として扱う。
同じflat形式を新しい別名namespaceへ置いて、対応付けの検証を省くことはできない。
