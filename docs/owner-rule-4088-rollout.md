# 分類規則の配布後確認と復帰（4088）

レビューとラバーダックの全修正指摘、同じ最終候補のCI、Rustの関連テストの成功後にのみ配る。
最新版のマージ済みソースから作り、ソースcommit、入力カタログ、成果物SHA-256を保持する。
別担当の配布版が進んでいたら、そのsourceを包含するかを照合し、古い版へ戻さない。

## 配布順と証拠

1. senderの質問画像互換性を配る。旧guardとも互換なので、ここでは分類を切り替えない。
2. OMB readerと容量監査の互換対応を配る。
3. guardを最後に切り替える。

各置換は管理者窓口で行う。
既存のSHA、所有者・グループ・DACLを直前に照合し、旧版を保持したatomic replaceを使う。
配置後に新旧SHAと同じ権限を読み返す。SACLを確認していなければ未検証と記す。
実行中のguardがロックで置換できない場合は、稼働中のものと旧版を保持して有限の再試行へ戻す。
他担当のプロセスを一斉停止したり、ロックや正規審査を回避したりしない。

固定のOMB reader配布先は、元3255の登録資料を確認した範囲では特定できていない。
未特定の実行物を上書きせず、必要なら既存モジュールと同じCLI名の正規配置先を用意する。
その場合は新設であること、以前の実行物を変更していないことを区別し、元3255へ返す。
guard切替前に少なくとも既存の5コマンドを含むreaderのビルド・CLI・合成の用途資格テストを確認する。
固定API・Codexの実物が取得不能なら、nativeの実受入は成功と記録しない。

## 読み返す種類

| 種類 | 確認方法と期待 |
|---|---|
| OMB・Shorts・OpenCodexの元の場所 | 内容を開かず、配置したguardの通常CLIで結果と匿名の根拠だけを取得する。不在の実行先は不在のまま記録し、稼働成功としない。 |
| 予定worktreeと既存linked worktree | 自社登録の直下の未作成ルートだけclearで、深い未作成先や別物は拒否する。正常なlinked treeは通常判定で通る。作成・起動はしない。 |
| 旧形式の所有の根と退役資格 | その時点で有効な既存の独立資格だけを使う。不在・期限切れは復活させず、実物がなければ通常分類入口の合成fixtureの結果と区別する。 |
| 照合済みの会話の返信 | 同じ元質問・本人・返信世代に結び付く既存受領だけを使う。未照合の本文・一覧・受信状態・コピーは拒否される。 |
| 生成画像の質問資格 | 最終ソースのsenderの統合テストで、既定の帰属から質問専用の照合を通すことと、受託陽性・別質問・通常logでは拒否することを確認する。実物の資格とその元質問がなければ、新しい質問や偽の生成票を作らない。実送信をしたと主張しない。 |
| OMBの固定native metadata | source/binaryはclear、nativeの規則による未帰属は正常APIとの固定結合を通るときだけ許可。他の保護は拒否する。実受入と合成fixtureを区別する。 |
| 混在保管先と報告 | 本文・状態・バックアップはclearにしない。容量監査のJSONで根拠が分かれ、従来status/schemaは保たれる。実データの走査や清掃はしない。 |
| 台帳の複製とメモの退避履歴 | 拡張子の前と後の接尾辞、退避したメモ、停滞報告・容量判断の保管先も拒否する。合成fixtureで本番設定を通し、原記録の内容は開かない。 |
| 古い容量監査の再開 | 根拠が保存されていなかった件数を未記録として保持し、既存の総数と整合することをJSONの保存・再読で確かめる。 |

通常利用者の環境で実物のCLIを読み返す。
環境変数を除く利用側の条件も、同じWindowsアカウントの非表示の子処理または合成テストで確認する。
identityの期限切れだけなら、同じ正規更新を一度行い、次の通常判定で確かめてから判定する。
この有限の更新だけで失敗を捏造せず、期限延長・許可ファイルの手編集はしない。

## 復帰する条件と順序

新しい配布物のSHA・権限の読返しが違う、受託陽性や混在本文がclearになる、
有効な既存資格の再現テストが失敗するなど、今回の切替に起因する問題があれば、
guard → 容量監査 → OMB reader → senderの逆順で旧版へ戻す。
変更後のソースを保持し、失敗した新しい実行物も別名で保持する。
新設のreaderだけは、同じバイトと所有を確認して別名へ退避し、以前の未配置状態へ戻す。
他担当がさらに更新した実行物は上書きせず、旧版と新候補を保持して原因を返す。
各段階の実SHA・権限・復帰可否を記録し、部分的な復帰を全体の成功にしない。

単なる不存在、元からのAPI停止、期限切れの旧資格、他担当の更新は今回の回帰と混同しない。
正常な配布を失敗扱いにはせず、実物で確認できた結果と未確認の実受入を分けて元2467へ返す。
