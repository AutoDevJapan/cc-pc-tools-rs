# 共有Cargoが128GiBで止まる問題の修正

2026-10-07 15時ごろの調査では、保存先はDドライブの `D:/CC/BuildCache/cargo-shared`。容量は138,401,126,999 bytes（128.896GiB）、73,800ファイル。Dの空きは1,825,769,099,264 bytes（約1,700GiB）、Cの空きは1,030,244,823,040 bytes。128GiBという固定上限で停止しており、実際のディスク不足ではない。

設定元は `cc-jobs/src/cache.rs`。`codex-jobs/bin/cargo.cmd` が `cargo_gate.exe` を呼び、共有target専用の固定1枠ロックの下で容量を確認する。`CODEX_JOBS_CACHE_MAX_GIB` で上書き可能。ジョブの起動環境は共有targetを指定し、incrementalを無効化する。終了時の `cc_cache_finish.exe` も同じ上限を参照する。Skill rust-cargo-target-contention は競合防止の手順であり、128GiBを設定していない。

主な内訳はdebug 123.468GiB、release 3.049GiB、Android 1.934GiB、wasm 0.435GiB。依存物にはwindows-sysの87構成、serdeの71構成、tokioの68構成があり、万世紀、GoDD、PC管理ツールなどの生成物が混在する。Cargoのdep-infoには相対ソースパスもあり、既存の成果物からリポジトリ・ブランチ・最後の使用日時を一意に復元できない。既存の所有台帳はない。使用履歴の代わりにファイル更新日時を使わない。

全ファイルの作成日時は10月4日以降で、7日以上前のものは0件。古い更新日時の約21MiBは、作成時に依存ライブラリから日時を引き継いだファイル。マージ済みブランチの成果物も共有依存物として再利用されるため、ブランチ名だけで消せない。今回、安全に不要と確定できる整理対象は0件。既存ファイルの削除・退避は行わない。

## 容量と整理の新しい動作

上書きがなければ、実際のDボリュームの「共有targetの容量＋空き容量」の25%を上限にする。最大512GiB、最低100GiBの空きを残す。調査時点では約457GiBになる。明示上限は引き続き使え、空き100GiBの条件も適用する。Cの空きからDの上限を決めない。

80%に近づいたら、固定ロックとCargo自身の既存プロファイルロックの下で、台帳にある7日以上未使用のファイルを古い順に整理し、75%を目指す。所有台帳はゲートの実行前後を比較し、ゲート中に新しく作られたファイルのみ記録する。生成時の作業先とGitブランチを保存する。旧成果物を所有済みとして取り込まない。全てのゲート利用を全記録ファイルの使用として扱う。依存物は更新せず再利用できるため、安全側に使用日時の上限を記録する。継続的に共有targetが使われている間はこの整理の対象が増えないという制限がある。

再解析ポイント、パス逸脱、置き換わったファイル、隠し・読み取り専用ファイル、ハードリンクは整理しない。内部ハードリンクも保持するので、既存のsafe-deleteの判定は変更しない。削除失敗は再試行せず、同じボリュームの「削除希望」へ移動を試み、理由と結果を保存する。移動できなければ元のファイルを保持し、エラーを出す。容量を回復できなければ後続ビルドは停止し、無制限に生成しない。

所有記録を開始前にも保存し、Cargo中にプロセスが終了しても直前の利用を古い利用として扱わない。成功・失敗にかかわらず終了後の新規生成物を記録する。
