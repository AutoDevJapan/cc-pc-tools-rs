# 元1626の再試行を通常キューへ結ぶ

元1626は技術的な再試行時刻を記録しても、資格保存・待機解除・受付・通常startが分離されていた。解除後のクラッシュで取り残され、受付前後の本人停止を通常startが上書きする可能性があった。

このAPIは既存の元1626の資格だけを使う。期限は2026-10-21 00:00 UTCより前。dispatchableはfalseのまま、元の仕様・作業場所・実担当のセッション・モデル・権限・プロファイルを保持する。一般の製品、元2475、名簿例外、別日の制作へ広げない。

## 呼び出し

1. `todo.exe product-retry-reserve 1626 --key <固定キー> --expected-worker <元担当>`
   正式guardを窓なし・期限付きで再検証し、待機・所有・依存・実プロセス・実セッションを照合する。通常キューと同じ `codex-jobs/jobs/.queue.lock` → ToDo lockの順で意図を保存する。元wait_readyを消さず、実行はしない。返るrun_executable/run_argsはシェルへ連結せず、引数配列としてそのまま使う。
2. 通常の`codex_jobs.exe run`を返された引数で呼ぶ。
   `--original-product-retry-key`は元1626と同じlaunch-keyだけ。元意図と本文のハッシュ・作業先・実セッション・モデル設定が一致する場合だけ受付する。元waitを保持していても受付できるが、未結合のモデルプロセスは起動しない。通常の枠・資源・優先順位・重複防止を通る。
3. `todo.exe product-retry-bind 1626 --key <同キー> --job <実ジョブ>`
   queue → job state → ToDo lockの順に再照合し、正しい実ジョブだけを結合する。ここで初めて元waitを除き、worker receiptと世代を更新する。本文・ソース・本人停止・新しい依存や待機は上書きしない。

reserve/bindの結果のlaunchedは0。受付・結合と、実際のモデル実行は区別する。通常queueが最終の共有ロック内でも停止・期限・割当と本文を検査し、結合後に初めて実行を許可する。

## 中断と変更

キーは元waitのsince/not_before・元仕様SHA・元作業場所から固定する。ノートや資格確認時刻で変えない。受付後に落ちても同じキーの実ジョブを回収し、別のsupervisorを作らない。結合の再送も世代を増やさない。本文はハッシュ付きファイルへ一度だけ保存し、ツールの更新後も同じ意図の保存済み本文を使う。内容のない別原本を作ったり、不明な本文を復元した扱いにしない。

本人停止・新しい依存・新しい待機・仕様/元担当の変更が入ったら、その変更を保持して古い受付を起動しない。未結合は通常の待機、失効・無効化はqueuedの当該試行だけを終端にする。実行中モデルや他の仕事を終了しない。

原資格のセッションと、直近の実担当のthread/resume sessionは別。資格の古いsessionを実再開先として流用しない。正式guardと実担当記録の両方を確認する。

## 配布と受入

todo.exeとcodex_jobs.exeを同じ検証済みソースから通常配置してから、既存Go巡回へ接続する。APIだけ、Goの候補判定だけ、登録や結合だけを自動再開成功と報告しない。親2706がAPI、子2709/PR181が既存巡回への接続と、自然に期限を迎えた元1626の実自動再開を担当する。

原保護設定の復旧、旧質問の再送、一般のローカル作業範囲の登録は本件に含めない。

## 同じ担当が既にキューへ戻っている場合

通常の文脈引き継ぎ・429待ちなどで、結合済みの同じ担当がqueuedへ戻る場合がある。初回の実sessionは厳密に固定するが、起動後の通常の文脈引き継ぎのsessionは同じ担当の継続として扱う。元の作業先・sandbox・プロファイル・仕様と担当の結合は引き続き照合する。

新しい技術待機が満了したときに結合済み担当がqueuedで残っていれば、reserveはその担当を正規APIで再評価し、`continued_existing:true` / `job` / `saved` / `launched:0`を返す。呼び出し側はこの場合runやbindを追加で呼ばない。同じ待機の再送はsavedfalseになる。新しい担当や世代は作らず、期限・本人停止・新しい依存を保持する。依存完了後の同担当の入場時には、通常queueの共有lockで元ToDoだけをdoingへ戻す。

## 終端化した受付の再試行

reserveの入力keyはGoが観測した待機のbase key。返却keyとrun_args内のキーは、正式APIが割り当てる実試行のkeyであり、bindにはこの返却keyを渡す。元waitの識別子は変えない。

元状態を再検証し、以前の未結合受付が終端かつプロセスも残っていない場合だけ、旧意図を履歴へ保管して次の試行keyを発行する。未受付の意図が元状態変更で失効した場合も、先の受付がないことを確認してから保管する。liveの担当や結合済みの同じ試行を新keyで再起動しない。1待機での試行は0/1/2まで。上限到達は元waitと記録を保持する技術的な保留であり、本人の判断待ちや完了へ変えない。
