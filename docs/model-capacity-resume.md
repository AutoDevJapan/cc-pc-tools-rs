# 混雑したモデルから同じ会話を再開する

`codex_jobs.exe` は子プロセスが終了して最後のイベントを読み終えた後、失敗原因に `Selected model is at capacity` が含まれる場合にモデルを切り替える。大文字小文字は区別しない。成功・取消・監視処理の起動失敗は対象にしない。

切り替え順は `gpt-6.1-sol → gpt-6-astra → gpt-6-luna → gpt-6.1-sol`。現在のモデルから次へ進み、1ジョブで最大3回切り替える。その後も混雑で失敗したら最終の失敗を保存して終了する。この回数は429エラーの再試行回数と別に保存する。混雑と429が同時に記載されていても、混雑の3回上限を優先する。

セッションIDは有効な `thread_id`、次に保存済みの `resume_session` を使用する。有効なIDがない場合や、この3種類以外のモデルでは自動で別モデルへ移さない。新しいジョブを作らず、元の待ち行列へ戻し、`codex exec resume <セッションID>` に次のモデルを渡す。プロンプト、作業場所、権限、推論の強度、ToDoの所有情報、文脈の引継ぎ段階を保持する。通常のOAuthログインをそのまま使い、認証を切り替えたりAPIキーを追加したりしない。

`job.json` の `capacity_retry_count` と `capacity_history` に回数・時刻・切り替え前後のモデル・セッションID・秘密情報を伏せたエラーを保存する。元の `events.jsonl` と `stderr.log` は追記のまま保持する。監視処理を更新しても回数と履歴は保持する。

配備時は現在の実行ファイルを別名へ移して新しいファイルを配置する。実行中のジョブを終了しない。必要なら既存の `reload-queue` で、子プロセスが動いていない待機中の監視処理だけを更新する。更新前から実行中の監視処理はその実行ファイルの動作を維持する。
