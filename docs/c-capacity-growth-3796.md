OSハンドルはFILE_READ_ATTRIBUTESだけで複製し、内容を読んでいない。
同じファイルを複数のプロセスが開くため、容量はファイル識別子で重複を除く。
未分類のパス・個別ファイル名・コマンドラインは出力せず、この匿名測定で
一般の保護判定や削除資格を変更しない。

Dockerの既存02:07集計と14:00集計を照合した。イメージ57.79GBとビルドキャッシュ
44.69GBは表示値が不変。ボリューム24.31→24.35GB、コンテナ383.4→394GBであり、
数値はDockerの丸めた表示。朝以降の差分やホストCの回収量とは同一視しない。
イメージの最も新しい作成日は10月21日。削除候補や不要性の認定には使っていない。

既存の正規`opencodex storage codex-logs status --json`は、既知のログスキーマと
匿名の集計だけを返した。元DB本文・ターゲット名を取得する独自SQLは実行していない。
`storage report`から保存したのも固定の分類別バイト数・件数・時刻だけで、
実パス・個別の大きいファイル名は保存/表示しなかった。これは論理ファイル長の
参考集計であり、一般guardの復旧、リンク境界の検証、Cの実割当や削除資格の証拠ではない。
今後の一般領域の再帰調査は通常guardの確認が必要。正規ログCLIの仕様は
[用途限定の診断](https://github.com/mashfromband/opencodex/blob/dev/docs-site/src/content/docs/guides/codex-log-guard.md)にある。

最初の管理者読み取りは、NTFS全体のallocationreportを含めた55秒の期限で終了124。
原結果を保持し、同じ呼び出しを無限再試行しない。allocationreportを外した独立の
VSS・ページファイル・NTFS・USNメタデータ読み取りは、既存AdminBrokerで終了0。
OS/本人データ/未完了成果を変更していない。

結果の取得前に期限へ達し、自分が起動したfsutilだけを終了した。取得行0、未測定。
AdminBroker自体の終了0を、allocationreportの成功へ読み替えない。残留fsutilは0。
同じ全量問い合わせはこれ以上繰り返さず、分類資格と既存原記録の正規復旧へ返す。

原保護が未復旧の一般領域を、別名・コピー先・全許可・ファイルID読取で走査しない。
既存の用途限定CLIと実所有証拠を照合し、Windowsの匿名メタデータによる絞込みを続ける。
必要な保護資格の不足は具体的な測定と目的を元2467・親3628へ返す。
