# 履歴照合と実行中の境界確認

ToDo3049 / [Issue #259](https://github.com/AutoDevJapan/cc-pc-tools-rs/issues/259)

## 観測と対象

元3047/3048は一時的にqueued・0stepとなり、3047には履歴照合ロックの
OS error 33が記録された。その後、現行版の通常キューで3047が37step、
3048が53stepまで進んだ。起動不能が継続しているとは扱わない。
既存の照合記録は8,713件、全体16,099msで、開始ゲート待ち11,255ms、
レコード読取4,381ms、確定447msだった。これは修正後の性能値ではない。

受付用一覧は30秒で再照合が必要になる。実行枠を割り当てないツール境界の
確認までこの再照合を開始していた。実行中の担当も全履歴の読取と
照合ロックを競合させうる機構を再現したが、保存されたerror 33の全事象を
この呼出しだけに帰属させることはできない。今回の変更は候補の読取と、
実際の受付・停止を伴う遷移との分離に限る。
分割走査や永続化形式の変更は、自然回復後の根拠では必要性を確認できず、行わない。

## 入力・出力と責務

- 境界確認は完了した一覧から候補IDを取り、各候補の現在のレコードを読む。
  全履歴の走査、一覧の書換え、実行枠の確保を行わない。
- 一覧が存在しない、壊れている、または照合未完了なら、境界確認は候補不明を返す。
  次の確認へ延期するだけで、実行中の担当や履歴を消さない。
  候補不明を子孫なしの空一覧へ変換せず、文脈上限でも準備や一時停止へ進めない。
- 実受付は境界候補の読取とは別に履歴照合を準備する。初期化と30秒後の更新、
  scan→queue→stateの順序、競合時の有限の再試行を保持する。
- 実受付はqueue gate取得後にも完了一覧と最新の各候補を読み直す。
  照合や保存が失敗したとき、部分一覧から成功や実行枠を作らない。
- 実際に担当を止める可能性がある完了境界では、一覧を再照合してから候補を再判定する。
  旧方式の子孫が見つかったら準備や一時停止の前に延期する。遅い準備の後、
  確定側でも30秒以内の履歴網羅を要求し、期限切れなら停止を確定しない。
- 登録は従来のqueue/state lockで原子的に行い、照合の確定時に新規登録と
  再登録を合流する。旧active、PID identity、source所有、仕様変更、
  cancel/drain、モデル枠、優先順位の検査を保持する。

## Given / When / Then

| 条件 | 操作 | 観測できる結果 |
| --- | --- | --- |
| 完了した一覧が30秒より古く、他の照合所有者がいる | 境界を確認する | 現在の候補が返り、照合ロックを取得・待機しない |
| 一覧が未作成・破損・未完了で、照合所有者がいる | 境界を確認する | 候補不明として延期し、一覧と旧ジョブを変更しない |
| 完了一覧と多数の終了履歴がある | 境界を複数回確認する | 候補の現在値だけを読み、終了履歴を再走査しない |
| 古い一覧の作成後に旧方式のactiveと新規登録が増えた | 境界確認後に通常受付する | 実受付が旧activeも照合し、上限と所有権を守る |
| 走査中に登録、確定時に読取失敗、または部分一覧へ変更 | 通常受付する | 登録を保持し、不完全な状態で起動しない |
| 別プロセスが走査ロックを所有する | 並行する通常登録と照合 | 登録が保存され、起動は照合完了を待つ。所有者を停止しない |
| 文脈上限に達し、子孫の一覧が不明 | 完了境界を確認する | inventoryや一時停止へ進まず、確認を延期する |
| 完了一覧の後に旧方式の子孫が増えた | 実際に停止可能な境界へ進む | 再照合で子孫を発見し、inventoryや一時停止より前に延期する |
| 準備の後に履歴網羅が30秒より古くなった | 停止を確定する | code 75で延期し、古い一覧から停止を確定しない |

並行登録・確定失敗・他プロセスの照合ロックの条件は既存のparity回帰検査を再利用する。変更クレートと利用側の検査、
別モデルレビュー、正式CI、通常マージ、既知hash・backup・原子配備の後、
元ジョブの実プロセスとstepの増加を再確認する。同じ件数・条件の測定値を残す。

## Red / Greenと同条件測定

修正前のnextest `c9702d8b-b565-46e9-b9aa-3e333e4054f6`では先行4件がすべて
意図どおり失敗した。2件は使用中の照合ロックへのアクセスでerror 33、1件は
境界確認による想定外の全走査、1件は候補3回に対する777回のレコード読取だった。
修正後の`26b89aef-110e-4122-b585-c889c324e27e`では5件とも成功した。
この最初の候補は別モデルレビューで未完了一覧の扱いにMustが1件見つかった。
文脈上限と一覧欠落で延期しないRed（`5c5e3af7-8dc3-44de-b57a-79e9bf0b2c17`）を
確認後、候補不明を明示し、実際の停止遷移でも旧方式の子孫を再照合するよう修正した。
追加3件を含む8件が`b3d5b3dd-fdfc-4c1a-8b63-62629539a9df`で成功した。
子孫が実際に終了した場合はinventoryと一時停止の注入先へ進む正の対照も確認する。

再レビューでMustは解消した。追加提案に対応し、候補不明の親にも実際の検査対象と
なる仮想PIDと完了イベントを設定した。さらに実際の一時停止後に履歴を31秒古くする
parity検査を追加した。停止確定側の2呼出しを古い通常読取へ戻した場合に、誤って
停止・次の起動へ進むRed（`8eac2e1c-52a4-4dff-abbd-cef3e7ef7160`）を確認した。
新しい読取へ復元後は9件が`6427f7eb-f246-4ce2-a074-04372cb9f5fd`で成功し、
期限切れなら元プロセスを維持し、同じ条件で履歴が新鮮なら停止して引き継ぐ。
実行コードの追加変更は古いコメントの訂正のみで、停止処理は再レビュー済みのまま。

専用worktreeの同じtestプロファイルで、同じ内容の合成ジョブファイル8,713件
（終了8,712件、候補1件）を使用した。初期照合後、仮想時刻を毎回31秒進め、
境界確認を3回測った。ファイル読取とOS lockは実物で、外部の担当やAIは起動しない。
実運用の履歴を複製・表示した測定ではない。

再測定は次で行う。

```text
cargo nextest run --locked -p cc-jobs --lib --run-ignored only -E 'test(boundary_snapshot_history_perf)' --success-output immediate
```

これは境界確認に限った測定であり、通常受付の全走査の短縮やキュー全体の
起動時間改善を証明する値ではない。
