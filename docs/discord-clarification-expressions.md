# 説明受付の表現境界（Issue414）

対象: [Issue414](https://github.com/AutoDevJapan/cc-pc-tools-rs/issues/414)。
既存の[説明補足契約](discord-question-clarification.md)を維持する。

## 判定の順序

1. 対応する引用符の直後に「って・という・について」や格助詞が続く場合、引用内容を名詞として扱う。
   引用内の語を作業指示に数えない。選択を確定する節全体を引用符で囲っただけの場合は判定を残す。
2. 文全体の作業依頼を先に調べる。理由や費用の語の後、接続語の後、次の文の依頼も対象にする。
   「教える・説明する・見せる・示す・聞かせる・伝える・知らせる・話す」依頼は説明として区別する。
   この動詞の例外は「説明してもらえますか」のような、直後の「て＋丁寧な依頼」に適用する。
   名詞で頼む従来の「説明をお願いできますか」や「内訳をお願いできますか」も維持する。
   「内訳をまとめる・補足する・出す」は情報の提示として扱う。「費用を出す」はこの例外に含めない。
   「手続きをお願いできますか」や
   「進めてください」は作業依頼であり、先行する説明動詞では免除しない。
   後ろに別の作業依頼が続けば、その作業依頼を優先する。
   「決めて、進めたの？」のように理由を問う文中の接続形と、直接の作業依頼を区別する。
   「選んで」は「て」と異なる活用として扱い、依頼の語尾との組合せをテストする。
3. 選択記号ごとに節を対応させる。選択の確定、必要性が分かったという断定と、理由を質問する節を区別する。
   「aにして理由を教えて」は選択の指示を含む。「なぜaにして理由を教えるの？」はその理由を問う。
4. 数量を伴う「が」、禁止の理由、「って」で引用した話題は理由質問として調べる。
   漢字の語末や区切りだけを根拠に受理しない。「払うが」「くらいが」「まんがなんで」の対照を維持する。

この判定は、元質問へ説明を補う用途のために列挙例と対照例で境界を固定する。
自然言語の完全分類は保証しない。すべての指示を理解する機能や、一般の承認判定へ広げない。
引用は対応する「」・『』・“”・ASCII二重引用符の単一行を扱い、入れ子を完全解析するものではない。
本人性、元質問、用途、固定本文、現在返信版、保存前検証、GET回収、非通知の契約は変更しない。

## 定義を尋ねる返信（ToDo3258、Issue352）

元質問への初回説明で、理由を尋ねる語だけを認識し、用語の定義を尋ねる返信を
拒否していた。架空例「作業領域ってなに？」「作業領域って何？」
「作業領域とは何ですか」「作業領域とは？」を説明要求として扱う。
定義の問いに続く「作業領域を二種類に制限したい」という方針の表明も、
その問いへの説明を妨げない。説明送信は方針の実反映・元判断の回答とは別の工程である。

既存の優先順位は維持する。説明不要、明示的な実行指示、a/b等の選択確定は
定義の問いを含んでも説明専用の入口では拒否する。引用された問いだけを説明要求に
せず、「作業領域ってなにか変わったね」という叙述も区別する。
本人の原文、元の固定説明、用途JSONを言い換えて受付を通す修正は行わない。

受入は実Rustの分類と公開check_clarificationの両方で変更前の拒否を再現し、
修正後に同じ陽性・陰性を確認する。元質問の現在版・指紋・本文・本人・bot・
用途・通知なし・重複防止の照合は変更しない。架空例の成功をDiscord実配達とせず、
正式マージと配布後に、元の固定入力でcheck-only・初回送信・API読戻しを確認する。
