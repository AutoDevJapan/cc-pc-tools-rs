# 返信確認の期限と、既存dispatcherの実行期限を分ける

元3650の実再開時、元の確認情報の復旧後も優先順位待ちが続いた。
既存の毎分タスクは動いていたが、返信確認の後に開始する新着取得の期限が
periodic normalの32秒を使い、repair-stepへ到達できていなかった。
実healthはscheduler_deferred、schedulerの永続状態は手動実行時しか更新されていなかった。
元の優先順位を変えたり、待機中の元作業を別の起動経路へ移したりして解消しない。

既存dispatcherの同じrepair-stepを、同じユーザーの独立した毎分実行へ移す。
起動プログラムはunattended-runner scheduler-tick、呼出し先と引数は固定する。
実行自体は一回で終了し、新しいAI監視担当や巡回ループは作らない。
従来のscheduler.lock、優先順位、起動間隔、所有、停止、依存、容量、資源、保護判定を使う。
旧の毎分タスクは返信・新着・報告・既存CI受付を継続する。

明示的なscheduler-stage-mode.jsonが有効な場合だけ、旧の周期処理から同期呼出しを外す。
設定は用途とenabledを確認する。未設定の互換動作と通常の単独CLIは保持する。
新しい実行は独立した短いロックと150秒の期限を持ち、元のrunner.lockを取らない。
正常終了・busy・失敗・期限・結果保存失敗を区別する。失敗の生出力や他の作業本文を
結果へ保存しない。Rootの資格、ToDo、権限や停止状態を新しいファイルから変更しない。

旧のhealthには、新実行が本当に完了して保存した結果だけを使う。
用途、mode、成功、開始/終了順、未来の時刻、3分の有効期限、実行時間を照合し、
設定やPIDがあるだけで起動・成功としない。記録は健康状態の観測であり、起動の許可ではない。

正式CIと別モデルレビュー後、現在の実行物と並行変更を確認する。
新しいタスクは旧タスクのprincipalと非表示実行を引き継ぎ、重複開始はIgnoreNew、
実行上限は3分とする。旧のdispatcher呼出しを外す有効化と組み合わせ、二重の巡回を残さない。
既存タスクの返信確認の毎分の動作と、dispatcherの実状態更新・実起動をそれぞれ確認する。
確認情報が成立した元作業から再開し、4件の元番号と履歴、元の保留と依存を保持する。
