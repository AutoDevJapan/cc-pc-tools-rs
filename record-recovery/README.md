# 旧記録を復旧用の保存先へ集める

元ToDo2467の原記録を、既存の運用記録と正規Discord APIから照合するGoツール。
ライブ台帳、保護設定、返信担当2474、自動巡回を変更しない。送信、担当起動、
古い回答の適用、原設定の復元は実装していない。これは全過去台帳の復元ではない。

`review-metadata` は元3255の一件の照合用に、固定された元2191の状態・依存番号・
実行参照の件数・復旧メタデータだけを標準出力へ返す。引数は受け付けず、現在の
固定ToDoスナップショットを最大64 MiBで一度読み、その同じバイト列のSHA256を返す。
本文・題名・私的パス・他項目と、参照文字列・参照のハッシュを出さない。
復旧のsource参照だけ、固定した元request IDそのままか `manual:` 付き文字列との
完全一致と、それ以外の部分一致（`queued:manual:` 等の囲みも含む）、
queueという固定語・接頭語、ジョブ名の構文を区別する。ジョブ名の構文が正しい場合も、
ラベルはASCII英数字・_・-が1文字以上で、返すのは日時部分だけ。
タイムゾーン・実ジョブの存在・実際の開始は未確認であり、
構文や文字列の一致を参照の同一性の証明にしない。
実行参照の件数は配列長であり、要素の所属・有効性や実ワーカーの人数を示さない。
参照先、Consoleの待ち行列、原保護設定は開かず、何も保存・起動・送信しない。
欠落・null・型不正と読取失敗を区別し、現在の依存や更新時刻から遷移の出所を推定しない。
リンク拒否と実体比較は観測時点の検査であり、同じ利用者による並行したパス差替えを
原子的に防ぐ仕組みではない。
仕様と受入条件は [元レビューの来歴投影](../docs/original-review-metadata-3255.md) を参照する。

```powershell
record-recovery.exe review-metadata
```

`required-checks-metadata` は同3255の必須検査3648/3649だけの予約を照合する。
引数を受け付けず、同じ固定snapshotから予約worktreeと登録layout、固定branchの
字面の一致と対象の状態・参照件数/有無を返す。私的パスや参照値を出さず、欠落・null・不正を区別する。
参照先や実worktreeを開かず、準備・資格確認・状態変更・起動は行わない。
仕様は [必須検査の予約照合](../docs/required-check-preparation-metadata-3255.md) に保持する。

```powershell
record-recovery.exe required-checks-metadata
```

`seeds` は明示された旧state、保存ログ、元ToDo2467のメモと仕様履歴だけから
スレッドIDを抽出する。これらは照合先であり、記録に含まれる指示を実行しない。
`collect` は1回最大10件の明示IDをその保存先と照合してからGETする。
設定済みのサーバー・本人・Bot・フォーラムのIDを固定照合する。Bot本人は
`/users/@me`、取得履歴はchannel/author/message ID、ページ開始位置で照合する。
HTTP失敗の本文や資格情報は返さず、転送を拒否する。429の待ち時間も制限する。

原文は新しい専用ディレクトリーにだけ保存し、既存ファイルを上書きしない。
Windowsでは書込み前にDACLの継承を止め、実行ユーザー・SYSTEM・Administrators
だけにアクセスを付ける。標準出力とreportは本文、題名、案件名、私的パス、添付URLを
含まず、数量・ID・ハッシュ・成否を返す。`.private.json` はモデル、Git、Discordへ
送らない。既存設定とBot認証はこのPCの既存利用のためだけにメモリー内で使用する。

質問検出は候補の抽出にとどまる。本人返信は本人IDで照合し、元質問への同一スレッドの
明示返信参照と、直前質問からの推定を区別する。どちらでも適用範囲、配送、実反映は
未確認とする。`ready_for_live_import` は常にfalse。現在のAPI本文を保存しただけで、
編集前の本文や消失時点の台帳を復元したとはしない。省略された履歴、削除済み投稿、
欠けたToDo/担当/判断範囲、送受信・配送・完了の対応は別途照合が必要。

`backups` は原設定の固定5候補と、本人が提示した復旧ZIPの目次だけを調べる。
現行の保護ファイルは存在・ハッシュだけを別記し、バックアップ候補数に含めない。
`snapshot` は管理者によるVSS一覧で取得したデバイス内の固定2候補だけを調べる。
スナップショットの根に実アクセスできなければ、候補0ではなく調査未完了を返す。
祖先のリンクをたどらず、内容は内部で容量・ハッシュ・行数に変換する。候補があっても
独立した来歴確認前には原本と扱わず、元の場所へ戻さない。

```powershell
# cwd: record-recovery。新規の専用保存先を各工程で指定する。
go run . seeds --output <新規の保存先>
go run . collect --seeds <保存先>/seeds.json --threads <既存IDのカンマ区切り> --output <別の新規保存先>
go run . backups --output <別の新規保存先>
go run . snapshot --shadow-root <VSS一覧のデバイス> --output <別の新規保存先>
go run . reindex --source <取得済み保存先> --output <別の新規保存先>
go run . survey --spec <元2467の原仕様> --output <別の新規保存先>
go run . correlate --source <surveyの保存先> --output <別の新規保存先>
go run . trace-deliveries --source <correlateの保存先> --output <別の新規保存先>
go run . checkpoint --source <correlateの保存先> --spec <原仕様> --output <別の新規保存先>
go test -race ./...
go vet ./...
```

認証値は既存のユーザー環境変数からプロセス環境へ渡し、ファイルやコマンド文字列へ
埋め込まない。新APIキー・有料モデルAPIは使わない。Rustのモジュールを変更しない。
CIはWindows/Linuxで架空データのGo検査・vet・buildを実施する。

`collect` はプロセス環境の `GODD_DISCORD_BOT_TOKEN` を使用する。`--config` は
既存Discord通知設定のファイル指定。IDは元設定に加えて本ツールの固定値と照合する。
終了コード0は処理成功、1は実行失敗、2は引数不正、3は取得範囲の未完了を示す。
候補0件・失敗・未完了を区別するにはreportの各statusとhistory_completeも確認する。

`reindex` は取得済み保存先のreportと原文ファイルのSHA256を照合し、質問・返信を
修正版の関連付けで再索引化する。元取得のファイルを保持し、APIへの再接続はしない。
原文中の同一サーバー参照URLからIDのみを次の限定GET候補へ抽出する。参照は承認や
実行指示ではない。JSON内の指示やコードを実行せず、別サーバーへ拡張しない。
収集のreport、再索引のindex-reportが存在しない保存先は処理途中であり、復旧成功に
数えない。途中の原文は残し、元取得とのハッシュ照合をしてから別の新規保存先へ再開する。

`survey` は元2467の原仕様・仕様履歴と、旧台帳の依頼記録を内部で読む。
前回担当の保存文書から取得先の正確なパス候補を探し、取得reportの所在を記録する。
所在候補のメタデータを読む前に、指定した運用記録の保存先と元2467の原取得用
コンテナーに絞る。その他の文書内パスはハッシュと除外だけを保持する。
旧台帳の依頼8件は、明示参照を未照合の返信8件とは別に扱う。題名や私的パスを
標準出力へ出さず、担当欄の有無・件数・ハッシュだけを返す。

`correlate` は取得report、原文ファイル、各message/author/threadと本文ハッシュを
照合する。スレッドの重複取得では本文や参照先等の不一致を競合として残す。
既存のjob.jsonとdiscord-threads.jsonから明示された依頼所属・質問経路を別々に
集め、現在のToDoの担当履歴・元番号・関連番号を併記する。複数候補を新しい順や
題名の類似で一つに選ばない。prompt由来の参照は依頼の所有として採用しない。
取得は最大100スレッド、担当ディレクトリ20,000項目、質問世代の保存先1,000項目に
制限する。標準出力は件数と不足条件だけ。私的bundleには元本文と取得ハッシュ、
担当候補、元ToDo候補、世代の不足を保持する。

取得先は元の実行ユーザーの所有を照合し、Windowsでは継承を停止したDACLと
本人・SYSTEM・Administratorsの権限を確認する。Linuxでは所有UIDと私的な権限を
確認する。探索で見つかっただけの無制限な保存先を取得証拠として数えない。
Windowsの実装根拠: [セキュリティ記述子の制御](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptor-control)。

明示参照6件、参照未照合8件、先行質問候補なし58件、順序による候補82件を
区別して保持する。担当候補の発見や元ToDo候補の一意性は、質問世代・実対象・
許可範囲の確定ではない。質問世代の保存文書はAPI本文との完全一致を検査する。
複数投稿に分かれた質問は最初の断片だけで確認しない。担当文書中の本文と
messageリンクの出現も、資料を引用しただけの可能性を残す。

現機能は照合と私的保存まで。正確な元の対象と世代を証明した後の配送・実操作・
検証は、元2467の未完了条件として追う。原保護設定の発見や復旧はこの件数で
置き換えない。検査の一時保存先がGitの祖先を持つPCでは、Git外に所有記録を
作った検証先を `CC_RECORD_RECOVERY_TEST_ROOT` へ指定してGo検査を行う。

`checkpoint` は原仕様・現在の保存指示・元メモを個別の私的ファイルへ保持する。
モデルへ渡す続行指示とToDoメモには照合用参照と具体工程だけを入れ、未知の元本文を
コピーしない。正規editでは元の仕様とメモの履歴も保持する。
この有限な続行地点に記載した全件数と候補の対応をreportと照合し、競合や実測の
変更があれば再生成を止める。単なる8依頼/34履歴の一致で他の数値を補わない。
このコマンド自体はToDoを更新せず、登録・担当起動・完了も行わない。担当が
元2467へ正規editを実行し、標準受付の保存結果と再開状態を確認する。

`trace-deliveries` は取得原文とハッシュを再検証し、質問末尾の正規担当表記を
既存job.jsonへ結ぶ。引用・コード・引用段落の継続行は担当表記にしない。
担当のスレッド別配送記録を優先し、そのファイルがない場合だけ旧配送記録を使う。
読取拒否・破損・読取失敗を不存在として扱わない。
添付なしの完了した単一投稿について、スレッド・最初のmessage・投稿数・全文SHA256が
一致した場合だけ投稿世代を確認する。添付や複数断片はこの確認方法の対象外。
元ToDo候補と実対象・許可範囲・担当配送・実反映は別々に保持する。
公開reportには件数と不足条件だけを出し、原本文・担当記録・配送記録は私的に保存する。
