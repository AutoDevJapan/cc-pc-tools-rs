# 条件が変わった技術待機の再確認を早める（元3728）

元3700で、元3669の代替レビュー完了後も通常の `wait-retry --after 60` が
旧期限を保持することを確認した。通常登録の「繰り返しで期限を延ばさない」契約は維持する。

`todo retry-sooner <id> --after 60 --reason "確認した状態変化"` はプレビューだけを返す。
その `state_sha256` を同じ引数の `--apply --expected-state-sha256 <hash>` へ渡す。
通常のToDoロック内で、台帳の実パス、元の行全体、プロジェクトと依存の現状態を比較する。
行の仕様・メモ・担当世代・担当・待機が変化した場合や、別の台帳の確認結果は拒否する。

保存は有効な `retry-time` の将来の期限を早めるだけ。新しい時刻は60〜86400秒後で、
既存期限より前でなければならない。旧理由・開始時刻とその他の待機情報を保持し、
`wait_ready.recheck` に確認時刻、旧期限、状態変化の理由、照合したハッシュを残す。
仕様、メモ、進捗、依存、担当所有、再開世代は変更しない。

本人停止・延期、未回答の質問、別の再開条件、不明または未完の依存は拒否する。
プレビューと保存の失敗で台帳を書き換えない。保存失敗は通常の原子的な保存のエラーとする。
既存の毎分処理が実時刻到達後に元のToDoを通常割当へ戻す。
期限の短縮は実回復、レビューの受入、製品作業の完了を意味しない。
新しい監視処理・キュー設定・モデル設定・質問は追加しない。

受入は `cc-todo/tests/retry_sooner.rs` と既存 `ready.rs`、利用側の待機・割当テストで確認する。
元3669への適用は配布後の状態を読み直し、同じ旧技術待機かつ全依存完了の場合に限る。
