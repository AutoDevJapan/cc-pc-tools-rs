# Discordの質問だけで画像を見て回答できるようにする（ToDo3082）

画像付きの質問は、質問スレッドに本文・背景・画像・選択肢を直接置く。
進捗は別の通知なしスレッドへ記録する。UIの実装承認は本人回答を待つ。

## 受入条件

1. 通常の `ask --attach` が正規のGo会話処理から既存の送信処理へ届く。
2. 元画像の現在の保護判定、出所、サイズ、形式、SHAと送信バイト列の照合を維持する。
   未確認の画像を全体設定で許可しない。コピーで保護判定を回避しない。
3. 質問の開始メッセージに画像を添付する。長い質問の続きも質問側に置く。
   メンションは最初だけとし、進捗と関連リンクは通知しない。
4. 添付を含む同じ入力を固定し、結果を失った場合は同じ質問を回復する。
   画像の欠落・変更時は送信成功や質問待ちを記録しない。
5. 画像なしの質問、報告、本人返信の配送、判断世代と重複抑止を維持する。
6. 関連Go/Rust検査、別モデルレビュー、CI、マージ、限定配布を確認する。
   正規に送信可能な画像を1件だけ実Discordの質問側で読み返す。
7. 同じ正規生成証拠を持つ将来の画像を、コードへの画像別追加や再配布なしで利用できる。
   目的別の登録・検証は通常のguard分類を変更せず、未知・偽造・別用途を拒否する。

## 仕様と根拠

- 元ToDo3082の本人依頼と有限作業仕様。並行3081のモデル処理へは触れない。
- [Discord: forum thread creation](https://docs.discord.com/developers/resources/channel#start-thread-in-forum-or-media-channel)
- [Discord: uploading files](https://docs.discord.com/developers/reference#uploading-files)

## 最初のRed/Green

`go test -p 2 -parallel 2 -run '^TestConversationCLIAskAttachments$' -count=1 .`
をunattended-runnerで実行。変更前はaskのattachが不正引数となり失敗。
attachの解析と配送後は成功。これはCLIの確認であり実送信は別の受入とする。

Rustでも通常CLIの添付拒否と質問開始メッセージの画像0枚をRedとして確認し、
接続後に質問側の画像・長文・選択肢が揃う検査が成功した。
画像の送信結果が欠落した場合の待機抑止、同じ添付での自動再試行、
変更された画像の拒否、旧質問の配置を変更しない再試行も確認する。

## 実添付の対象変更

本人の全体再設計の追加指示により、旧局所UI案へのa/b質問は投稿しない。
実添付は新しい具体的な設計質問を対象とし、元画像・作成したツールの実行記録・
SHA・サイズ・対象ToDoと判断範囲を照合してから少数だけ送る。
出所確認が未完了ならその送信を保留し、未知画像の一律許可を追加しない。

当初の候補はToDo3084のA-v3/B-v2だった。本人のOperations現UI維持の決定で質問は撤回済み。
元画像は用途資格の検査記録として保持し、質問へ再投稿しない。実行記録と生成記録を固定照合し、
元パス・画像SHA/サイズと、本文・decision・元ToDo・本人・質問forumを結び付ける。
用途付き資格は通常のclient分類と独立し、元の未分類結果は残す。
候補Go実行物で両方の実証拠の照合に成功。正式配布と実質問側の添付は別に確認する。

画像別の固定値をコードから外し、[通常の証拠登録](generated-question-evidence.md)へ移す。
原tool応答のPNGバイト列と原ファイルの一致、原生成sessionのユーザー依頼と元ToDoの一致も確認する。
資格データはWindowsユーザーに結び付けた鍵で署名し、送信直前にも原証拠を再検証する。

Opus 5.5/maxの固定92b182レビューで、送信結果を失った後の元画像依存をMustとして受領。
原画像削除後のGET回復と初回アップロード前のSHA相違拒否をそれぞれRed→Greenで確認した。
Windows CIで短縮TEMPが再現した画像テストは、合成入力の物理パスを正規化して関連raceで確認。

## 専任担当への依頼文を照合する（2026-10-21）

ToDo3135から、正規に生成したSystems画像の通常証拠確認が拒否される報告を受けた。
元セッションの最初の実ユーザー依頼が「本人の最新依頼を実行する専任担当。」から始まる。
旧検証器は先頭のToDo番号だけを認識するため、この定型の導入文を1回だけ除いて照合する。
直後の最初の行を依頼の見出しとし、引用外にToDo番号を1個だけ明記した書式に対応する。
本文の別の行・引用・コードから番号を探さず、複数の番号や繰り返した導入文は拒否する。
最初の実ユーザー依頼・原記録のSHA・元ToDo・画像全バイト・質問scopeの照合は維持する。
後続の依頼、別ToDo、引用、未知の導入文、導入文の繰り返しは拒否する。

登録と用途資格の回帰検査で、既存書式と定型導入文の書式を受け入れ、上記の不一致を拒否する。
実画像の通常checkでも確認する。ほかの拒否条件があれば原証拠を保持して原因を分ける。
その後、実送信対象はToDo3145の専用セッションで新規生成した画像1枚へ切り替わった。
最初の実ユーザー依頼の「ToDo番号」表記を同じ元番号へ照合する（Issue311）。
ToDo3135の旧画像・原依頼・原rolloutを書き換えて実送信へ流用しない。
質問は3145担当が本人指定の09:00 JST以降に1回だけ送る。この修復からは送信しない。
