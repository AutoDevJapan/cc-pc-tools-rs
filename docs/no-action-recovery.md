# 報告だけが続く担当の復旧（ToDo2827）

既存の1分巡回のstep / repair-stepが、正規のguardで源repoと作業場所を確認できる現在の実装担当を調べる。
製品名で対象を決めず、既存のguardが拒否する資源や本人判断用owner項目は対象にしない。
作業種別はimplementationと、実測例の元2783に保存されていたci_fixに限る。
新しい常駐処理・定期タスク・本人への再開質問は作らない。一般のkill_enabledは変更しない。
status / recoverはこの取消を実行しない。

## 検出

源repoと同じGit管理領域、登録された作業場所・ブランチ、scrub391の対象外判定を確認する。
本人停止、判断待ち、依存・能力・資源待ち、review/research、read-only、要約中の担当を除外する。
PIDと生誕、担当・起動世代を照合する。コントローラー以外の子処理がある間は回収しない。

events.jsonlは1担当につき最大1MiB・512イベント、1行256KiBで増分読み取りする。
型付きデコードでtype・itemのtype/id/statusだけを使用し、本文・コマンド・引数・結果は保持しない。
保存するのはファイルID、cursor、PID生誕と起動時刻、進行中toolのID、件数・観測時刻だけ。
担当との照合票にはパス等のメタ情報のSHA256だけを使う。
一度の巡回は順番を保存して最大2担当を読み、取消は最大1件。
一巡の上限IDも保存し、新しい担当が続けて増えても既存担当への折り返しを遅らせない。
追加観測は5秒までで打ち切り、源repo/作業場所の確認は各1秒、取消コマンドは最大8秒。
既存の呼び出し元の20秒枠を保ち、評価や通知を取消の必須経路に入れない。
評価は既存のrefresh、所有タブの回収は既存の巡回が引き継ぐ。

command_execution / file_change / mcp_tool_call / web_searchの開始・更新・終了は実操作として扱う。
進行中toolは時間にかかわらず保護する。最後の実操作から30分以上経過し、完全に読み終えた
観測にagent_message完了が3件以上ある場合だけ候補にする。agent_messageは操作時刻を更新しない。
初回・読み取り失敗・file交換・起動世代変更は新しい観測期間から始める。末尾未完・未読の
残りがあれば取消しない。壊れた行・切詰め・未対応tool・委譲イベントはその起動中の証拠を無効にする。
これらを操作ゼロとして扱わない。委譲先の完了を本文から推測しない。

## 取消と再開

既存のcancel --recovery --if-todo-readyに--no-action-checkを渡す。
既存yield予約とqueue→job state→ToDoのロック順を守る。追加のロック待ちはqueueが最大2秒、
job/ToDoは非待機。通常の取消や質問のCASは変えない。
既存のidle controller停止処理で稼働中の子を排除し、コントローラーを一時停止して
パイプの残りを有限に排出する。イベントを再読し、実操作・未完・世代の変更があれば戻す。
異常終了時の再開印も既存yield-pausedを使う。本文を記録しない。
ToDoロック下で現担当、世代、本人停止、新しい依存、源repo/作業場所を再照合して取消意図を保存する。
後から登録された待ちは後続の起動を止める。取消は既存の生誕確認済みプロセスツリー処理を使う。
終了が確認できたときだけ、同じToDoを同じworktreeへ再予約する。ファイルはreset・削除しない。

モデルの明示指定、effort、sandbox、MCP、network、追加ディレクトリを保持する。
自動選択だった実装担当は既存の実装用モデル設定を使い、通常のOAuth枠・健康確認・能力ゲートに通す。
新しいAPIキーや有料契約は使わない。
取消失敗の再試行は最初だけ既存の短い待機、その後は既存の技術backoffへ移す。
同じ停止で短い待機を使うのは最初の1回だけで、2回目以降は1時間待つ。
担当再開後に再び止まった場合も既存retry_countに従って待つ。本人判断blockには変えない。
取消の技術失敗だけでは独立した他作業のdispatchを止めない。

## 検査

cc-job-policyのaction_progress、cc-jobsのno_action、cc-schedulerのno_action_testsで
本文が更新され続ける停止、進行中tool、読み取り不能・壊れ・末尾未完・置換・切詰め、
本人停止・依存・別担当/世代・readonly、重複取消とbackoffを確かめる。
cc-jobsの実fixtureは専用storeと無害なプロセスだけを使い、観測時刻だけを仮想化する。
実取消→生誕の異なる/存在しない終了→同じToDo・同じ作業場所への同じ起動キーによる1回再開、
途中成果の保持まで確認する。実ユーザーの担当は検査用に止めない。
