# 容量計測から有限の削除候補判定へ接続する

元ToDo3085。既存の3時間計測と1時間清掃を維持する。計測だけの成功と、候補判定・回収・本人判断を区別する。

## 入力と出力

既存3時間処理が新しく生成した匿名の計測結果を、通常の共有ToDo CLIへ渡す。古い保護済みのログやcheckpointを候補判定担当へ読ませない。有限の判定担当は常に通常schedulerの資源枠を通り、直接起動しない。同じ識別子を持つ項目は1件だけにする。未完、実行中、依存待ち、本人回答待ちは保持し、完了した項目だけ次の新しい計測世代で再利用する。

初期受入インターフェースは `todo capacity-cycle --report-file <新規匿名結果> --spec <有限指示> --project <登録済み名>`。入力失敗や状態矛盾はキューを変更せず終了する。既存の元ToDo・所有権・質問は上書きしない。

`todo capacity-status` は今回の接続が新規生成した匿名の計測世代・判定行・結果だけを返す。旧保護ログ/checkpointを読む必要はない。未実施の判定結果はnull。状態確認では保存先を書き換えない。`capacity-result`で世代の一致する集計を記録するまで、その判定行を通常CLIでdoneにできない。

## 受入条件

1. 部分走査3・保護未分類4の結果を受けても、未調査をゼロ候補や全調査済みと扱わない。判定項目は通常待ち列へ1件だけ入る。
2. 同じ世代の再送と、未完中の次世代入力は項目数・実担当・本人待機を増やさない。再試行は同じ項目へ収束する。
3. 完了後の新世代は同じ項目を再使用し、古い履歴を保持する。停止・依存・本人判断待ちを自動解除しない。
4. 判定結果は、未調査、候補、保持理由、実回収量、保管確認、必要質問の作成/送信/回答反映を分けて記録する。未確認はnull/unknownで表し、捏造しない。
5. 判定担当は現在の適格資源だけを対象に、実所有者・終了・不要・削除範囲を確認する。Windowsの移動/削除は絶対パスと内包、既存所有証明を先に確認する。未知領域や失われた保護原本を推定して許可しない。
6. 元1時間清掃のroot/削除判定、監視taskの件数、3時間/1時間間隔を変えない。質問は本人だけが決める具体的な対象に限り既存経路で1問ずつ送る。

## 検証

隔離した共有ToDo保存先でCLIの実結果を検査し、変更前のunsupported commandをRedとして保持する。Greenでは1件再利用、待機保持、異常入力、世代順序、実行中の収束を確認する。変更範囲のGo/Rust検査、Claude5.5/maxの別モデルレビュー、固定HEAD CI/マージ、既存exeのSHA256を照合した限定CAS配布、既存taskからの新しい結果と通常schedulerの実接続を確認する。
