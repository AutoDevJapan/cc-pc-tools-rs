# Codexジョブの起動と順番待ち

Rust製の `codex_jobs.exe` が、複数の呼び出し元から届くジョブを共通の順番待ちに入れます。同時に動く親は初期設定で6件です。実行中の親から起動した子は親の枠を使い、各親につき同時2件まで起動します。起動できる子を親より優先し、その中でオーナーの直接依頼（`req-`）、PRを仕上げる担当（`shep-`）、その他の順に起動します。同じ順位では待機開始が古いものを先にします。子の枠が埋まった親があっても、別の親の子は起動できます。

同じ順位以上の親が順番待ちしている場合、連続2時間以上動いた親はコマンドやツールの `item.completed` の後、次の `item.started` の前にCodexを停止し、同じ順位の最後へ戻ります。ジョブID・ToDo・作業フォルダ・セッションと元の依頼文を保ち、次の起動には `exec resume` を使います。待機者がいない場合、子・孫が実行中または順番待ちの場合は譲りません。失敗・取り消し・セッション未記録・完了や判断待ちの作業は再開しません。

ツール完了後も長いコマンドが裏で動くことがあるため、実際のプロセスも確認します。CargoやCiv6の処理、その枠を持つ処理、別のCodexが残っている間は終了を待ちます。起動時からあるMCPサーバーは停止と再開の対象にできますが、その後に起動した実処理は待ちます。PIDと作成時刻で本人・親子を照合します。進行を一時停止してイベントの保存を待ち、次の項目が始まっていないことを再確認してから停止します。停止時には共有資源を持つ処理が終わり、枠が返っている必要があります。

更新前から動く親も、更新済みの待機プロセスがこの境界で停止し、新版の監督へ引き継ぎます。新版の監督はツール完了時と、終了が遅れた背景の処理を待つ間に自分で確認します。配備時はexeを差し替えて `reload-queue` を実行します。Civ6の実機試験やCargoの途中で実行中の親を一斉に止める操作は不要です。

停止前に `yield-transition.json` へ同じセッションの再開記録を保存し、停止・保存・監督の起動に失敗した場合は同じジョブで再試行します。未確定の引き継ぎを失敗として通知せず、まだ生きる子孫があれば枠を保持します。一時停止した担当が終了した場合は `yield-paused.json` を使って進行を再開します。同じ秒の受付にも順序番号を使い、譲った親が待機者を追い越すことを防ぎます。旧型のターン終了予約はv0の互換処理だけに限ります。

親のIDは環境変数 `CC_JOB_ID` から取得して `parent_job_id` に保存します。別の起動元が明示するときは `run --parent-job-id <ID>` を使います。明示した親は同じキューで実行中である必要があります。環境変数の親が終了していれば警告を出し、独立した親として順番待ちに入れます。孫以降も最上位の親の枠に属し、直接の親ごとに子の上限を適用します。親が終了しても子が動いている間は親の枠を保持します。祖先の記録が読めなければ、そのIDで枠を保持し、他の親の起動判定を続けます。

設定は実行ファイルと同じフォルダの `queue-config.json` に置きます。配布先は `D:/CC/Tools/codex-jobs/` です。ファイルがなければ下記の値を使い、次の起動判定で変更を読み直します。0件の上限や不正な設定はエラーにします。

```json
{
  "max_running": 6,
  "max_children_per_parent": 2,
  "max_429_retries": 5,
  "retry_delay_seconds": 60,
  "max_retry_delay_seconds": 900
}
```

待機中は `status` の表示が「順番待ち」になります。JSONの `status` は既存の監視ツールが読む `queued` を維持します。待機中の監督プロセスはCodexを起動せず、3秒ごとに空きを確認します。待機中も `cancel <ジョブID>` で取り消せます。起動枠の確保と登録にはOSのファイルロックを使い、終了したプロセスのPIDが再利用されても別のプロセスを止めません。過去のジョブは共有索引で30秒ごとに照合し、各待機プロセスが毎回すべての履歴を読むことを避けます。

待機中も監督プロセスが60秒ごとに生存記録を更新し、既存の停滞監視が再開し直すことを防ぎます。実行ファイルを更新して待機中の監督プロセスへ反映するときは `codex_jobs.exe reload-queue` を使います。実行中のCodexは停止せず、順番・セッション・ToDoの担当を維持します。

429で失敗したときは同じジョブの同じセッションを使い、60・120・240・480・900秒後に再試行します。待つ間は起動枠を空けます。再試行は最大5回です。セッションが記録されていないときは新しいセッションを勝手に作らず、失敗を記録します。待機中は終了通知を送りません。子プロセスが生き残っている場合は枠を消費したままにします。

終了済みの429ジョブを復旧するには、最初に対象を確認します。

```powershell
codex_jobs.exe recover-429 --since 2026-10-06T17:00:00+09:00
codex_jobs.exe recover-429 --since 2026-10-06T17:00:00+09:00 --apply
```

`--apply` を付けた場合だけ復旧します。`events.jsonl` の最終イベントを確認し、ToDo・同じセッション・後続の担当と照合します。完了済みや判断待ち、後続の担当があるものは除きます。同じジョブIDを使うため、ToDoとの関連を維持します。新規受付も同じToDoやセッションの二重起動を拒否します。ToDoファイルを変更する場合は `--todo-file <path>` を指定します。

一度このコマンドで復旧したジョブを停滞監視が取り消していた場合も、同じ検査をして再開できます。オーナーが直接取り消したジョブは再開しません。

親IDの記録がない古い子は、実行中の親の `events.jsonl` にある成功した起動コマンドと、その出力のジョブIDから関連付けます。同じIDを複数の親が起動した記録は採用しません。指定時刻以降に取り消され、一度も開始していない子は同じIDで再起動できます。後続の担当があるものや、親が終了したものは除きます。これは指定時刻以降の子の復旧を明示的に依頼されたときに使う管理コマンドです。取り消し理由を自動判別する機能ではありません。待機中の古い子を関連付ける際は、その監督プロセスも新版へ起動し直します。

配備は実行ファイルの差し替え、`reload-queue`、`max_running` を6へ復帰、対象の確認と復旧の順で行います。実行中の処理を途中で止めず、ツールが完了した境界で新版の監督へ引き継ぎます。旧版も読める設定項目を維持します。`max_children_per_parent` は旧版が不正なキーとして拒否するため、それらが終了するまでは本番設定に追加せず、新版の初期値2を使います。

```powershell
codex_jobs.exe recover-children --since 2026-10-06T21:00:00+09:00
codex_jobs.exe recover-children --since 2026-10-06T21:00:00+09:00 --apply
codex_jobs.exe reload-queue
```

検証: `cargo test --manifest-path cc-jobs/Cargo.toml`。既存の互換性検査に加え、6件の親が枠を埋めても子を起動して完了できること、兄弟12件の同時判定で2件までに収まること、孫と親終了後の枠保持、親IDの取得、旧記録の復旧と再実行を確認します。外部のCodexや通知APIは偽物に置き換えて検査します。
