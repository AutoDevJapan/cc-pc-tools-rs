# 再開担当と元の質問を結ぶ（ToDo3751）

質問のdecision.todo_id、本文、題名、元スレッド、normal-ask要求IDは元作業のまま保持する。
通常askのscheduler-item/jobは送信の識別に混ぜず、現在の担当を確認する入力として渡す。

今回の受付は元1171と有限担当3277だけ。正規current-product-successionの元3638/実装3650、
登録project/root、元仕様と担当仕様のSHA、実jobと作業場所を照合する。
元のrecovery_unverifiedを変更せず、別製品・別原質問・本人停止を許可しない。

送信側の原質問とAPI証拠は1171を保持する。回答配送先だけを3277として別に保存する。
担当の質問待ちには原質問のfingerprintを共有する担当用の受領情報を作り、正規ToDo CLIを使う。
原質問の受領情報も保持し、担当用の情報を原APIのtodo_idだったとは扱わない。
既存の依存待ちは上書きしない。送信済みでも待機登録は保留と明示する。
依存待ち中の回答全文は比較付きのメモと次の指示文の原子的な更新で同担当へ届け、依存・所有・状態を変えない。
元rowのsnapshotと両仕様は正規ToDo CLIのロック内でも再照合する。
編集回答は同じ回答の古いブロックを指示文から置き換え、メモの履歴は保持する。
依存解除後、未回答なら同じ質問への待機だけを登録する。本人の回答は再質問しない。

固定の失敗段階だけをCLIへ返す。本文、引数、トークン、生の下位エラーは出さない。
busy、入力不一致、元作業の範囲、再開担当の資格、送信・証拠確認・待機登録を区別する。

受入: 同じ元質問の再試行が一つの投稿に戻り、元rowを保持すること。
無関係actor、別project、仕様hash差、本人停止を拒否すること。
元の依存と担当を保持し、返信全文を正しい有限担当へ一度だけ届けること。
Rustの橋渡し、Goの会話処理、実ToDo CLIの関連テストと別モデルレビュー、CIで確認する。
Stripe操作とGit道本体の受入はこの修復に含めない。
