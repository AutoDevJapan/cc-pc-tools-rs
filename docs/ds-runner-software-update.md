# Task runner software maintenance

The software reader can consume one reviewed Task runner capture. The authenticated API owner, repository, exact producer files, run attempt, job, publication marker, artifact archive and three attested subjects must agree. The fixed application includes the complete 185-file module inventory. The PE digest, Windows/amd64 build information and input/source-proof digests are checked before a private candidate is issued.

The expected capture tuple is the third formal run (generation 3) and its exact artifact and subject digests. The first and second formal runs (generations 1 and 2) are retired: their hosted artifacts expired, their tuples are kept only as a record, and every consumer rejects them, including a tuple that reuses one of their run, job, check run, artifact, archive or attestation identities. A new capture may carry the same output digest, which does not retire it: every generation so far built the same executable from the same fixed source, so all three share one output digest. These constants alone do not issue a candidate: the normal constructor still checks the authenticated metadata, original payload and full cryptographic proof. A JSON report, a matching caller-supplied hash, a path or a fixture does not issue this candidate.

The input-free maintenance commands are:

- --verify-ds-runner-capture: authenticate and verify the real capture without opening the installed target or any stage/backup. This separates actual archive/signature acceptance from installer qualification.
- --verify-ds-runner-update: authenticate the candidate and inspect the compiled predecessor without creating a file.
- --prepare-ds-runner-update: retain the original executable as a fixed backup and create the fixed stage with exact ACL and byte readback. Existing conflicting leaves remain intact.
- --apply-ds-runner-update: repeat the checks, use the native replacement operation and inspect the installed generation, ACL and payload again. Previously prepared leaves are re-read under a fresh candidate; an earlier report is not an apply permit.

The normal caller starts the same helper through its owned child mechanism. The internal worker requires the inherited pipe and actual OS parent check. A successful caller result also requires the child to be reaped, exit zero and return exactly one canonical record. Short output writes and partial constructor/close failures cannot produce a successful result. When an owned child exits zero or one, the caller accepts its record only after both stdout and stderr reach EOF without overflow or read failure, the process has been waited and reaped, stderr is empty, and the canonical record matches the operation state. A valid exit-one result keeps its confirmed commit and cleanup facts, adds the caller’s reaped observation, and still exits one. If complete collection or the state cannot be established, the result is worker_outcome_unknown. Any other child end, including a timeout, an exit code above one, stderr output or a malformed or inconsistent record, is reported as worker_outcome_unknown, and an apply run then carries commit_attempted=true with commit_outcome=unknown.

Only the compiled Task runner target, stage and backup are software-maintenance inputs. Target access begins with metadata and READ_CONTROL. Body handles are opened after the private artifact and maintenance-purpose checks. Current identity, parent identity, ACL and bytes are compared again at each use. Partial files and unexpected collisions are retained for reconciliation; there is no deletion fallback.

The Windows replacement operation is not a compare-exchange by file ID. The cooperative maintenance mutex is owned on a pinned OS thread. It does not prove quiescence against arbitrary same-user namespace changes. ReplaceFile requires the stage body handle to close immediately before its exclusive open; that interval is a specific review and acceptance limit, not a proven immutable lease. After a confirmed replacement, the reader holds the same candidate body without write sharing and checks its identity, bytes, parent, owner and group before any DACL restoration. It skips that write when the complete original owner/group/DACL string already matches. A different owner or group, changed body or identity, unavailable rights or cancellation fails closed. When the DACL differs, the fixed original DACL is restored on the held stage object and the exact descriptor and bytes are checked again. This does not close the interval between releasing the staged body for ReplaceFile and acquiring the new body, or prove an atomic namespace lease. A failed replacement or postcheck is recorded rather than silently retried. ReplaceFile is called without a backup argument, and its documentation says that a failure to rename the replacement can leave the replaced file no longer present under its original name, so no result claims the target is unchanged. The commit_outcome field has four values: not_attempted (a recheck or the release of the staged body handle stopped the publish before the native call), confirmed (the call reported success), unconfirmed (the call was made and reported failure; the namespace was not re-observed) and unknown (written only by the caller when no trustworthy worker record was observed). commit_attempted and update_performed are derived from it and must agree with it. The original backup remains available. Creation time is expected to follow the predecessor while the installed file ID follows the stage.

After the installed program is independently qualified, the original --inspect-task-question-source command remains the metadata-only route. Its normal fixed Task provider and per-input guards validate the original Task and the original body/decision/image tuple. The expected flags are --todo-id, --cwd, --body-file, --decision-file, --attach, --body-sha256, --decision-sha256 and --image-sha256. This route does not register an image, post a question or prove that the Task belongs to a repository. Those are separate operations and evidence.

The maintenance result is an observation, never a source, Task-data, media or sending permission. Software replacement and installed readback are separate fields so a committed operation followed by a failed postcheck cannot be reported as either verified success or proven no-change. Close failures of metadata and body handles, the maintenance mutex and server response bodies are kept as cleanup_failed together with the primary failure, from the artifact and server checks through the target session to the caller. A handle whose close failed is not known to be closed: the target session keeps it referenced, never closes or reopens it again and reports it on every close, the first one included; nothing is deleted. A security descriptor whose release failed while a fixed leaf was being created with its exact ACL is handled the same way: the created leaf and the cleanup failure stay together with any primary failure, the release is not retried, and every close reports it.

The new synthetic and owned-file tests must run on Windows before acceptance. They cover candidate cancellation/panic/close ownership, critical API fields, request/body cleanup, prepare recovery, conflicting leaves, generation changes, commit/readback separation, outcome classification, forwarding of failure facts and unknown observations through real owned children, cleanup facts, normal caller output and metadata-handle data-access denial. Source preparation alone is not runtime success.

## Failure reasons

A failed maintenance record may carry failure_reason. It exists so that the first real runs are not blind. It is a diagnostic fact, not an authority: no success, admission, update or retry decision depends on its value, and a qualified record never carries one. The value is one token from a fixed vocabulary that names the stage that stopped and, for a server answer, its numeric HTTP status. It never contains a URL, response text, credential, path or raw error. A typed error produces it; an error whose text merely looks like a reason does not. The worker's record is accepted only if its reason is in the vocabulary, only in a record that is not qualified, and a capture record accepts no target reason. A record that fails this check is not forwarded: the caller reports worker_outcome_unknown, which is never a success. The publish step of apply adds no token of its own: a failed publish is described by the reason (commit_outcome_requires_reconciliation) and by commit_outcome.

The stage tokens have the form ds_runner_<phase>_<kind>. The phases are owner, repository, workflow, run, jobs, artifacts, producer_compare, producer_file, source_commit, source_tree, job_log, job_log_object, artifact, artifact_object, archive, attestation, trust_root, signature and recheck. A run reports the first stage that fails; the stages are reached in this order: the credential steps, owner, producer_compare, producer_file, source_commit, source_tree, repository, workflow, run, jobs, artifacts, job_log, job_log_object, artifact, artifact_object, archive, attestation, trust_root, signature and recheck. The kinds are unavailable (no usable answer: the request was refused or failed, or its body could not be read or closed), malformed (the answer lacks a required field or repeats a key), too_large, paginated (a Link header), mismatch (the answer does not match the pin), expired (the artifact is listed as expired) and absent (the pinned artifact is not in the run's artifact list; GitHub removes an expired artifact from it). A server answer other than 200 is ds_runner_<phase>_http_<status>. The credential steps are ds_runner_credential_not_found, ds_runner_credential_access_denied and ds_runner_credential_unavailable; ds_runner_owner_mismatch means the authenticated owner is not the fixed owner. ds_runner_capture_not_bound means the compiled pin is not usable, ds_runner_cancelled and ds_runner_deadline_exceeded name the end of the run's own context, which is reported whichever stage saw it. The installed-target steps, only for verify, prepare and apply, are ds_runner_target_open_failed, ds_runner_target_read_failed, ds_runner_target_snapshot_invalid, ds_runner_target_predecessor_mismatch, ds_runner_target_changed, ds_runner_target_backup_failed, ds_runner_target_stage_failed, ds_runner_target_leaf_mismatch, ds_runner_target_postcheck_failed and ds_runner_target_postcheck_mismatch. A leaf collision keeps its own result reason and gains no second one.

When the caller has no trustworthy worker record it writes worker_outcome_unknown and may add one of ds_runner_worker_not_started, ds_runner_worker_timed_out, ds_runner_worker_not_confirmed, ds_runner_worker_exit_other, ds_runner_worker_output_incomplete or ds_runner_worker_record_invalid. These tokens are outside the worker vocabulary, so a worker record cannot claim them.

The fixed evidence flow is also reachable through a package-private opener parameter (openDSRunnerCandidateWith). It exists so that owned tests can run the same constructor against synthetic server data; the normal entry passes only the owner-credential opener and the compiled pin, and no caller input chooses either. openNormalDSRunnerCandidate is the only caller outside tests. Another caller would need a reviewed source change, and the seam skips no check: the pin is validated before any request, and the archive, executable, signature, trusted-root, log and subject checks run in the same order.
