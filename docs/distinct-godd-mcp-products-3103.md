# GoDD MCPとGoDD MCP αの識別を分離する

ToDo3103。本人の2026-10-20訂正を仕様の根拠とする。
対象は管理ツールの製品カタログ、部署、実行順位、読み取りAPIの帰属だけ。
UI、CSS、配置、顧客側のソース・環境・PR・保護設定は変更しない。
画面全体の方向はToDo3084が保持する。

## 入力と照合

|固定製品ID|正式名|GitHub repository ID|照合したowner ID|部署|順位|
|---|---|---|---|---|---|
|godd-mcp-contract|GoDD MCP|1156778979|133784601|受託部|10|
|godd-mcp-alpha|GoDD MCP α|1154066087|246834983|GoDD事業部|60|

2026-10-20に通常のGitHub OAuth読み取りで2つの数値組を再照合した。
所有者の名前や顧客の一覧は保存しない。IDの対応は現在確認した所有に限り、
リポジトリ移管などで所有が変わった場合は未確認として扱う。

作業に`product_identity`があれば、`product_id`、`repository_id`、`owner_id`を
照合する。固定IDは省略可能だが、指定された各値の矛盾、未確認の所有、
不正な型を名前の照合で救済しない。`repository_id`と`repository_owner_id`は
明示した事業上の対象がないときだけ使うコードリポジトリの識別とする。
事業上の対象はコードの作業場所とは独立に記録できる。

強い識別がない旧記録は本人が指定した完全な製品名・既知の別名だけで関連付ける。
その場合、記録の製品分類とGitHub所有確認の有無を分ける。
GoDD MCPをαの省略形として扱わない。GoDD/MCPの部分一致や自由文から帰属させない。
他製品の既存名、部署、順位は保つ。

## 受入条件

1. 2つのrepository IDは別の固定製品ID・部署・順位を返す。共有のコード作業場所や
   登録プロジェクトより、検証済みの事業上の対象を優先する。
2. αを省略した入力はαへ合流しない。曖昧な派生名・別所有者・不完全な識別は
   unknownを保持し、他方の正式名が付いていても救済しない。
3. 受託製品は順位10、自社αは60。依存関係の既存の順位引き継ぎは維持する。
4. αのCIジョブと受託のToDoに相反する関連があっても、αの結果・実行状態を
   受託側へ載せない。2641/2737/3093のα作業を受託に結ばない。
5. 同じジョブが複数ToDoに記録されても、現在実行中のジョブは1回だけ帰属する。
   ToDoの記録と各ToDo自身の進捗は削除・合算しない。
6. 現在の担当が確認できない製品はunobservedとする。CCジョブが0件でも
   未観測のネイティブセッションを停止中と断定しない。
7. 保護中のメタデータAPIと通常APIは同じ識別規則を使う。原保護を解除せず、
   顧客の自由文や作業場所、秘密値をAPIに追加しない。

## 原因と検査

既存カタログにはαだけが登録され、受託製品が欠落していた。
順位はGoDDから始まる名称を一般のGoDD順位へ分類していた。
APIの帰属は名前と作業場所が中心で、同じジョブを複数ToDoへ関連付けられた。
固定製品IDとrepository/ownerの照合を共有し、識別と観測の根拠をAPIへ加える。

回帰検査を先に保存し、Cargo資源を割り当てた有限の検査ToDoでRedを実測してから
実装する。変更したクレートと利用側を選び、Green、doctest、別モデルレビュー、
CI、merge、配布、実API読戻しを別々に記録する。未実行を成功と書かない。
