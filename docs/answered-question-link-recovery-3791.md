# 回答を反映した質問と、結果が未確認のリンク投稿を分ける

## 確認した問題

質問本文と別の通知なし進捗投稿が正規APIで確認でき、本人が回答し、
担当が作業を実行しても、後続のリンク投稿だけが送信結果未確認になる場合がある。
送信側の `question-links` が `pending` のままなので、同じ入力を再実行しても
`RecoveryMessagePending` が返る。上位の会話受付も `reserved` のままになる。

2026-10-25、元3080のGoビルドキャッシュ整理でこの状態を確認した。
キャッシュ整理は元の担当が一度実行し、終了コード0、時間切れなし、標準エラー0だった。
Cドライブの空きは28,286,996,480 Bから41,160,892,416 Bへ増えた。
差分12,873,895,936 Bは他の処理も動く間の観測値であり、独立した回収量の証明ではない。

受付3791は元質問・現在の未編集回答・本人・対象範囲を正規APIで照合した。
元担当の実行記録と事前確認のハッシュも照合し、削除を繰り返していない。
原質問、回答、私的な識別情報、実行記録は元の保存先に保持し、この文書へ転載しない。

## 修復で満たす条件

1. 元の質問本文全体、本人、質問世代、進捗投稿、元ToDo、現在の回答版を確認する。
   `pending` や短い回答だけを承認・実行・配送成功の根拠にしない。
2. 実行済みの成果、担当の実ジョブ、具体的な検証結果を原記録へ結び付ける。
   元作業の所有・未完了・停止・依存を変更せず、キャッシュ整理を再実行しない。
3. 未確定のPOSTを再送せず、元の送信記録を保持する。リンクの未確認と、
   質問本文の配送・本人回答・作業の実行・質問の終了を区別する。
4. 正規の受付と送信側の両方で、現在の回答版の反映を検証して終了できるようにする。
   索引や台帳の手編集、成功票の捏造、旧質問の再送を修復手順にしない。
5. 質問の終了はPATCH後のGETと再照合で確認する。追加回答・編集・別の本人・
   別の対象・未反映の回答・本文の未配送は、成功や終了と扱わない。
6. 通常の完全配送を維持し、一般の保護分類、原台帳、通知条件を変更しない。
   元3080全体の完了、別のレビューやCIの成功まで推定しない。

## 現時点の到達点

元のキャッシュ整理と受付3791による独立確認は済んでいる。
リンク投稿の正規な復旧と質問の終了は未完了であり、修復の実行・関連テスト・
別モデルレビュー・CI・マージ・既存実行版への反映・実質問の終了確認を必要とする。
通常のソフトウェア修復として追い、本人へ同じ判断やPC操作を求めない。

## 正規の回復手順（Issue #492）

送信側のread-onlyな回答照会は、質問の全分割と通知なし進捗を再GETし、
`question_delivery_verified` と `auxiliary_links_unconfirmed` を別々に返す。
`DeliveryVerified` は追加せず、完全配送の従来条件を保つ。

Goの `conversation recover-answered` は、明示した質問・回答・元受付・現在の担当を
保存済み入力、正規API、実ジョブと元の起動指示へ照合する。現在の未編集回答が
1件だけで、未確認が補助リンクだけなら専用の回復段階へ進む。この段階は反映・
終了成功ではなく、元の待機要求、所有、停止、依存を保持し、自動配送は行わない。
続いて通常の `source-link`、`source-verify`、`implementation-record` で元資料を保持した
現在版の実反映を記録し、`close` が新しい回答や編集も再確認してPATCH後GETを行う。
反映記録が無い場合は終了できない。未確定の補助POSTは再送しない。
