# 依存完了後の同じ有限作業を継続する

元3669の追加受入。3719の古いquota実行はresume世代2・依存世代0、
現在の依頼は世代3・1であり、古いquota capsuleを拒否する検査は正しい。
現在の依頼から新しい契約を作る通常の受付を追加する。

現在の実親だけが、同じ登録specのSHA・source・両世代を指定して継続を登録する。
登録は起動や復旧成功ではない。元source・原返信・親edge・worktree・停止・
依存・待機期限・資源・モデル指定を変更しない。古いquota証明の世代は修正しない。
通常schedulerの準備、jobs登録、最終キュー受付で同じ現在の契約を確認する。
reviewの通常のモデル選択と作者除外は維持し、researchの指定へreview用回答を流用しない。

受入条件:

- 現在の正当な依頼・実親・保存spec・同じsource/所有/世代/範囲・排出・新鮮な
  既存OAuth利用可を確認し、同じresearchをSol/maxで起動する。
- 偽造、別source/owner、古い世代、spec/範囲変更、排出未確認、未完依存、停止、
  未確認/枯渇OAuth、API鍵だけの経路や費用増を拒否する。
- 通常review既定、別モデル、有限な再試行予算を保つ。
- 関連検査、別セッションのレビューとラバーダック、最終headのCI、通常merge、
  Windowsの正規更新・読戻し、3719のnativeモデル/effortと親の正規受領を別々に確認する。

PR454の完了と今回の追加受入は別である。今回の実受入はまだ未実施。

## 受付と実行

`todo continue-subwork` は、呼出元の `CC_JOB_ID` と指定した親jobが同じで、
実processと現在の親所有が照合できた場合だけ、現在の依頼の指紋を保存する。
元の親edgeは登録時のまま残す。sourceのresume/依存世代がともに現在より古く、
同じspecの実行を有限契約で証明できる場合に限る。現在の停止や未完依存は解除しない。

親3080が実行する入力例（各値が現在も一致することが前提）:

```powershell
todo.exe continue-subwork 3719 --source-job 20261026-180903-todo-3719 --parent-job-id $env:CC_JOB_ID --resume-generation 3 --dependency-generation 1 --spec-sha256 4f6fe32f62db56bed2acb4d378147ff952ad06230243fb45f7674f3158313fc3
```

別担当の環境変数を親のjobへ書き換えて実行しない。受付は起動しないため、
その後の通常schedulerが優先順・待機期限・資源・所有を再検査する。
準備時は通常のreview既定またはresearch指定を選び、現在のOAuth利用可を確認し、
新しいlaunch keyとscopeへ結ぶ。jobsは登録時と最終受付時に元sourceと現在の世代・
spec・停止・依存・scope・健康情報を再照合する。再試行回数と履歴も引き継ぐ。
OpenAIは利用可能と照合した公開namespaceを今回の契約にだけ結び、
集約値で別の枠が利用可だったことを、実際に選んだ枠の証明にしない。
通常のアカウント設定、モデル既定、課金設定は変更しない。
新workerへ移せるのは次の1世代だけで、後の継続はそのworker自身の結果を使う。
保持した元の依頼を、何度でも使えるquota例外にはしない。

健康情報を再取得する間は共有キューのロックを取らない。検査不能は既存の有限な
metadata再検査へ戻し、期限が来ただけでは復旧と判定しない。
登録specの原文と新workerの原返信を既存のreader/ACK手順で親が受け取るまでは、
3719の継続作業を完了と報告しない。旧8486Bの不一致記録は証拠に流用しない。

## ラバーダック4164の指摘への修正

元の92cdb785に対するLuna/maxの正式レビューで、呼出元の偽装と旧v1の再試行予算について
Must2件を受領した。別の生存プロセスを親として環境変数を合わせる反例と、未復元の
v1 capsuleを持つsourceの反例が、修正前にいずれも失敗した（Red 4d50740f）。

受付CLI自身が、作成時刻を照合した実親のプロセスツリーに属することを確認する。
環境変数や親プロセスの生存だけでは受け付けない。旧v1のsourceは、既存の正規処理で
復元した使用済みの切替回数と履歴が揃う場合だけ継承する。今回の世代から旧capsuleの
前任を検証できない未復元sourceは拒否し、回数を0で補わず、原sourceも書き換えない。
復元済みv1の正例は登録・Start・最終キューを通し、切替回数を消した負例は拒否する。

修正後の関連62テストと4クレートall-targets Clippyは成功した。最終コミットに対する
両別セッションの再確認、正式CI、配布と3719の実受入は引き続き別に確認する。

## 親世代の最終再確認

0509dcf0に対するセルフレビュー4163は先の2件を解消済みと確認したうえで、受付後の
親世代の更新を最終queueが検出しないMust1件を返した。同じ版のラバーダック4172は
修正指摘0であり、この結果の違いを保持する。

Red 711ae07cでCLI・scheduler・最終queueの3反例を確認した。親の現在の担当と
worker receipt、親ジョブ自身の世代、親ToDoの世代を一つの共通処理で照合し、
親世代を要求とactorの指紋にも含める。受付だけの重複した親確認は取り除いた。
親の終了だけで世代を更新したことにはせず、同じ現担当の終了後も世代が一致する
正例を維持する。要求の受付後に親の担当・世代・receiptが変わった場合は、
scheduler・jobs登録・最終queueが同じ契約を拒否する。
