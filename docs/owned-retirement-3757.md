# 退避した一時データの元所有を清掃へ引き継ぐ

元3628の独立工程、ToDo3757。元3361の有限判定と原保護の復旧2467は別に保持する。

## 入出力と責任

Go safe-deleteは所有・原受領・利用解除と有限な現物照合を担当し、削除しない。
Rust cleanup-8hは既存C/D削除希望の内側だけを既存のハンドル削除で処理する。
通常planの512MiB上限、planを別のexecへ提出してfinishする手順は変更しない。
退避と削除を別の状態・数量で記録し、新しい定期処理は追加しない。

新規createでは元ジョブ・元ToDoと祖先の実体を記録する。読取側は自己チェックサムを
原受領の代用にせず、正規ジョブの成功したcreate出力と一致することを確認する。
旧v2も同じ原受領を検証できる場合だけ扱う。欠落や曖昧なコマンドは保持する。
ジョブの作業場所・ToDoのjobsを照合し、caller指定のパスやreceiptを原受領にしない。

元担当は`release`で特定IDの不要・依存なし・保持なし・再生成可を記録する。
同じ元ToDoの実行中の担当だけが記録でき、元の作成出力、現在のToDo/仕様、
Gitの保存・push、リンクのない現物一覧を確認する。解除の原出力も正規ジョブの
成功した単独CLI実行と一致して初めて清掃に使う。解除の自己申告ファイルだけでは
清掃資格にならない。元製品や元ToDo全体の完了とは区別する。

`cleanup-lease --path`は正規の退避先から元IDを引き、元create/release/quarantineの
原出力、現在のジョブ・ToDo、保持条件、元場所の不在、同じvolume/file ID、祖先と
全項目の安定を照合する。退避先索引は検索の手掛かりだけで、証明には使わない。
一般guardのclearを元場所・元root・退避先・payloadごとに必要とする。
リンク、外部hardlink、別ドライブ、差替え、期限・件数超過、読取失敗は保持する。

資格確認からfinishまで元IDのOSロックを保持する有限な子プロセスを使う。
Rustは子の一覧と各ハンドルの実体を照合してpayloadだけを削除し、親フォルダーと
原証拠を残す。成功後に子へfinishを返し、元receiptを`quarantine_removed`にする。
失敗・部分削除・子の終了時は自動的に再登録せず、残物とcanonical receiptを保持する。
既存の1h清掃のrun lockも維持する。通常の退避物を資格失敗時に汎用削除へ戻さない。

## 受入テスト

- 架空create→原出力→release→原出力→quarantine→原出力→候補→別process削除→finish。
- 改変receipt、原出力欠落、偽のecho/複合コマンド、不明/違うToDo、保持/依存あり、
  dirty/unpushedソース、稼働資源、再生成不可、壊れたJSON、旧v2の情報不足を保持。
- 祖先junction、payload内link、外部hardlink、volume/file ID差替え、元場所の再出現、
  別ドライブ、全一覧変化、ロック競合、期限/件数超過を保持。
- 容量は候補の論理bytes・実際に削除したbytes・Windows空きの前後を分ける。
  既存のguard、保持名、E既存データ、一般清掃・ごみ箱の境界を維持する。
