# 進行中の元ToDoへ古い質問の回答を届ける

元3110から分離した配送修復。既存の新会話に保存済みの回答だけを扱い、
製品の実装、質問の再送、保護分類の変更、担当の起動は行わない。

## 再現と境界

新会話の質問待ちを保存した後、本人の新しい直接指示で元ToDoが次の世代へ進むと、
古い待機は残っていてもstatusはdoingになり得る。現行Goはblock以外を拒否するため、
正規APIで取得・保存した回答が元ToDoへ通常配送されない。

通常の質問待ち解除と、進行中の作業への回答の配送を分ける。
配送だけでは回答の実反映・製品完成を意味しない。

## 入出力と不変条件

`todo question-answer --delivery-only --answer-file ... --delivery-note-file ...
--expected-state-file ...` を既存CLIへ追加する。

- Goが正規APIの現在の質問・本人・回答・編集版と保存元を照合し、元プロジェクトの
  正確なrootを既存guardで確認する。未知・保護対象は本文を展開せず保留する。
- Rustはtodo.lockの同じ区間で現在の全行とexpected-stateを比較する。
  検証済みの元waitが現存し、answerの質問世代・本人・SHAが完全に一致し、
  元waitに保存された世代より現在の世代が進んだtodo/doingだけを配送対象にする。
  世代の欠落を推測しない。別の質問・停止・未完依存・完了・未知状態は拒否する。
- 保護確認と書き込みの間で対象が変わらないよう、Goは同じ読み取りから元行と
  登録project/pathを取り、確認したprojectとpathのSHAを`--scope-file`へ渡す。
  edit、質問待ち、回答、取り下げは、Rustが同じToDoロック内で現在の登録と照合する。
  editは`--expected-state-file`の元行全体も比較する。scopeのSHAは本人性や保護判定の
  代わりにはせず、既存guardを省略しない。本文は保護判定の後に展開する。
  Rustの元行snapshotはcanonical storeと同じ64MiBを上限とし、1MiBを超える履歴も
  比較する。質問/回答のenvelope・メモ・理由の既存入力上限は変更しない。
- メモは現在の原文を完全な接頭辞として保つ追記だけを認める。回答と元質問の私的参照、
  元ToDo・取得時刻・本人・thread/message・現在版SHAを担当へ渡す。
  新しい直接指示を優先し、古いaを新しい許可として解釈しない。
- 担当終了時に通常のメモが置き換わっても次の担当へ届くよう、同じロック内で
  既存の`owner_instruction`を保って回答参照を追記し、引き継ぎ本文のSHAを記録する。
  時刻だけの再試行期限は保存したまま配送し、期限を解除しない。
- 独立した`owner_question_delivery_receipts`へ元wait、answer、入力bytesのSHA、
  配送先の現在世代/担当、比較した元行のSHA、配送日時とメモ/引き継ぎ本文のSHAを保存する。
  status、元wait、仕様、履歴、作業場所、branch、担当、依存、権限を変更しない。
- 同じ回答版の再試行は変更なし。編集された版は別の配送記録にし、古い配送や実反映の
  記録を新しい版へ流用しない。正常な待機解除は元の担当/世代も照合する。
- 配送直後のGo保存が失敗した場合は、その版のcanonical配送記録から受領を回復する。
  通常の待機解除/imported経路も、同じ版の回答記録から受領だけを回復する。
  後からメモや引き継ぎが変わっていても、古い参照や停止理由を再作成・解除しない。
- 質問待ちへの各返信は、2通目以降も編集前に版別のreadyファイルを保存する。
  再取得で取得日時/受領SHAだけが変わった場合は、保存済みの元envelope/bytesを
  配送・回答記録か、回答済みの質問に残る現在のメモの版別目印と照合して受領だけを回復する。
  他の項目が違う場合や配送の根拠が残っていない場合は保留し、古い参照を追記しない。
  メモ追記だけの未完了配送は、元待機と担当が一致する場合だけ保存済み入力で正常回答を
  再実行し、回答記録を確認する。新しい停止は同ロックの判定で保持する。
- 取得状態が失われても既存の受領ファイルを照合して復旧し、同版の原bytesを上書きしない。
  通常取り込みが先に同じ会話の取得待ち・ToDo未割当を作った場合も同じ復旧へ通す。
  この版のメモ入力をまだ作っていない受領は初回の配送を許可し、過去の配送試行の有無を
  本文と編集時刻の版別目印で区別する。旧版のメモ入力だけでは編集後の回答を保留しない。
  旧版の再取得で原受領を置換済みの部分配送は、元回答の配送と実反映を分け、
  現在の受領SHAと締め/反映が未確認の理由を通常の受領状態へ保持する。
  回答処理の応答喪失や取得状態の再喪失でも、保存済み入力と現在の受領元が異なるなら、
  配送済みへ戻すすべての経路で同じ未確認理由を保存する。
  作成時刻がPCの現在時刻より後なら、受領ファイルを作る前に次の巡回へ保留する。
- 継続配送ではGoが同じ版の配送記録を読み返してから元ToDoとdeliveredを記録する。
  通常の待機解除/imported経路の初回配送ではメモと回答記録を読み返す。
  保存、配送、実担当の実読、実反映、配布を別々に確認する。

## 受入検査

1. Given 元waitと進んだ世代のdoing行、When 現在版回答を通常配送する、Then
   元メモを保持し同じToDoに回答が届く。世代/担当/状態/元waitは完全に保持する。
2. Given 同じ配送の応答喪失、When 再試行する、Then 重複記録も別の停止解除も起きない。
3. 元行CAS差、質問/本人/元回答SHA差、世代欠落/逆行、別の待機・明示停止・未完依存、
   保護判定失敗では元状態を保持する。編集回答には新しい版の配送が必要になる。
4. 実Rust CLIと隔離したGo受入検査でreadbackまで検証する。実担当の反映は偽造しない。
5. 担当への引き継ぎと未来の再試行期限を保持して配送でき、メモの置換と通常の
   担当交代でも参照が消えない。世代違いは旧経路のメモ編集より前に保留する。
   無関係なToDoの不明な世代値で、元ToDoの読み取り全体を失敗させない。

変更したcc-todoと公開APIの利用側、およびunattended-runnerの関連race/vetと実CLI結合を
選んで実行する。別モデルmaxレビュー、同じheadのCI、正常merge後の既存配布と
実API受信→保存→元ToDo配送を確認する。未確認の保護対象は個別の有限再試行へ保持する。
history reader、JSON reader/Windows publisher、画像sender/資格、PR279には並行修正しない。
