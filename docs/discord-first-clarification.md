# 初回から元質問へ説明を送る仕様（ToDo3259）

対応Issue: [#356](https://github.com/AutoDevJapan/cc-pc-tools-rs/issues/356)。

## 目的と現在の段階

本人が既存の質問について説明を求めたとき、通常の
`post --clarification-file <JSON>` から最初の説明を送れるようにする。
この文書は初回送信・初回check-onlyの受入仕様である。
候補の検査、正式マージ、配布、実送信の段階はIssueとPRの検証記録で区別する。

通常postを先に失敗させて予約を作る手順は追加しない。
原質問・本人回答・元ToDo・待機・停止・依存・元の判断範囲を保持する。
説明の送信を、元の判断への回答・承認・課金変更へ変換しない。

## 入力と同一性

既存の `discord-question-clarification-v1` と
`purpose: explain_original_question` を使う。既存の必須項目、未知項目・重複キーの
拒否、本文正規化、通常log ID・送信側ID・fingerprintの計算は維持する。
用途JSONを通常log IDの計算へ加えない。

新しい説明でも、元の独立したquestion:0受領記録を必須とする。
正規GETで、設定済み本人、認証bot、設定済み投稿先、元質問の本文・指紋・元ToDo、
説明を求めた本人返信の本文・作成日時・現在の編集版を照合する。
返信は説明・理由・費用の必要性を尋ねるものとして検証し、一般のa/b回答だけを
説明要求として扱わない。照合対象の私的ID・費用・原文は公開資料やfixtureへ入れない。

同じ本人返信は1つの固定説明にだけ結ぶ。別ID・別本文・別質問への結び直し、
原入力の編集、既存Pending/Posted/Verifiedへ照合JSONを後付けする操作は拒否する。

## check-only

通常CLI、Go conversation、Rust recoveryの各入口は、予約が存在しなくても確認できる。
元の入力ファイルから読んだ本文・用途JSONを検証し、正規GETだけを実行する。
新しい本文コピー・JSONコピー・原入力・bot記録・用途記録・送信予約を作らない。
結果は従来どおり `check_only: true, delivery: not_sent` とする。

確認の成功は送信権限を固定しない。実送信では同じ条件を改めて照合する。
既存予約がある場合はその原入力と完全一致しなければ失敗する。

## 最初の実送信

1. 保存や予約に先立って、元質問・本人・用途・現在の返信版・固定説明を検証する。
2. 成功後だけ、通常入口の原入力とGoのimmutable入力を従来の同一性で保存する。
3. Rustの同じメッセージ排他内で現在版を再照合し、固定用途・原入力を結び付ける。
4. 既存のPending/POST/Posted/GET/Verified契約で送信・照合する。

各層で無効な入力と判明した場合は、その層の新しい入力・予約を作らない。
先行層の検証後に本人が編集した場合は、下流の再検証でPOSTを止める。
既に検証済みのimmutable入力は書き換えず、現在版不一致の理由を保持する。
外部Discord上の編集をGETとPOSTの間まで原子的に固定できるとは主張しない。
各未予約部分を送る直前まで、可能な最新GETで本人返信を照合する。

GET成功後の別プロセス実行・再実行・応答消失も、同じ固定IDと排他で扱う。
既存PendingはGETによる回収だけを行い、応答が不明なPOSTを繰り返さない。
全部分が既に予約済みなら、本人の後の編集はGETだけによる回収を妨げない。
未予約部分が残るなら、現在版を再検証してからその部分を予約する。

## 投稿の制約

説明は同じ元質問へ、通知なし・本文メンションなし・返信pingなし・添付なしで送る。
新質問や新しい選択肢を含めない。質問を通常logの進捗先へ昇格しない。
旧台帳・共有設定・保護方針・契約・課金・新常駐を変更しない。
新方式が無効なら失敗し、旧送信へ切り替えない。

## 受入検査

| 条件 | 観測する結果 |
|---|---|
| log要求が未作成、元質問と本人返信が一致 | 初回check-only成功、GETのみ、全保存先が不変 |
| 同じ未作成要求を初めて実送信 | 正しい本文が元質問へ1件届き、同じ指紋のimmutable入力と用途を保存 |
| 元質問受領・本文・指紋・ToDo・bot・本人・返信版・用途・投稿先が不一致 | 原入力・用途記録・Pendingを作らずPOSTしない |
| 通常CLI確認後またはGo確認後に本文・JSONが変化 | 固定入力との不一致を拒否し、新しい本文へ置き換えない |
| check-only後または未予約部分の送信前に本人が編集 | 現在版不一致でPOSTを止める |
| 初回送信の並行実行と再実行 | 同じ要求・本人返信へ結び、二重POSTしない |
| POST応答消失またはPosted後のGET失敗 | 既存Pending/PostedをGETで回収し、POSTを再実行しない |
| 複数部分の一部だけ予約済み | 既存部分はGET回収、未予約部分は現在版を再照合 |
| 別ID・別本文・別質問・同じ本人返信の流用 | 結び直しを拒否、原入力・原用途を保持 |
| 既存未送信log予約 | 同じID・本文・投稿先で再開できる |
| 既存送信予約へ用途JSONを初めて指定 | 後付けを拒否 |
| 通知・メンション・返信ping・添付・新質問・選択肢・通常進捗 | 送信を拒否し、元質問を進捗先にしない |

Rustの通常入口とrecovery、Go conversation、およびRustの公開入口関数を呼ぶテスト実行物と
Goの保存処理を結ぶ検査を対象にする。
失敗の再現を実装より先に確認し、修正後に同じ条件と関連利用側を検査する。
別モデルmaxの固定base/headレビューと必要CIの成功後に通常マージする。
配布は並行変更を含む最新mainと既存実行物のsource/hashを照合して行う。

## 依存と実運用の完了条件

配送修復PR #315は同じGo conversation_storeを変更している。
その通常マージを確認するまで、共通Go/Rustの実装・配布を重ねない。
元ToDo3153全体の完了と、このPRのマージを混同しない。
待機は元3259の有限wait-retryへ保存し、3153全体doneを依存条件にしない。
既知の追加レビューだけが前提ならそのToDoを `wait --on` で待ち、レビュー終了後に
PR #315の通常マージを改めて確認する。実装前の受入テストは、配送修復が変更する
ファイルと別のファイルで準備できる。

## 実装前の再現範囲

`cc-ask/tests/clarification_first.rs` は通常Rust入口からGo runnerへの境界、
`unattended-runner/conversation_first_clarification_test.go` はGoからRust senderへの境界で、
未予約の確認・初回送信・検証拒否時のファイル不変を各3件で検査する。
両方とも送信側を置き換えた架空データであり、本人性やDiscord実配達の成功を証明しない。
修正後はRust sender本体でも元question:0・本人・現在版・競合・応答消失・部分回収を検査する。
`unattended-runner/conversation_bridge_integration_test.go` は実際のRustテスト実行物を起動し、
Rustの公開入口関数と実際のGo CLI・conversationLogInner・保存処理を通す。
Goのrunner loader・設定と状態の初期値・Discord senderを架空データへ置き換える。
CRLF本文の初回送信後の再実行と、既存未送信予約からの再開を確認する。
実行時は `CLARIFICATION_RUST_TEST_EXE` に同sourceから生成した `clarification_first` の実行物を明示し、
Goの `TestClarificationRealRustBridgeCRLFRetryAndExistingGoReservation` を実行する。
Rust側の `real_go_state_bridge_fixture` はこの結合検査の補助であり、単独の呼出しを受入成功に数えない。
通常のRust検査ではignore、Go補助は環境変数がなければskipする。
この結合検査は明示した実行物を使う手動検査であり、現在のCIでは実行せずskipする。
外部Discordの実配達と本番のCLI全段階は、配布後の指定実例で別に確認する。

## 実例への反映

原質問と本人返信を保持する私的証拠を再照合し、指定された新しい問いへの説明を
配布後の通常入口で初回送信する。実Discord GETで本文・投稿者・宛先・通知抑止を
照合するまで完了にしない。予約や受領だけを実配達と呼ばない。
費用・機能・必要性の説明には原質問とサービス公式資料を使い、税務上の認定や
契約の継続・停止を推定しない。旧説明の再送や同じa/bの再質問を行わない。

元3110へ固定base/head、レビューの実model/maxとMust対応、CI、merge、配布SHA、
実説明のmessage/thread、元reply版、通知抑止、元の未完判断を保持した証拠を返す。
保護方針の担当には利用できる仕様・配布実物のsource/hashを渡す。
