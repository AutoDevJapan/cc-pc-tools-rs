# opencodex の応答監視

Rustで、同じWindowsプロセスの `/healthz` が20秒以内に応答しない状態を監視します。3回続いたときだけ、プロセスの実行ファイル・起動時刻・所有記録・ポートの所有者を照合して、そのプロセスハンドルを終了します。PIDファイルがない場合も、`runtime-port.json` のPIDとポートが一致すれば監視を続けます。存在する所有記録が食い違う、不正、読み取れない場合は終了を拒否します。終了直前にも同じ条件を再確認します。応答を返す503、不正な応答、起動後120秒以内のプロセス、意図的に停止しているサービスは終了対象にしません。

通常は既存のサービスが5秒後に再起動します。手動起動でサービスの親が失われていた場合も復旧できるよう、終了後に `opencodex-proxy` の定期タスクを起動します。復旧待ちの間に起動が失敗した場合は、ポートが開いていないことを確認して60秒後に再試行します。ポートが開いているのに所有記録が一致しない場合は、別のサービス起動を重ねません。終了後120秒は次の終了を抑制します。

## 検証・配置

所有記録が両方とも欠落した場合は、設定の `expected_cli` があるときだけ、保持したプロセスハンドルから別の所有確認を行います。同じ利用者のプロセスで、指定された実行ファイルとCLIを使い、起動引数が厳密に `CLI start --port <設定ポート>` の形であることを確認します。プロセスの現在の環境から `OPENCODEX_HOME`、または `USERPROFILE/.opencodex` を確認し、監視の設定先と一致することも要求します。起動記録を作り直したり、インストール履歴 `serving-runtimes.json` で代用したりしません。

この確認はx64 Windowsのプロセス構造に限定し、読み取り失敗・不明な構造・環境の重複キー・相対的な設定先・3秒の読み取り期限を超えた場合は拒否します。現在の環境は不可分なスナップショットではないため、構造の変化を検出し、終了直前に全条件を照合し直します。生の起動コマンドや環境は出力・保存しません。存在する所有記録の不正や矛盾は、この確認で上書きしません。古い設定では `expected_cli` を省略すると従来の記録による確認だけを使います。配布時の設定は配置済みのnpmパッケージのCLIを指定します。

プロセス構造の参照: [Microsoft PEB](https://learn.microsoft.com/en-us/windows/win32/api/winternl/ns-winternl-peb)、[CrashpadのWindowsプロセス構造](https://chromium.googlesource.com/crashpad/crashpad/+/refs/heads/main/util/win/process_structs.h)。

`inspect` は所有確認と健康検査を読み取りだけで実行し、PID・起動時刻・健康状態・検査時間だけを出力します。監視の状態や復旧記録を書かず、稼働中の監視と並行して配置前の確認に使えます。

```powershell
cargo test --locked --manifest-path cc-ocx-watchdog/Cargo.toml
cargo clippy --locked --manifest-path cc-ocx-watchdog/Cargo.toml --all-targets -- -D warnings
cargo build --release --locked --manifest-path cc-ocx-watchdog/Cargo.toml --bin ocx_health_watchdog
```

別モデルのレビューでMustがなくなってから、実行ファイルを `D:/CC/Tools/ocx-health-watchdog/ocx_health_watchdog.exe` に配置します。`install` はログオン時の定期タスク `CC-OcxHealthWatchdog` を登録して起動します。タスクは同一アカウントの権限で動き、1分ごとの起動も登録します。動作中は追加の起動を無視し、監視が終了していた場合に再開します。監視を意図的に止め続けるときはタスクを無効にします。releaseバイナリはWindowsのGUIサブシステムを指定するため、コンソール窓を作りません。子プロセスは `CREATE_NO_WINDOW` で起動します。

`check` は1回だけ検査し、検査結果を保存します。監視が既に動いている場合は多重起動を拒否するので、状態確認には `status.json` を読みます。`watch --config <絶対パス>` では隔離検査用の設定を読み込みます。設定は `Config` の全フィールドを持つJSONです。配布する既定値は20秒・10秒間隔・起動猶予120秒・終了間隔120秒です。

## 記録

同じ配置先の `status.json` に最新の検査結果を保存します。`events.jsonl` は検査失敗・終了意図・終了結果・サービス起動・別プロセスの正常応答を保存します。成功時のメモリとCPU使用時間は1分ごとに記録します。5MiBを超えると直前1世代だけを保持します。

状態表示・イベント記録・導入記録を書けない場合も、健康検査は続けます。5MiBを超えたログを入れ替えられない場合は追記を止め、その記録の失敗を数えます。失敗回数は次に保存できた状態の `observation_write_failures` に記録します。プロセスを終了する前の復旧意図は、引き続き保存に成功することを必須とします。

復旧意図は終了前にディスクへ同期して `restart-pending.json` へ保存します。Windowsが終了要求を受理した場合は、5秒以内に終了を確認できなくても意図と終了間隔を保持します。監視が再起動しても、別プロセスの正常応答を照合して未処理の復旧を引き継ぎます。終了要求を受理した記録がなく、元のプロセスの正常応答を再確認した場合は古い意図を取り消します。報告に失敗した記録は残し、10分間隔で再試行します。繰り返した復旧は1件の文章へまとめ、Discordの「後片付けの記録」へ通知・メンションなしで投稿します。本文・認証情報・アカウント情報を監視記録へ保存しません。

`ocx_watchdog_fixture` は検証専用のRust製サーバーです。指定ポートに健康応答または応答停止を作ります。10100では起動を拒否します。製品のバイナリとして配置しません。

調査の確定事項と未確定事項は [調査記録](INVESTIGATION.md) を参照してください。
