# 混雑したモデルから同じ会話を再開する

`codex_jobs.exe` は子プロセスが終了して最後のイベントを読み終えた後、正規protocolの混雑エラーの場合だけ再開する。
大文字小文字は区別しない。成功・取消・監視処理の起動失敗、tool本文は対象にしない。

2026-10-20の順序は、同じGPTモデル・別OAuth枠を最大3回追加で試し、その後に適格なClaude候補を検討する。
別枠は要求だけに公開account selectorを指定する。全体のアカウントを切り替えない。
5、15、30秒の待機期限を通常の待ち行列へ保存する。帰属や利用枠が不明な場合の15分待機は最大3回。
回数は429の予算と別で、混雑と429が同時に記載されても混雑側の上限を優先する。
対象外モデルや不正な履歴では別名のモデルへ推測で置換せず、429の再試行にも進まない。

セッションIDは有効な `thread_id`、次に保存済みの `resume_session` を使う。
セッションがまだ作られていない失敗では元の本文を使い、不正なIDでは再開しない。
新しいjobを作らず、元の待ち行列へ戻す。プロンプト、作業場所、権限、ToDoの所有情報と文脈を保持する。
同モデルの再試行では元のeffortを保ち、Claude候補にはmaxを明示する。

`job.json`へ同モデルの回数、使用した公開selector、期限と履歴を保存する。
新しい監査項目には生のエラー本文・個人ID・メールを残さない。起動要求とnative turn_context、取得できた上流メタデータを分ける。
元の `events.jsonl` と `stderr.log` は保持し、監視処理を更新しても回数と履歴は保つ。

配布は稼働中のソースとの並行変更を確認し、AdminBrokerで既知の元配備先へ有限CASを行う。
既存の `reload-queue` は子が動いていない監視処理だけを対象にする。
更新前から動いていた担当は元の実行版と起動設定を保つため、配布だけで全担当のeffortが変わったとは報告しない。
