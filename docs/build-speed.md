# Rustのビルドとテストをまとめて進める

このPCでは、異なる生成先のCargoの同時件数をCPU使用率と空きメモリから動的に決める。同じ生成先では1件ずつ実行し、その順番待ちはPCのビルド枠を使わない。CPUが75%未満で空きメモリが16GiB以上なら増枠し、CPUが90%以上か空きメモリが16GiB未満なら新しい受付を待たせる。通常の上限は論理コア数÷4（32コアなら8件）。新しく始めるコマンドの並列数は実行中の件数で分け、通常は1件10並列までにする。詳細は[共有ビルド枠](cargo-gate.md)にまとめる。

Cargoのゲートとジョブの起動環境がsccacheを設定する。実行ファイルは`D:/CC/Tools/sccache/sccache.exe`、キャッシュは`D:/CC/BuildCache/sccache`、上限は30GiB。旧設定とサーバーを混ぜないため、ポート42259を使う。通常の開発ビルドは自作クレートの差分ビルドを有効にし、registryの依存ライブラリをsccacheで再利用する。全件テストではincrementalを無効にし、ライブラリをキャッシュする。各worktreeの生成先は分ける。明示した生成先は維持する。旧共通生成先を環境変数で引き継いだ場合は新方式へ移す。旧共通生成先を意図して使う場合は`--target-dir`かCargo設定で指定し、その保管量の検査と排他処理も維持する。

Cargoの順番待ちを示す生存中のプロセス記録があるジョブは、ジョブの実行枠に数えない。同じ家族の別ジョブが実行中なら、その家族の枠を維持する。死んだプロセスの記録で枠を空けない。ビルド開始時に待ちの記録を消し、再び実行中として数える。

同じジョブで待ちと実行が混在していれば実行枠を維持する。更新前のゲートが残した待ちの記録も、プロセスの作成時刻を照合して扱う。入れ子のCargoが親と違う生成先を要求し、その生成先が使用中なら、相互待ちを防ぐためすぐエラーにする。親の処理が終わってからそのCargoを実行する。

## 検査の回し方

sccache 0.18.0のRust用キーはCargoの環境変数を含むため、ゲートは決定した生成先を`--target-dir`でCargoへ渡し、生成先の環境変数をコンパイラーに引き継がない。生成先と排他の単位はそのまま維持する。registryの依存は別worktreeでも再利用できる。生成コードを含む依存や自作クレートには絶対パスが残るため、すべてのクレートの命中を保証するものではない。根拠は[sccacheのRust用キーの実装](https://github.com/mozilla/sccache/blob/v0.18.0/src/compiler/rust.rs)。

- 作業途中は、変更したクレートと、その変更に依存するクレート・結合テストを選ぶ。例：`cargo nextest run --locked -p cc-jobs`。必要に応じて`--test <名前>`や`-E 'test(名前)'`で絞る。公開APIを変えたら利用側も含める。
- 同じ生成先で、テスト・Clippy・ビルドを一つの順序にまとめる。保存のたびに全workspaceを回したり、同じ検査を別担当から重ねたりしない。
- マージ前も変更の影響範囲を選ぶ。対象のライブラリのdoctestは`cargo test --locked -p <名前> --doc`で確認する。共有設定・依存やテスト選択の変更など全体を確認する必要がある場合だけ、理由と版を残して`cargo nextest run --locked --workspace`と`cargo test --locked --workspace --doc`を行う。Lua・実機などRust以外の受入条件も影響があれば確認する。
- 失敗した場合は原因を直して該当検査を確認する。追加の変更で結果が無効になった範囲だけをやり直し、最終ソースと同じ内容の有効なCI結果は重複して実行しない。
- nextestのテスト並列数もPCの負荷に合わせる。このPCでは1件10並列を使い、外部資源を共有する検査の直列指定は維持する。

2026-10-17の本人指示は、旧「マージ前に全workspaceを必ず1回」の規則を更新する。
小さな変更ごとに独立した全体・releaseビルドを重ねず、関連テストのコンパイルを
再利用する。まとまった変更後や、テスト外の対象の確認・配布に必要なビルドは行う。
詳しい選び方とCIの動作は[変更の影響範囲](test-build-scope.md)を参照する。

全件の実行時間には、テスト実行ファイルのコンパイルも含める。変更前後は同じソース、同じプロファイル、同じ対象で測る。キャッシュが空の初回・変更なし・1ファイル変更・別worktreeへの再利用を分けて記録する。結果は`D:/CC/Reports/build-speed-2026-10-08.md`に保存する。

一次資料：[sccache](https://github.com/mozilla/sccache)、[nextestの配布バイナリ](https://nexte.st/docs/installation/pre-built-binaries/)、[nextestの実行範囲](https://nexte.st/docs/running/)。

## 担当の起動とビルド枠

Cargoが必要なToDoの担当がモデルの順番を待ったりレビューしたりしている時間は、ビルド枠の占有時間に数えない。このPCのスケジューラーは、共有ゲートの設定ファイルをその場で読み、設定上限までの `codex-jobs/cargo-build.lock.N` を確認する。空きがあればCargoが必要な担当を起動できる。確認に使ったロックは直ちに解放する。実ビルドはゲートが生成先と共有枠を取り直すため、負荷に応じた受付と生成先ごとの排他は維持される。

ゲートが未配置の場合は従来の判定を保つ。ゲートを経由したと確認できないcargo/rustcがある場合も待つ。sccacheが起動したrustcの親をたどれない場合は、空き枠があっても一時的に待つ。動的設定と受付記録が無い旧版の配置では、従来どおり3枠を確認する。スケジューラーの観測は受付の予約ではなく、負荷と生成先は実ビルド時にゲートが再確認する。

共有枠の確認が失敗したらCargoを使う担当だけを待たせる。終了したジョブの反映と、Cargoを必要としない作業の起動は続ける。Civ6の割り当て規則は維持する。
