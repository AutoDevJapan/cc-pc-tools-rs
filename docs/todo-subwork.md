# 主担当に必要な独立作業を共有ToDoから起動する

有限な調査・検査・レビューは、主担当の完了を待つ依存関係ではなく `subwork` として登録する。
新しいPRの実装担当を増やすための指定ではない。種類は `research`、`check`、`review` の3つ。

```text
todo.exe add demo "PR86の終了境界を調べる" --spec request.md --subwork-of 880 --parent-job-id <稼働中の主担当> --subwork-kind research
todo.exe add demo "PR86の関連検査" --spec checks.md --needs cargo --subwork-of 880 --parent-job-id <稼働中の主担当> --subwork-kind check
```

別ToDoに登録済みの有限作業は `todo.exe subwork <番号>` に同じ3引数を指定する。
仕様のある未完了項目だけが対象。実行中・順番待ちの担当がある項目には設定できない。
親は別の未完了ToDoの主担当で、履歴に登録され、プロセスの作成時刻まで一致して稼働中でなければならない。
親子のプロジェクトの表示名は異なっていてよいが、実際のリポジトリとGitの共通管理領域は一致させる。
下位作業をさらに親にすることはできない。

保存する `subwork` は、親ToDo、登録時の親ジョブ、種類、親のリポジトリ・Git管理領域・worktree・PRを持つ。
子の作業場所はschedulerが管理する専用worktree。親の作業場所との共有は認めない。
調査とレビューは読み取り専用で実行する。検査も保存済み仕様の範囲だけを扱い、主担当のソースやPRを変更しない。

同じPRの主担当との所有権衝突だけを除外する。別の親や普通の実装担当との衝突は従来どおり待つ。
CPU、RAM、起動間隔、Cargo、Civ6、同じToDoの重複防止、OAuthのキューは通過する必要がある。
独立ToDoは親と別の実行枠を使う。親の枠を使って上限を回避しない。
起動と再開はschedulerが担い、停滞監視から別のConsole受付へ二重に委譲しない。
起動引数の `--subwork-of` と `--assigned-needs` は、保存済み関係・起動識別子・割当と照合する。
準備時の識別子だけでは起動できず、資源確認を通った後にschedulerが保存する受付記録も必要になる。
親がまだ稼働していれば、schedulerが確認した親ジョブを `--parent-job-id` でも渡す。

準備中に仕様・資源・関係・作業場所・状態が変われば古い準備結果を起動しない。
ジョブ登録と実行枠取得でも保存済みの関係を再確認する。
親が終了・消失したら親の指定を外して通常の実行枠で続ける。
同じToDoとworktreeの主担当が再開したら、確認できた新しい担当へ関連付ける。
親ToDo自体が消えたり、保存した関係が変わったりした場合は起動せず確認待ちになる。

親が子の結果を必要とする場合は、親から子への `todo.exe wait` を使える。
子から親への完了待ちは、間接的な待機も含めて拒否する。

## 既存の誤分類だけを修復する

```text
todo.exe subwork 2193 --subwork-of 880 --parent-job-id 20261010-010432-todo-880 --subwork-kind research --repair-owner-wait
```

`--repair-owner-wait` は既存の `work_owner_job` と指定された担当が一致し、その親ToDoが `wait_on` にある場合だけ使える。
終了済みの親の記録も照合できるが、稼働中の親に対する例外や親の実行枠は与えない。
指定した親への誤待ちだけを取り除き、別の依存待ち、本人による停止、仕様、履歴、worktree、進捗を保持する。
親の状態や依存関係を変更しない。次の通常の受付で資源と担当を確認する。

配備対象は `todo.exe`、`scheduler.exe`、`codex_jobs.exe`。共有ポリシーを組み込む関連実行ファイルも現行の配備元と照合する。
更新は既存実行ファイルを退避して置き換える。実行中の担当を終了しない。
既存の順番待ち監視には通常の `reload-queue` を使う。設定ファイルは変更しない。
