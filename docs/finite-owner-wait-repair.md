# 終了した親を待つ有限作業の修復

親が子の結果を待っている一方、未開始の子のジョブ記録だけに親の所有権待ちが残る場合を扱う。
通常の `subwork` 登録が使える場合は、そちらを優先する。

この修復は下位作業の資格や実行枠を与えない。終了した親への自動待機を一つ取り除き、
既存の通常受付へ戻す。別の作者、資源、手動依存、本人停止は引き続き受付を止める。
共有ToDo、原仕様、原ジョブID、作業場所、モデル、実行権限を変更しない。

```text
codex_jobs.exe repair-owner-wait --request-file request.json
codex_jobs.exe repair-owner-wait --request-file request.json --apply
codex_jobs.exe reload-queue --job-id <同じ子のジョブID>
```

要求には `job_id`、`owner_job_id`、`todo_id`、`parent_todo_id`、`kind`（research/check/review）、
`child_spec_sha256`、`parent_spec_sha256`、`prompt_sha256` を指定する。
ハッシュは保存済みの両仕様と子の原 `prompt.md` の正確なバイト列を指す。
操作者は原仕様を読み、独立した有限作業であることを確認して種類を指定する。
題名やPR番号だけから有限作業と推定しない。

プレビューも適用も既存のキュー、両ジョブの状態、共有ToDoの順にロックする。
子の監督プロセスは作成時刻まで照合し、子の実処理と親のプロセスは終了を確認する。
親の正常終了、親から子への結果待ち、両ToDoの原担当履歴、同一リポジトリとGit管理領域、
別々の専用worktreeと保存ブランチ、自動待機の原所有根拠が一致する場合に限る。
子から親への手動依存は間接的でも拒否する。

適用は原待機と根拠、要求、親の終了・待機状態を `work_wait_history` へ残す。
別の待機は保持する。状態が変わった再実行は再検証で拒否するため、応答が失われた場合は
同じジョブの履歴を確認してから次工程へ進む。

適用や監督の更新は実行開始を意味しない。元ジョブの開始時刻、元の作業場所、
実際のツール処理を確認する。レビュー完了・CI成功・製品完成もそれぞれ区別する。
