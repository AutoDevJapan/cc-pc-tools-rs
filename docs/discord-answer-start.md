# Discordの回答後に担当を再開する

ToDo #2161では、旧セッションが別の作業に使われていても、承認済みの回答から作業を続けられるようにした。ジョブの受付と、Codexが入力を受け取って実行を始めたことを分けて記録する。

- `answer_receipts[].launch_job` は起動先の予約。順番待ち中は他の窓口・担当へ同じ回答を渡さない。
- `handled_by` と `launch_confirmed` は実開始を確認した記録。実行ステップ、ターンの開始イベント、ターン完了、または最終結果を根拠にする。セッションの作成だけでは確認しない。
- 予約先が入力を受け取る前に終了した場合、回答を再開可能な状態へ戻す。古い `handled_by` も同じ証拠で移行する。実開始の確認済み記録と、CLIで回答を読んだ証拠は保持する。
- 予約先の記録を読めない場合は予約を解除しない。死んだwriterの推測による削除は行わない。
- 同じセッションの占有と、同じToDo・Discord依頼の担当は別に調べる。別作業が占有していれば旧セッションを再開せず、元の指示・回答・作業場所を独立セッションへ引き継ぐ。同じ作業の担当があれば重複起動を防ぐ。
- 既存ToDoとの関連を保存し、実開始後に担当を記録する。回答より後の判断待ちは上書きしない。起動の試行番号は従来どおり保存し、受付結果を取り逃しても同じジョブを回収する。
- 別担当が成功しただけでは回答を渡したと扱わない。実開始と、その回答が入力に含まれる証拠を確認する。

回帰検査は `cc-ask/tests/resume.rs` の、別作業によるセッション占有、起動前の予約、古い記録の移行、起動直後の失敗、記録の読み取り失敗、同じ作業への引き継ぎ、開始イベントの各ケース。既存の返信・依頼受付・追加指示・ロックの検査も維持する。

実行ファイルを更新する際は、原本の並行変更を照合して統合し、検査した内容をreleaseビルドする。既存の配置手順で定期タスクを一時停止し、状態ファイルを保持して実行ファイルを交換する。再開は `CC-DiscordAskTick` から行い、配置先のハッシュと定期タスクの結果を確認する。
