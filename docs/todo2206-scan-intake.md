# 履歴走査と新受付の分離（ToDo2206）

履歴3132件を読む間、新受付30件が同じ走査ロックを待ち、60秒で失敗した。PR76は長い走査をキューのロックから外したが、受付の前に走査の完了を待つ構造は残っていた。今回、受付の保存と実行前の照合を分離する。

## 保存と実行

- 新受付は短いキューの排他区間で、ジョブ、連番、索引への登録を保存する。履歴の走査ロックは取得しない。
- 索引が未完成でも登録したIDと所有者情報を保持する。登録処理が部分索引を完成扱いにしたり、走査中の登録を削除したりすることはない。
- 監督側が履歴を照合する。走査中なら別の監督は待たず、受付済みのジョブを待機状態に保つ。
- 実行の直前は完成した索引から記録を読み直し、プロセスの作成時刻、ToDo・関連ToDo・セッション、既存の作業所有者と実行枠を確認する。
- 発見済みの重複は受付で拒否する。未照合の古い担当は履歴照合後、実行前に検出して待機させる。古い記録が完了扱いでも、その担当の子プロセスが生きていれば所有権を保持する。
- 読めないジョブの索引には、ToDo、関連ToDo、セッションなどの所有情報を残す。PIDが再利用され、作成時刻が変わった場合は生存扱いにしない。

新しい受付キーは、恒久的なキーのロックを `create_new` で初めて作った担当だけが履歴検索を省く。別担当が先に排他を取得した場合や保存途中の停止には、開始記録と原子的な受領記録で対応する。ロックの1バイトは読まない。受領記録からIDとジョブのキーを照合して返すため、完了したジョブの再送も同じIDになる。旧版のキーで受領記録がない場合は、過去履歴を一度検索して移行する。

## 再現と計測

元の統合検査は517fb92で130.939秒、1受付成功・29失敗。失敗は走査ロックの60000ms超過だった。当時の保持者は記録されていないため、過去のPIDと工程の時間は確定していない。

旧受付を維持した比較用コピーに、同じ条件の回帰検査と診断を適用した。検査が走査ロックを保持すると、30件全てが60000msの待ち超過で失敗した。保持者はPID79432、工程は `fixture:history_scan:blocked`。受付工程は64.204秒、検査全体は103.390秒。履歴件数、同時受付数、ロックの60秒上限は変更していない。

修正後はロックを保持したまま30件が3.663秒で受付成功。解放後、3163件の読み込みは38.537秒、索引確定は72ms、走査全体は38.638秒だった。通常の同時受付も30件が3.605秒で成功し、3149件の読み込み44.541秒と確定15msが別工程になった。走査のディレクトリ取得時期により、新受付が読み込み件数に含まれる。

走査の保持者、開始、列挙、記録の読み込みと件数、確定を記録する。工程の計測結果は `.queue-scan-metrics.json` に保存する。これは診断用で、保存失敗によって受付や照合の結果を変更しない。
