# 履歴プロトコルと現在の回収処理

履歴の読み取りでは、返答を受け取ってから次の要求を送ります。
各要求の実際のパイプ書込みが成功したことを記録し、最後の返答を確認するまで標準入力を閉じません。
返答が書込み完了より先に届いた場合は保留し、その書込みが失敗したら結果を利用しません。

## 今回接続した範囲

PR744の履歴プロトコルを、現在のプロセス回収処理へ接続しました。
履歴用の有限な要求列を受け取った場合は、既存のstrict回収を必ず使います。
通常の呼び出し側が回収方式を省略しても、この条件は外れません。

返答を利用するには、次をすべて確認します。

- 各要求のパイプ書込みが完了し、対応するIDの返答を最後まで受信している。
- 標準出力と標準エラー出力の読み取りが終わっている。
- ルートプロセスの終了を確認できている。
- 保持した全プロセスの終了を確認し、Jobの総数と一致している。
- 起動前に保持したルートのPIDと生成時刻が、同じ結果に残っている。
- Jobのハンドルと、launcher・tokenの後始末が失敗していない。

要求を書き終える前にパイプが閉じた場合や、回収数が不明な場合は、返答がそろっていても利用しません。
launcherまたはtokenの終了処理に失敗した場合は、残りの終了処理も試み、返却予定の応答を消去して固定のエラーを返します。
この失敗をJobの回収結果と取り違えません。
件数は既存の最終照会から取り出し、失敗を成功へ変えるための追加照会には使いません。
ハンドルの後始末が終わった後の結果に件数を添えるため、途中で確認できた数値だけが残っても、回収済みという意味にはなりません。

## 現在の接続状況

今回の変更は、既存の履歴処理を現在のAPIで扱えるようにするものです。
通常の操作入口の履歴providerと、元の2件を示す識別情報は、まだ接続していません。
履歴から完了済みのturnを見つけても、元の入力・応答を読む権限や、インストールする権限は作りません。

元の2件の評価には、正常なproviderが発行した出所と、保持した入力・応答の一致を別に確認する必要があります。
この確認ができるまでは、保護された本文を開かず、新しい生成もしません。

## テスト

返答待ち、最後の返答後のEOF、通知、取消、不正な返答、出力上限を検査します。
未送信の要求への予測応答、途中・最後のパイプ書込み失敗、書込みと応答の競合、launcher・tokenのClose失敗も対象です。
回収数が不明な場合や、ルートの生成時刻が違う場合は、結果を利用しないことを確認します。

検査結果はコミットごとに確認します。
最新の対象コミットと結果は、[PR759のChecks](https://github.com/AutoDevJapan/cc-pc-tools-rs/pull/759/checks)から確認できます。

[コミット0be68e1](https://github.com/AutoDevJapan/cc-pc-tools-rs/commit/0be68e1379a67bc1765d42367d6e2ee71b960468)の[Windows CI](https://github.com/AutoDevJapan/cc-pc-tools-rs/actions/runs/43766793539/job/132973672866)では、対象のテスト関数50件のうち49件がPASS、1件がSKIPとなり、サブケース137件がPASSしました。
これは当該コミットの検査記録です。

SKIPは`TestUnslopNormalHistoryMetadataTransport`です。
このテストは、許可済みの検査用スレッドIDを`UNSLOP_HISTORY_TEST_THREAD`に指定した場合だけ実行します。
IDを指定していないCIでは、実際の履歴取得を行わずSKIPします。
この結果には、実環境との接続確認と、履歴処理全体のrace検査は含まれていません。

## 失敗が重なった場合

起動の有無、ルートの終了確認、Jobの回収、通信、終了コード、資源の後始末を別々に記録します。
通信と後始末が両方失敗しても、起動したJobの回収を確認できなかった事実は消しません。
起動していない処理を、回収できなかったJobとは扱いません。

ファイルを開く途中で失敗した場合も、取得済みハンドルの終了をすべて試みます。
終了を確認できなかった資源は参照を保持し、固定の失敗情報で返します。
呼出し側の通常の確認結果には、元のパスやエラー本文を含めません。

要求と応答が正常に完了した子が終了コード3を返した場合は、通信障害へ置き換えず、その終了コードを保持します。

固定の`history`欄には、起動・終了・回収件数・通信・後始末の結果を分けて返します。
回収件数は同じ処理の最終照会に基づく値で、別の処理から補いません。
Closeに失敗したハンドルは強い参照で保持しますが、それをClose成功やJob回収成功とは扱いません。
既存の関数の戻り値とエラー照合は保ち、履歴providerが未接続の従来応答には新しい欄を追加しません。

負例テストでは、同じ子が初期化、要求の部分読み取り、予測応答、標準入力のCloseまで進んだ記録と、実際の書込み失敗を要求します。
起動準備で失敗しただけの結果は、この検査の成功には含めません。

## 標準入力の所有とClose失敗

履歴処理の標準入力は、同じ取得処理が作ったパイプを使います。
親側で書込みとCloseを管理し、それぞれの結果を子の終了コードとは別に残します。
そのため、子が異常終了しても、標準入力のClose失敗が終了コードの陰に隠れません。
書込みやCloseが終わっていない場合も、成功にはしません。

ファイルをCloseする前に、元のハンドルとファイルの識別情報を所有者に保持します。
Go側のファイルがClose失敗後に無効になっても、この情報は残ります。
失敗した生のハンドル値を自動で再Closeすることはありません。

guard確認の前後で取消しが起きた場合は、取消しとして返します。
まだ起動していない子を、回収できなかった子とは扱いません。

履歴用パイプの書込み・Closeは親が個別に確認します。Closeが未完了なら元の所有者を保持して失敗として返し、後から成功したと推測しません。
