# 元の修復作業の起動登録を戻す

本人から再開を指示された既存の修復作業が `todo` / `dispatchable=false` のままで、通常の `dispatch-one` の対象に入らない場合に使う。作業を作り直さず、起動登録のフラグだけを戻す。

`scheduler resume-registration --id <ID> --request-file <JSON>` で現在の状態を確認し、返された `state_sha256` を `--apply --expected-state-sha256 <SHA256>` に渡す。JSONには同じ `todo_id`、`intent: resume_registration_only`、実際の再開依頼を記録する `request`、その出所を記録する `source_ref` を指定する。これは担当が受領した指示の記録であり、この文字列自体を本人認証や新しい権限の証明にはしない。

対象は既存のPC修復3プロジェクトのうち、現在も元の作業場所が正規の保護判定を通るものに限る。未確認の復旧状態、本人停止、未回答の質問、外部待機、未完の依存、起動予約、実行中または待機中の担当、独立した子作業は変更しない。元仕様、履歴、作業場所、待機期限、モデル指定、保護判定は保持する。確認から保存までに元の行や依頼が変わった場合も保存しない。

成功は再開登録の保存であり、実起動ではない。その後の通常の `dispatch-one --id <ID>` が、従来の優先順位・資源・所有・作業範囲の条件を再確認する。実際の起動と処理の証拠を取得してから再開済みと報告する。guardの例外や期限、資格、失われた原保護設定を変更する手順ではない。

手動の起動要求には `dispatch-one --id <ID> --wait` を使うと、実行中の巡回を最大30秒待てる。既存の自動呼出しは即時のbusy応答を維持する。起動しなかった場合も、元の再確認期限と固定の準備失敗コードを返すため、単なる受付と実起動を区別できる。
